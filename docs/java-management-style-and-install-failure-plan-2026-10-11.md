## 1. 需求与已核实问题

用户认为设置中的 Java 管理页与整体样式不协调，并报告安装失败：

> Java 安装目录移动失败：目录被占用或没有移动权限，请解除占用并检查目录权限后重试

本次目标是统一页面视觉和交互层级，并定位实际使用目录中的安装失败，使真实安装可以完成登记、刷新和重载识别。

### 1.1 页面现状

- `JavaTab.vue` 已用一个 `UiCard` 包住管理组件，卡片底板本身沿用主题变量。
- `JavaManagerPanel.vue` 的视图切换使用两个 `NButton secondary`，管理操作主要使用默认边框按钮，空状态使用 `NEmpty`。标签、操作和提示之间缺少与项目通用控件一致的视觉层级。
- `JavaTab.css` 为扫描和空状态设置至少 200px 高度；截图中默认空状态图标、文字较淡，大块留白使页面显得松散。
- 项目已有 `components/ui/Button.vue`、`EmptyState.vue`、`Icon.vue`、`Loading.vue`，可复用其主题变量和状态表现。
- 管理组件也用于 `JavaManagerModal.vue`；页面样式调整必须验证弹窗复用。

## 2. 已选定的页面方案

保留现有单卡片及「已安装 / 下载」两个视图，统一卡片内的控件与信息层级。

### 2.1 工具栏

1. 两个视图入口组成紧凑的分段切换；选中项使用项目主题强调，未选中项使用低强调背景。使用实际按钮并提供可访问的选中状态、键盘焦点，不以业务操作按钮的强强调区分视图。
2. 「重新扫描」「检查更新」使用通用 `UiButton` 的低强调样式，配合已有图标；「添加现有 Java」作为主要管理入口，使用统一的次要按钮样式。
3. 标签与管理操作使用一致的高度和间距；窄内容区自然换行，操作文字和加载状态不裁剪。
4. 卡片头与内容区沿用已有分隔线、圆角、间距和表面变量，不修改通用卡片或全局主题。

### 2.2 搜索、空状态与列表

1. 保留现有搜索输入行为，调整尺寸、图标及布局，使其与工具栏密度协调；不重新实现输入或下拉组件。
2. 空清单使用 `UiEmptyState` 和项目图标，文字沿用主题的次要文字颜色，控制图标尺寸和上下留白。
3. 区分「没有登记的 Java」与「搜索没有匹配项」：前者提供「下载 Java」按钮，点击仅切换到下载视图；后者提供清除搜索入口。新文案同步六语言。
4. 扫描状态和空状态使用相近的内容区域尺寸，避免切换时明显跳动；不通过固定高度限制长列表。
5. 已安装条目、下载包条目和 Java 任务区域统一间距、字体层级及按钮风格；路径保持可换行或完整查看，错误文字允许换行。
6. JRE/JDK、版本和来源信息保持原有含义；失效、停用、使用中和被设置引用的状态仍然清楚可见。

### 2.3 业务边界

安装、选用和启动保持各自独立。保留安装计划审阅、移除确认、更新检查、启用停用、使用保护和已有 IPC 语义。空状态入口不自动安装、不自动选用 Java。组件自身不增加卡片，弹窗仍使用已有容器。

## 3. 安装失败的定位与修复方案

本部分采用「复现并收集证据 → 修复已确认原因 → 同目录验收」的顺序，不把单纯加长重试作为默认解决方案。

### 3.1 在实际目录中建立基线

1. 初始化并核对当前工作树所需子模块，检查适用规范、运行环境及实际启动器加载的后端提交；验证使用与日常运行一致的 Windows 账户和权限级别。
2. 读取实际 Java 管理目录的清单、临时目录、正式目录、待清理记录和目录权限，记录安装前状态；只保存必要证据，不输出账户、配置或个人目录细节。
3. 用独立诊断目录验证实际管理根目录内的创建和移动能力，确认 `.staging` 与 `installed` 的路径类型、权限继承和目录边界。诊断目录只清理本次创建的内容。
4. 通过真实启动器和正常 IPC 复现同一个 Java 25 JRE 安装，观察下载、解压、探测完成及提交时机。若目标已有内容，先核对登记和拥有权，不覆盖未知目录，不替换用户正在使用的 Java。
5. 如复现移动失败，在失败发生时检查相关 Java 进程是否已退出、是否存在目录或文件占用句柄，以及实际移动权限。使用系统已有诊断能力或工具；诊断证据保存在仓库外。

### 3.2 根据证据完成最小修复

| 已确认的原因 | 实施方向 |
| --- | --- |
| 本程序遗留进程或文件、目录句柄 | 在拥有该资源的代码处补齐等待退出和关闭路径，再进行移动；必要时修改 Core 探测实现并执行其测试。 |
| 本程序目录创建或权限处理错误 | 修正具体创建或权限处理逻辑，使同一运行账户具有所需移动能力；不改变用户整个数据目录或系统权限。 |
| 外部短暂占用，且可测得释放时间 | 在 Java 安装领域中调整有界等待，并记录必要阶段与耗时；确保持续失败仍有稳定错误码和安全回滚。 |
| 外部持续占用或外部策略拒绝 | 明确指出已确认的阻断条件和可操作恢复方式；不关闭安全软件、不自动提权。阻断解除并真实安装通过后才认定修复完成。 |

如果证据表明必须改变安装提交顺序、数据目录策略或采用复制替代原子移动，需要补充方案供用户审阅；这些更改不属于本方案预先授权的实现范围。

### 3.3 失败与诊断边界

- 保留现有安装目标、拥有权、路径边界和取消互斥检查。
- 新目录未移动成功时，不操作外部出现的目标目录；登记失败继续恢复本次新目录及旧版本，恢复失败保留备份。
- 如需增加生产诊断日志，只记录中文动作、失败阶段、系统错误码、尝试次数和耗时，不输出完整个人路径、请求体或日志专用编号。
- 检查失败清理是否覆盖原始异常或丢失重要证据；仅对实际发现的问题补修复及回归。
- 测试夹具用于模拟确定的占用与回滚边界，不能代替真实安装成功的证据。

## 8. 实施与验证记录

### 8.1 已确认的失败条件及实际修复

在原实际 Java 管理根目录中，独立空目录移动正常，根目录、`.staging` 和 `installed` 的权限继承规则一致。首次使用当前代码执行真实 Java 25 JRE 安装，再次复现探测成功、提交时 `WinError 5` 且 2.5 秒重试耗尽的失败。

随后对同一真实归档执行「解压 → 移动 → 移回 → Java 探测 → 再次移动」：探测前可以立即移动；探测后移动失败，延迟约 5.4 秒后恢复。诊断使用 Windows Restart Manager 查询可执行文件和 DLL 的占用，未返回占用进程；因此没有把具体安全软件或残留 Java 进程认定为原因。相关 API 仅用于仓库外诊断，参考 [Microsoft RmRegisterResources](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmregisterresources)。

依据上述持续时间，将 Windows 已知访问拒绝、共享冲突和锁冲突的等待窗口调整为最多 9.5 秒：初次尝试加最多 12 次重试，保留最初的 0.1、0.2、0.4、0.8、1.0 秒间隔，之后每次等待 1 秒。成功仍立即返回；POSIX 与其他错误不扩展重试；未知目标、拥有权、取消互斥和回滚边界保留。安装器接入共享日志器，补充中文系统错误码、重试次数与移动成功耗时；真实五秒占用验证记录了 8 次重试、约 5516 毫秒完成移动。

新增五秒持续占用回归在原实现上失败、修复后通过；持续失败回归核对最多 13 次尝试和累计等待不超过 10 秒，覆盖 Windows 错误 5、32、33 及 POSIX 分支。另在原实际根目录用真实 Windows 目录句柄阻止移动，五秒后释放，新实现约 5.5 秒成功，验证真实系统调用可恢复。
