## 1. 目标、范围与交付边界

目标是让“名称表达的职责、后台真实状态、用户看到的结果”一致：最后一次选择不会被旧请求覆盖，保存确认对应实际写入，任务从提交到执行结束持续可见，诊断能够说明原因并给出可执行的恢复入口。

本次审阅版默认范围为第 4 节的 P0—P6：已发现缺陷、关联领域模型、既有能力的体验闭环、Java 信息及缺少运行时提示。Java 自动下载单列为 P7，提供设计与验收要求，但需要用户明确纳入实施范围。资源收藏、整合包整体升级、OS 深链接、OptiFine 安装和内容寻址下载缓存留作独立专题，不随本方案默认实施。

工程整理随对应功能发生：修复身份问题时整理标识和路径，修复任务反馈时整理任务模型；不开展无行为收益的全仓重命名。大型组件仅按本次涉及的职责拆分，不同时重做布局、主题或状态管理框架。

## 3. 全阶段统一规则

### 3.1 标识、模型和兼容

| 概念 | 后端内部名称 | 前端业务名称 | 边界要求 |
| --- | --- | --- | --- |
| Minecraft 根目录 | `minecraft_root_path` | `minecraftRootPath` | 旧 IPC `game_path` 保留 |
| 磁盘实例目录名 | `instance_directory_name` | `instanceDirectoryName` | 旧 `version_id` / `versionId` 经适配转换 |
| 实际游戏数据目录 | `game_data_path` | `gameDataPath` | 复用现有隔离解析，不改变目录布局 |
| 原版游戏版本 | `minecraft_version` | `minecraftVersion` | 不与实例目录名互用 |
| 一次运行的进程 | `game_process_id` | `processId` / `selectedProcessId` | 旧进程事件中的标识字段保留 |
| 加载器模组 ID | `mod_id` | `modId` | 与在线项目身份分开 |
| 在线来源身份 | `source_project_id` / `source_version_id` | `sourceProjectId` / `sourceVersionId` | 同时携带平台 source，未知时不猜测 |
| 应用后台任务 | `OperationManager` / 应用操作引用 | `ApplicationOperation` / 应用任务模型 | 原 IPC 命令和 `game:operation_progress` 保留 |
| 下载速度 | `speed_bytes_per_second` / `speed_mib_per_second` | 明确 bytes/s 或 MiB/s 的字段 | Core/第三方参数不强行重命名，转换仅发生一次 |

新增稳定领域结构优先采用 Pydantic 或不可变 dataclass；IPC 的不可信字典尽早转换。前端在 API 适配层将旧字段转换为业务模型，受影响生产调用链统一迁移，避免两套可独立修改的业务对象长期并存。短作用域中的 `result`、`item` 等名称可保留。

删除兼容导入之前核对生产、测试及公开使用边界；如果旧别名存在已确认的外部消费方，则在适配位置保留并标注迁移，不先删除再修调用方。

### 3.2 请求与保存

读取请求同时捕获目标身份和请求代次。切换、清空、关闭、卸载都使旧请求失效；旧结果、错误和 finally 均不得改变当前状态。可取消请求时释放资源，但请求取消本身不能代替结果校验。

写入请求捕获不可变目标与提交内容。成功只确认该次内容；后续编辑保持脏状态并继续排队。已经提交的旧目标保存可以完成，但不得把结果写到新目标界面。失败保留待保存内容，不用“更新 UI 后当作成功”替代落盘确认。

### 3.3 用户反馈与日志

提交成功与执行完成分开。后台任务只由执行方给出最终成功、失败或取消；取消请求、等待超时和线程实际停止分开表达。中文操作日志按现有 `IpcLogPolicy` 与操作上下文记录动作、阶段、结果和耗时，不显示内部任务编号、凭据、完整命令或个人目录标识。

加载、空内容、加载失败、可恢复诊断使用既有 UI 组件。错误只由负责呈现的边界提示一次；有效旧内容是否保留取决于目标身份，不能把 A 的内容留在 B 的页面。界面操作以具体用户动作描述，不展示内部状态机或技术编号。

### P1：实例身份、目录切换与详情页面一致性

覆盖：N05、N09、FN03、F01、F03、F04、F10。难度：中高；前后端及缓存联动，衣柜为独立子提交。

主要文件：`ECL/services/game/workspace.py`、`scan.py`，`ECL/api/game.py`；`frontend/src/utils/path.ts`、`types/instances.ts`、`features/instances/stores/instanceStore.ts`、`features/instances/api/instanceWorkspaceApi.ts`、`composables/useResourceInstallTarget.ts`、`views/instances/InstanceDetailModal.vue`，模组、存档、截图、服务器及资源详情页，以及 `features/accounts/components/WardrobeModal.vue`。

实施步骤：

1. 扩展现有 `ResolvedInstanceTarget` 的内部语义，复用路径校验与隔离解析；区分根目录、实例目录、游戏数据目录。调用方逐步迁移，不建立另一套解析器。
2. 在扫描/工作区响应中增量提供根目录和实例的规范身份字段，前端 API 将其转换为 `rootKey` / `instanceKey`。身份基于服务端解析的实际路径；现有目录优先验证同文件/目录关系，不能用无条件小写合并。无法确认时保守保留区分。Windows 常规大小写别名、大小写敏感目录、POSIX 与符号链接分别验证。
3. 未有服务端身份的过渡数据使用明确路径策略，并只在一个工具中处理。`instanceWorkspaceApi`、扫描缓存、安装目标、选择恢复等使用同一身份规则；根目录 `/`、驱动器根、UNC 和尾斜杠不能归一成错误路径。
4. `switchPath` 使用独立选择代次；A→B→A 每次选择都推进代次，不只比较路径字符串。等待期间明确当前目标，返回后仅最新请求可以更新实例选择；持久化失败明确提示或恢复一致状态。
5. 详情组件以实例身份与 tab 共同确定生命周期；模组 watcher 观察完整目标。各页读取时捕获目标，统一检查结果、缩略图/图标、服务器状态与 loading/error。离开目标时清理选中项、编辑器及确认框。
6. 旧缓存键只在唯一对应时恢复选择；新旧键含歧义时重新加载并要求重新选择。身份缓存升级不改动用户实际目录；旧全局实例设置迁移保留原有兼容读取，避免把两个真实实例的配置合并。
7. 衣柜本地选择、账户纹理和官方披风分别捕获选择/账户身份及请求代次，每段纹理 await 后复核，结果完整后再提交对应预览。切账户、关闭、卸载均使请求失效；错误反馈同样校验目标。纹理加载可提取 composable，复用现有 URL 缓存与释放策略，不复制一套账户状态。

用户可见结果：快速切目录保持最后一次选择；同名实例不会混淆；详情只显示当前实例内容，旧请求不弹出当前页面错误；衣柜选中项、账户和纹理预览保持一致。

验收：目录乱序、多根目录同名实例、组件复用、同目标多次刷新、关闭后响应、所有隔离策略、路径根与大小写分支均通过；衣柜分别验证本地 old→new、账户 A→B、官方披风切换和关闭后的迟到成功/失败。文件操作仍经过后端边界校验，前端身份键不成为文件访问授权。

### P2：自动保存与共享配置可靠性

覆盖：FN02、F02、F05。难度：中高；涉及保存生命周期与原子更新。

主要文件：`ECL/utils/config.py`、`ECL/api/settings.py`、`models.py`、`registry.py`、`operation_logging.py`；`frontend/src/components/instances/InstanceDetailProfileTab.vue`、`InstanceDetailSettingsTab.vue`、`features/settings/stores/settingsStore.ts`、`features/settings/api/settingsApi.ts`、`composables/useResourceInstallTarget.ts`、下载设置及另存为目录调用方。

实施步骤：

1. 资料页借鉴现有设置页 saveChain：捕获目标、表单快照和 payload，按目标串行保存；成功只更新该快照，后续编辑再次提交。去掉将响应到达时最新表单当作已保存的逻辑，以及以裸 `Record<string, unknown>` 改写稳定业务模型的路径。
2. 保存队列的生命周期独立于当前 tab。关闭/卸载时将最新脏快照交给队列，待保存内容不会因清理 debounce 计时器而消失；切换实例不把旧表单提交给新目标。
3. 保存失败保留失败快照与最新编辑，可再次编辑或重试；不新增每次保存都要确认的弹窗。恢复成功后清理对应错误，不能清除其他目标的失败。
4. 增加正式 `settings_download_patch` IPC（建议名），采用明确的 Pydantic 请求模型，仅开放现有 download 字段：mirror_source、按类型的 resourceInstallCache、resourceSaveDirectories。两个映射按指定键合并，未传键保持不变；“无绑定”沿用现有空记录语义，不等同删除全部缓存。
5. `ConfigStore` 在同一个锁内完成读取、校验、局部合并和原子落盘，写失败保留旧内存/磁盘状态；成功后广播变更并返回已确认分区。IPC 在线程边界调用阻塞磁盘操作，并声明中文日志策略、注册和模型覆盖测试。
6. 所有项目自身 download 写入调用方迁移到该局部接口；settingsStore 继续维护共享队列与已确认状态，资源选择 composable 不再直接“读取整段→写回整段”。保留 `settings_set` 的已有全量替换契约，但不拿它作为并发局部更新入口。

用户可见结果：修改资料后切页仍保存最新内容；不同资源类型记忆各自目标，切下载源也不会丢选择记录。保存失败不显示成功，不用额外确认按钮改变即时保存体验。

验收：提交 A 时编辑 B、A 成功/B 失败、保存期间切实例与卸载；两资源类型和镜像源并发更新；其他字段保留；字段校验失败及原子写失败回滚。旧接口全量替换仍按原契约工作，其外部调用方不在局部更新保证之内。

### P3：应用任务与异步动作反馈

覆盖：N03、N07、N10、U02、FN01、FN05、F06、F08、F09。难度：高；跨任务事件、查询和 UI。

主要文件：`ECL/services/operations.py`、`ECL/services/game/operations.py`、`base.py`、`install.py` 与各长任务提交 API；`frontend/src/app/runtime/useAppRuntime.ts`、`composables/useTaskQueue.ts`、`useAsyncAction.ts`、`components/panels/TaskQueuePanel.vue`、`features/instances/stores/modpackImportStore.ts`、`instanceInstallStore.ts`、`features/plugins/stores/pluginStore.ts`、`views/Plugins.vue`。

实施步骤：

1. 应用注册表继续使用现有 `OperationManager`，整理 `_game_operations` 等过窄内部名称；确认消费方后处理游戏领域兼容别名。正式 IPC 和事件名保持兼容，在适配层形成应用任务模型。
2. 前端任务条目容纳任务类型、后端标识、目标身份、展示名称、进度单位、取消/重试能力；类型不再限于 install/download。后端未明确支持重试的任务不展示直接重试按钮。
3. 在线整合包/导入首先接入，随后纳入已有复制、导出、修复、存档备份与资源操作。收到 operationId/taskId 立即登记任务；事件可能先于回执，因此登记必须幂等并按后端标识合并，不能生成第二条重复任务。
4. 查询补齐漏掉的最终事件；切页保留任务。乱序或重复进度不能把结束任务改回运行中。安装/复制等完成后只刷新对应目标一次；提交时不刷新成“已完成”。启动器重启可读取已有持久化结果，但不新增断点续执行保证。
5. 内部统一任务状态，适配现有 failed/error、cancelled/canceled；请求取消保留运行信息，直到执行方确认停止。等待超时提示状态待确认，而非直接记成取消。
6. `clearCompleted` / `completedCount` 改为 `clearFinishedTasks` / `finishedCount`，界面使用“清理已结束”；显式清理包含成功、失败、取消，运行与取消待确认条目不能清理。失败原因在用户清理前保留。
7. 安装和整合包 store 的提交状态改为 `isSubmittingInstall`、`isSubmittingImport` 等；真实执行状态由任务模型提供。速度在内部注明 bytes/s、MiB/s，并核对 Core 边界只换算一次。
8. 为 `useAsyncAction` 增加明确结果入口（如 runResult），区分 success、failed、cancelled、skipped；现有 run 作为兼容包装。插件重复提交返回 skipped，按插件身份限制冲突动作；不同插件可独立执行。成功消息只有执行成功的调用发出，共用 loading 用在途计数或动作集合管理。
9. 加载器/Fabric API 请求按目标与类型管理代次；清空、空版本、切回 Vanilla、关闭也使请求失效。移除强制截断，选择器保留全部返回版本并可搜索；列表渲染使用既有组件能力，必要时虚拟化，不引入不可见的 20 条上限。

用户可见结果：导入后可持续看见进度、失败和取消结果；重复点击不出现虚假成功；安装可选版本完整，清空后旧列表不会返回。

验收：事件早于回执、终态与迟到进度、漏事件查询、重复登记、切页、取消未停止、失败记录清理；插件重复/冲突操作只执行一次并只提示一次；30 条以上加载器列表全部可达；清空后旧成功/失败/finally 不影响当前状态。

#### P3-T：工具页下载的控制状态、查询恢复与校验

覆盖 T03—T07，并联动 T08 的领域模型命名；在 P3 中作为优先子批次，随统一应用任务状态实现。

主要文件：现有 `components/connect/CustomDownloadCard.vue`、`features/download/stores/customDownloadStore.ts`、`app/runtime/useAppRuntime.ts`、`ECL/services/custom_downloads.py` 及下载 IPC；拟新增 `features/download/api/customDownloadApi.ts`、`features/download/customDownloadValidation.ts`。组件路径在 P6-T 搬迁后更新，禁止旧路径和新路径各维护一套控制器。

1. 下载 store/会话控制器拥有完整的表单、提交互斥、正在请求取消、跟踪任务及查询错误状态，表单组件仅调用动作。提交回执未到时跨页重挂仍处于提交态，不允许再次发起；离开页面不取消已经提交的后台下载。
2. 每次提交/重试捕获参数和动作代次；任务回执按所属提交关联登记，不能由已卸载组件覆盖新跟踪任务。HTTP 请求头编辑行建模为 HeaderRow，转换后的 headerByName 仅用于 IPC，不把 UI id 作为 HTTP 头字段发送。
3. 任务进度由 P3 应用任务状态统一维护，卡片和任务面板读取同一条任务；集中查询串行执行，使用查询代次及终态保护。取消发起后显示请求状态，实际停止以执行方终态为准；旧 running 快照不能恢复已确认结束的任务。
4. 查询失败保持“暂无法确认当前状态”，在会话控制器中有上限地退避重查；连续失败后保留“刷新状态”入口，不错误开放再次提交，也不把查询错误冒充下载失败。恢复后清理查询错误，释放定时器的时机由会话宿主决定。
5. 保留 currentDraft 与 lastSubmittedDownload 的独立语义；卡片区分“重试原任务”和按当前表单“开始下载”。重试使用原意图和原目标，界面简洁说明，不展示内部任务编号或完整敏感请求头。
6. 提取前端文件名/请求头校验，以跨语言共同样本验证原后端 DownloadPolicy；补 CON .txt、设备名带空格变体、Unicode 名称、尾点/空格、UTF-8 长度和头字段冲突等边界。后端仍为最终校验边界，前端不复制下载服务。
7. 命名使用 isSubmittingDownload、isRequestingCancel、isTaskRunning、queryError、headerRows 等表达不同职责。原 operationId 等协议字段保持兼容，不用一个 busy 变量承担全部操作状态。

验收：提交 A 未返回就切页/重挂，后台只收到一次提交；B 与 A 回执乱序不造成任务标识和展示不一致；cancel 查询与旧 poll 乱序不回退终态；查询失败可恢复且没有无限重查；更改表单后重试仍明确使用原参数；前后端共同样本接受/拒绝一致。将新增探针转为真实挂载、store 和后端回归测试。

### P4：本地模组身份、来源与依赖诊断

覆盖：N01、N06、N08、U01、U03。难度：高；加载器元数据与在线来源联动。

用户可见结果：模组详情打开正确平台；缺依赖能区分“没装”“被禁用”“版本不对”和“无法判断”，并提供对应操作。

验收：审计四条依赖样本与错误平台跳转回归；必需/可选、多声明、提供别名、禁用内嵌容器、重复提供者、复杂未知谓词、损坏 Jar；在线查询失败仍显示本地清单，离线来源未知可搜索，不冒充已识别。

## 7. 兼容、数据保护与失败恢复

- 配置继续即时保存；新增局部接口保留原配置格式与其他字段，写失败不更新已确认状态。旧目标记录读失败采用明确未绑定，不自动替换成另一实例。
- 身份键变更只影响比较、缓存和适配，不移动实例目录；有歧义的旧键不自动迁移，原配置保留供恢复。数据库/文件字段迁移在同功能提交中记录读取顺序与回滚方法。
- 依赖诊断不自动删除、禁用或下载模组；未知版本规则显示未知。来源反查失败不阻止本地列表。
- 实例健康诊断不把有效继承版本误判损坏，不删除损坏目录。复制、修复、恢复和安装沿用临时目录/原子提交，失败保留原实例及用户文件。
- 请求失效限制界面更新；已提交写入和实际工作线程依服务状态完成，不能把前端关闭说成服务已停止。
- 回滚按功能提交逆向处理，并检查新增字段的向后兼容。涉及用户数据时先恢复兼容读取，再撤销界面入口；不靠删除用户文件回滚。
