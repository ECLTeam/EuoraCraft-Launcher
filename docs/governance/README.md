# 外部规范与工程治理

本目录维护采用的外部条目、实际覆盖和检查证据。项目规则入口仍为 [AGENTS.md](../../AGENTS.md)，检查命令集中在其第 6 节。

## 覆盖记录

记录包括来源条目、业务范围、维护角色、测试/人工检查入口、实际结果、未覆盖范围及关联问题。状态使用“待调查、部分覆盖、已覆盖、不适用”；没有证据不得标为已覆盖。不适用必须写原因。

报告通过只说明记录的工具、依赖解析版本和场景通过。依赖审计发现的是版本公告，不能直接推断产品已可被利用；自动可访问性扫描无法证明完整 WCAG 合规。

## 门禁与证据

独立工具 [governance.py](../../ECL/tooling/governance.py) 使用标准库校验报告，不加载应用、不自动修改依赖。扫描采集与门禁校验分开：采集命令成功表示得到完整报告，`check` 才决定该报告是否允许通过。

- 有效报告且无未处置发现：通过。
- 新增违规、未人工复核的 `incomplete`：失败。
- 工具异常、报告空缺或损坏、依赖跳过、实际页面未打开、覆盖为空：失败。
- 例外过期、重复、超期或在对应范围不再匹配：失败。

报告放在 `build/governance/`，CI 产物保留 14 天。每份报告记录工具版本、UTC 时间、平台、源码提交和 gitlink；依赖报告保存实际版本清单，浏览器报告保存场景、窗口及引擎版本。使用合成数据，不上传账户、完整配置及真实个人路径。定期工作流每周上海时间周五 03:00 运行，不自动通知他人或批量建单。

扫描依赖服务失败时保持失败并重试，不使用忽略注册表错误、自动修复或忽略无修复版本等参数。PR 不使用发布凭据，不通过 `pull_request_target` 执行 PR 代码。工作流失败与分支保护 required check 是不同状态；仓库设置和远端 CI 未核实前不声明远端门禁已生效。

## 有限期例外

[exceptions.json](exceptions.json) 是唯一例外来源，当前仅包含有证据的对比度人工复核，没有依赖漏洞豁免。CI 不自动用扫描结果更新它。维护者必须审查变更及其批准依据；AI 不自行接受风险。

每条例外必须填写：`scope`、`rule`、`subject`、`location`、`repository`、`reason`、`issue`、`approval`、`owner`、`approved_on`、`expires_on`、`risk`、`disposition`。同一场景和规则的复核可用 `locations` 精确位置列表替代单个 `location`；逐项匹配，新增位置不能被旧列表放行。日期采用上海日期的 ISO 格式；`disposition` 为 `temporary` 或完成证据核对的 `manual-review`，后者用于自动工具不能下结论的人工复核，不能豁免已确认违规。

依赖的对象和位置分别为精确包名、已安装版本；规则使用工具原始公告标识。可访问性对象和位置分别为完整场景名称、报告中的节点定位；规则为 axe 规则。报告保留 axe 原始 `target`；含组件生成 ID 的节点另存经过唯一性验证的精确 `governance_target` 结构定位，优先用于门禁匹配，不修改页面属性。禁止包名、版本、页面和选择器的通配忽略，不允许全局禁用。

严重、高危、未知风险或涉及凭据/越权/用户文件的问题最多 7 天复核，其余依赖和可访问性项目最多 30 天。关键风险须用户明确处置；延长须重新审查。确认误报或不适用也须保留证据，不把版本命中直接当成可利用漏洞。

普通问题按 [贡献指南](../../CONTRIBUTING.md) 查重登记，以用户影响归并，不按公告数量机械拆单；公开报告不包含敏感漏洞细节。独立修复遵循已批准范围。可访问性人工复核写明场景、实际检查方法及证据，不能把全部 `incomplete` 自动登记为已复核。

## 跨仓库调用

主仓库使用当前提交的工具和例外。前端独立 CI 从其 `tests/browser/governance-revision.txt` 固定的主仓库提交只读取治理文件，不跟随浮动 main；更新治理规则后同步该引用。先交付主仓库工具提交，再交付前端引用，最后更新主仓库 gitlink，避免循环引用。
