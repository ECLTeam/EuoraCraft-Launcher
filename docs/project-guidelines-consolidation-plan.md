## 5. 拟采用的关键条文

### 5.1 规范维护与冲突处理

- 新规则应归入对应职责章节，合并重复表述，不按对话顺序持续追加独立小节。
- 通用原则负责共同约束，语言或平台章节只补充其专属要求；同一命令和验收门槛只保留一个权威定义位置。
- 同时适用且可以共同满足的要求按较严格者执行；直接矛盾时不能自行选择，应明确冲突并向用户确认。用户本次明确指令优先于仓库默认约定。
- 新规范约束后续新增或修改的代码；存量问题随相关功能收敛，禁止借规范整理发起无关的全仓重构。

### 5.2 业务命名与术语

- 名称直接表达业务对象、动作与结果；禁止项目自造缩写、无定义的隐喻和无法说明职责的泛化名称。
- `Manager`、`Context`、`Policy`、`Resolver`、`Registry` 等后缀必须对应实际职责，不设词语黑名单，也不以更长或更专业的名称作为改进依据。
- JVM、IPC、OAuth 等通用术语保留；项目专有概念在所属模块或已有相关文档首次出现时用中文定义，同一概念跨代码、文档、日志和界面保持一致。
- 内部标识符沿用各语言现有命名风格；面向用户的描述使用清楚的业务语言，不泄露内部实现术语。
- 第三方属性、环境变量、外部协议字段和 Python 魔术属性遵循其契约。项目自有协议字段允许在批准方案中同步更新，不保留无需求的旧字段别名。

### 5.3 逻辑可读性

- 业务流程应能按代码顺序理解前置检查、执行、副作用、结果提交和失败清理；失败路径与正常路径应清楚可辨。
- 避免嵌套三元表达式、多层否定、依赖隐式真假值的业务选择以及包含多个副作用的表达式；清晰的单条件表达式和纯数据转换无需机械展开。
- 通过提前返回、语义明确的局部变量和有业务意义的函数划分降低阅读成本，不把简单过程拆成大量仅转发一次的函数。
- 注释说明约束、原因和优先级，不用长篇注释替代清晰实现；保留已有文件头和中文多行 docstring 要求。
- 不新增固定函数行数或嵌套层数门槛；先判断业务规则是否集中、流程能否直接读懂。

### 5.4 抽象与依赖边界

- 新增基类、工厂、适配层、注册表或通用框架，必须在实施方案中指出当前调用方和解决的问题；未来可能扩展不构成单独依据。
- 优先使用普通函数或职责明确的类；有真实复用、必要的资源生命周期或外部扩展契约时再引入对应抽象。
- 固定映射和条件分支按语义选择，不为了禁止某种语法而增加分支，也不为保存一张表专门创建无业务职责的类。
- 保留“不新增脱离领域归属的模块级私有业务映射”要求；规则放入已有领域类或使用清晰分支。归属确有困难时在方案中说明。
- 使用固定提交的子模块时围绕该提交的真实公开接口编程；无明确多版本支持需求时，不用属性探测、签名探测或多种返回形态维持旧调用方式。外部插件明确声明的可选能力另按其契约处理。

### 5.5 状态、输入与失败

- 同一业务状态只有一个权威维护者，其他模块通过其公开接口读取或订阅；派生值优先计算，不维护多份可独立修改的等价字段。
- 覆盖顺序由所属领域统一定义并测试，不由多个页面和接口重复拼装。
- JSON、IPC、网络和插件输入在边界校验，进入业务层后使用明确模型；保留前后端原有类型约束。
- 区分首次运行缺少文件、未配置、损坏、网络失败与程序缺陷；不能将失败转换为空数据或成功结果来掩盖问题。
- 默认值、重试、回退和缓存均须有当前业务依据；回退明确触发条件、结束条件、可观察结果和副作用，不要求每个外部操作都增加备用路径。
- 保留原有并发保护、请求失效、原子写入、回滚和资源关闭要求；取消等待不等于执行已停止。

### 5.6 未正式发布阶段的兼容策略

- 按当前未正式发布阶段定位，项目不默认承诺内部配置、IPC、自有持久化格式和模块接口的历史兼容；未来建立兼容承诺时须单独确认支持范围。
- 内部契约变更同步更新生产方、消费方、类型、测试和文档，并移除废弃入口；不得主动增加旧字段别名、双格式读写、旧接口转发和自动迁移。
- 必要的迁移作为明确需求处理：方案写明实际使用者、数据范围、不能直接替换的原因、失败处理和迁移代码退出条件，经用户确认后实施。
- Minecraft 版本、操作系统、整合包与外部协议按产品明确的支持范围维护，不按名称中是否出现 `legacy`、`compat` 或“旧版”判断应否删除。
- 不兼容不授权删除或覆盖存档、实例、账户凭据及用户文件。遇到不支持或损坏的数据保留原文件，明确失败原因；仅对已经确定可重建的缓存或经批准可重置的偏好执行对应重建或重置。
- 备份、事务恢复、崩溃恢复和安装失败回滚属于数据安全，不因取消历史兼容而删除。
- 完成替换时清查旧调用方、配置字段、类型、事件、接口、测试和文档；不得仅为维持旧测试而保留废弃实现。
- 不为取消旧格式支持而新增扫描和清理用户历史文件的后台流程；是否拒绝、忽略特定字段或重置偏好由具体功能方案明确。

### 5.7 测试、交付与远端操作

- 完整保留功能变更提交前通过测试、缺陷修复提供回归测试、平台分支与主仓库集成验收要求。
- 后端统一列出 `ruff check ECL tests`、`ruff format --check ECL tests` 及相关 pytest；CI 的其他适用检查仍是最低门槛，不因集中整理缩减。
- 前端统一规定先 `pnpm check`；UI 或运行流程变更继续 `pnpm build` 并实际启动启动器验收。真实浏览器布局与真实启动器验收不能由 jsdom 替代。
- 文档变更按影响执行链接、引用、内容与差异检查；仅规范文字重排无需启动应用或重复执行与变更无关的功能测试。
- 功能完成后立即提交，使用中文描述的 Conventional Commits；文档整理实施完成后也以独立 `docs` 提交交付。
- 本地提交、原工作区本地 `main` 集成与远端推送分别报告。交付时检查工作树和无关改动；涉及子模块时先集成相应子仓库本地 `main`，再集成主仓库指针与本地 `main`，不能覆盖其他工作。
- 每次远端推送需要针对当前变更的明确授权；方案批准、实施批准、提交与本地同步不自动授权推送或发布。
- 需要推送或发布时，保留全部子模块指针核验、先子后主、CI 结果与产物下载检查，不因只改文档而跳过推送检查。

- 规范继续膨胀：单一入口、共同要求只定义一次，不增加每个改动都要填写的模板或额外审批层。
- 子仓库误用：本次不修改子仓库规范；后续触及子仓库时先读取其规则，有冲突时先明确适用范围。
- 交付误报：规范整理完成不代表存量代码已经符合新规，也不代表任何兼容分支已完成清理。
