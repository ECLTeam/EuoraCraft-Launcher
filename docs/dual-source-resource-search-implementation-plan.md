## 调研结论与方案取舍

当前 `OnlineModSearch.vue` 将空来源值回退为 Modrinth，后端 `search_mods` 只调用一个平台。热门预取也以 Modrinth 为主。已有 `alternatives` 数据结构和详情来源切换可以复用。

PCL-CE 的 `ModComp.cs` 使用独立平台偏移量、累计结果池和不足一页时继续读取。其下载量倍率和宽松 `IsLike` 判断不适合作为 ECL 的规则；同一批候选在批量加入结果池之前完成过滤，也不能可靠消除批内重复。ECL 将采用逐项更新身份索引，覆盖批内和跨页去重。

| 方案 | 行为 | 取舍 |
| --- | --- | --- |
| 每页查询两边后交错合并 | 实现较少，两个平台各自直接翻页 | 页长变化、跨页重复、重复多时缺项 |
| 独立读取位置＋统一结果池（已选择） | 聚合去重、按需补齐，每页 20 项 | 需要会话缓存和渐进分页，最终数量只能在读取完成后确定 |

范围为下载页的模组、资源包、光影、数据包、整合包。存档继续使用 CurseForge；FTB 保持整合包的独立来源选项，不进入此次双平台聚合。明确选择单个平台时保留现有单源检索和分页行为。实例管理中的 `game_resource_search` 不改为双平台。

## ECL 的身份合并规则

身份判断与排序分开，排名相近、描述相同或下载量相近不代表同一项目。

1. 同平台以 `(资源类型, 平台, 项目 ID)` 唯一标识去重。不同平台的相同数字 ID 不视为同一项目。
2. 模组、数据包优先使用 MC百科映射中的相同非空百科 ID；同时要求资源类型相同。若双方存在不同百科 ID，则拒绝使用后面的弱规则合并。
3. 没有共同百科映射时，跨平台仅在非空的 slug、原始项目名称、作者三者全部规范化后相等时合并。规范化使用 Unicode NFKC、大小写折叠、首尾空白及连续空白收敛；slug 额外统一空格、下划线和短横线。不删除所有标点，不以翻译显示名替代原名。
4. 任一必需字段缺失、出现冲突或匹配到多个既有项目时，保留独立卡片。描述、更新时间、加载器列表不参与身份判断，避免将分支项目误合并，或因两个平台发布进度不同漏掉强身份匹配。
5. 每个合并组最多保留一个 Modrinth 项目和一个 CurseForge 项目；同平台的不同 ID 即使共享百科条目也不自动折叠。冲突组不继续执行传递性合并。

候选逐项处理并立即更新来源 ID 索引、百科索引和完整身份签名索引。处理顺序固定，不受网络先返回的平台影响。比较索引候选而非将每个候选遍历整个缓存。

合并组保存稳定的 `groupId` 和两个 `alternatives`。展示字段使用已确定的主条目，优先补齐缺失字段；主条目在首次展示后固定。两个平台下载数不相加，作者信息不拼成虚构作者，详情和文件版本始终按用户选择的实际平台查询。

## ECL 的排序规则

本次特点是「平台内排名融合＋名称相关性＋稳定分页」。采用通用排名融合思路，再定义适合 ECL 的规则；不声称创造了新的通用搜索算法。

### 默认排序与相关性排序

每个平台按照对应 API 排序提供候选。候选在该平台的排名 `r` 从 1 起，使用原始读取偏移量加批内位置计算；去重前后都不重置排名。

对一个合并组定义：

```text
u(s) = 60 / (60 + r(s))
rank_score = max(u(s)) + 0.15 × second(u(s))
final_score = rank_score + 0.60 × title_match
```

只有一个来源时，`second(u(s))` 为 0。另一个平台也找到同一项目时给予适度佐证加分，不将两边下载数相加，也不使用固定的 Modrinth／CurseForge 下载量倍率。

`title_match` 取以下条件中的最大值：

| 命中方式 | 值 |
| --- | --- |
| 查询与原名、slug 或 MC百科译名规范化后完全相等 | 1.00 |
| 查询是上述名称的前缀 | 0.70 |
| 查询的全部非空词项均出现在同一个名称中 | 0.40 |
| 其他情况，或空查询 | 0.00 |

词项按空白分割；连续中文按一个词项比较，避免将常见单字命中放大。名称匹配只用于默认／相关性排序，描述不产生身份依据或排序加分。中文搜索仍复用已有英文查询转换，排序同时保留原始用户查询。

空查询时，「默认」明确请求两个平台各自按下载量排序，再以平台内排名融合。用户的「下载量」和「关注数」同样采用对应平台排序后的排名融合，以避免平台计量口径差异。关注数沿用现有平台参数映射，不承诺两边统计口径一致。

同分项目按来源轮换选择，让两边同等排名的项目交错出现；只有一边有候选时连续取该边。合并组计入主来源。最终同源同分以来源项目 ID 确定顺序，结果不随响应先后变化。不强制 1:1 配额，不将明显低相关的项目提前。

「最新发布」和「最近更新」使用两个平台的实际时间字段排序，缺失时间排到当前候选末尾；日期解析统一为带时区的 UTC 时间。规范化时补齐创建时间字段，不以更新时间冒充创建时间。

### 翻页稳定性

结果池分为已展示的固定顺序和未展示候选。补齐下一页时只对未展示候选重新评分，追加到固定顺序；已经展示的项目不会因另一平台晚返回而移动页码。

如果后续候选对应已展示项目，只补充其另一来源入口，不新增第二张卡片。返回上一页时读取最新合并元数据，不能直接使用过期的页面副本。

排序是按已取得的候选渐进融合，不保证对两个平台的全部项目进行全局排序。刷新会建立新会话，因此可能改变顺序。

## 平台读取、会话与错误处理

### 请求与响应

- 为 `search_mods` 增加独立 Pydantic 请求模型；不用约束不同的 `ResourceSearchRequest` 代替。
- 全部来源使用明确值 `all`；旧的省略来源请求继续默认 Modrinth，实际项目来源仍只允许 `modrinth`、`curseforge`、`ftb`。
- 聚合请求包含既有筛选、排序、每页 20 项，以及 `session_id`、`page`、`refresh`。筛选与会话不匹配时拒绝复用；聚合模式不允许用 offset 绕过会话直接跳远页。
- 响应保留 `items`、`sources`、`query`，补充 `sessionId`、`page`、`hasMore`、`totalExact`、`truncated`。聚合 `total` 表示当前已知唯一项目数，只有 `totalExact=true` 时才是最终数量；平台原始总量只放在各自状态中。
- 来源状态区分可用、缺少配置、请求失败、已耗尽，并保留稳定错误码。所有业务结构使用明确类型，第三方 JSON 在边界校验后进入业务层。

### 读取与补齐

1. 会话记录 Modrinth、CurseForge 各自的 offset、已读原始项数、平台报告总量、是否耗尽和错误状态。
2. 每轮并行读取两个尚可用且未耗尽的平台，每个平台 20 个原始项目。offset 按原始返回数推进，不按合并结果数推进。
3. 原始网络请求完成后顺序规范化、建立索引、合并。MC百科数据在并行读取前完成初始化，避免其现有惰性加载参与并发写入。
4. 对未展示候选排序后补齐下一页；不足时继续读取，最多每次操作 3 轮。保留多出来的候选供下一页使用。
5. 达到轮数预算但仍不足一页时允许短页，保持 `hasMore=true`；已展示页长及内容固定。若没有新增项而仍可能读取，展示继续读取／重试状态，不制造空白页，也不将预算耗尽当作搜索结束。
6. 上游返回空批次或读取位置达到有效的上游总量时标记耗尽。暂时错误不标记耗尽；总量变化不能倒退 offset。缺失／异常总量依靠空批次结束。

### 有界缓存与并发

- 新增由游戏服务拥有的搜索会话服务，使用独立会话锁；不在网络读取期间持有游戏全局锁。
- 每个会话同一时间只能扩充一次；相同条件的第一页与预取共享会话和在途任务，刷新使用新的会话代次，旧响应不能覆盖新列表。
- 后端有界执行器最多 4 个平台请求并发，入口等待有超时；不创建无限制线程。平台请求沿用现有网络超时，不增加无限重试。关闭游戏服务时禁止新请求，清理会话并关闭执行器。
- 热门预热改用 `all`，预热上下文并发降为 1；后台预热最多占用一对平台请求，为前台搜索保留另一对容量。前台同条件请求复用后台任务。
- 会话仅保存在内存：10 分钟空闲过期，最多 16 个会话，按最近使用淘汰；正在扩充的会话不被直接删除。容量占满时先淘汰可淘汰会话，否则返回可重试的忙碌错误。
- 单会话最多缓存 2,000 个唯一项目，或累计读取 8,000 个原始候选。达到上限时返回 `truncated=true`，提示细化筛选；不将截断总数伪装成完整搜索总数。
- 前端原有 24 小时页面状态不能继续携带过期会话；服务返回会话过期时清理对应缓存、回到第一页并重新搜索一次，避免无限重试。

### 失败与筛选

- CurseForge 未配置时跳过请求，在来源状态中说明，仅使用 Modrinth；不使整个列表失败。
- 一个平台失败且另一平台成功时保留成功结果及失败来源提示。失败来源在本次扩充操作内不重复请求，下次主动继续或重试时从原 offset 重试。
- 两个平台均失败且无可用缓存时返回失败，前端显示错误及重试入口；如果有缓存则保留缓存并显示失败状态，停止该次补齐。
- 两个平台都成功返回空结果才是正常无结果。加载状态在成功、失败、会话过期和过时请求场景均能退出。
- 全部来源的模组搜索应向两个平台传递相同游戏版本与加载器筛选；当前 CurseForge 搜索遗漏加载器参数，此次一起修复并覆盖参数测试。其他资源类型不施加模组加载器限制。
- 密钥只用于后端平台请求，不进入缓存键、响应或日志。

## 页面行为

- 「全部来源」默认使用上述聚合，单平台选项继续可选，整合包保留 FTB，存档保留固定 CurseForge。
- 聚合分页显示当前页、首页、上一页、下一页。读完时显示最终页数；聚合模式去除跨 10 页和直达末页按钮，避免为了跳页触发大量补齐。单平台保留既有分页。
- 一页 20 项；候选耗尽后的最后一页允许不足 20 项。预算限制产生的短页显示可继续读取状态。
- 卡片显示双平台来源标识，详情沿用已有来源选择器。默认详情使用该卡片固定主来源；切换来源后详情、版本列表和安装请求使用该来源真实项目 ID。
- 保持上轮已完成的透明搜索加载背景与「实例」导航名称。
- 更新六种语言的分页、来源状态、重试和截断文案。错误要在列表区域显示；不能依赖当前 `useAsyncAction` 吞掉异常之后的 `.catch` 来提示。
- 同步更新 showcase 传输的搜索返回结构，避免展示模式与实际后端类型不一致。

- 身份：相同来源 ID、跨平台 ID 碰撞、共同百科、百科冲突、完整签名匹配、缺字段、同名分支、同批重复、跨页重复、同平台不同 ID、歧义候选。
- 合并：两个 alternatives 均保留；后续命中更新已展示项且不新增卡片、不移动页码、不混用下载 ID。
- 排序：精确名与前缀命中、中文译名、空查询、两平台下载数尺度差异、双来源佐证、同分轮换、日期缺失、响应先后变化、稳定翻页。使用可计算期望的样本，不仅比较函数与自身输出。
- 分页：独立 offset、按原始数推进、重复多时补齐、短尾页、预算短页、无新增但未耗尽、失效会话、筛选变化、刷新、容量上限、TTL 与淘汰。
- 故障与并发：未配置密钥、单源失败、双源失败、缓存保留、重试位置、同会话并发、不同会话并发上限、服务关闭、MC百科初始化；使用同步屏障测试并发，不依赖长时间 sleep。
- 参数：CurseForge 模组加载器与版本过滤、各资源类型分类、MR facets、单源和 FTB 回归；平台分支覆盖 Windows 与 POSIX。
- API：非法来源／类型／页码／限额、会话与筛选不匹配、正常和降级响应、前端字段契约。
- 必须通过 `ruff check ECL tests`、`ruff format --check ECL tests` 和 CI 对应完整 `python -m pytest --tb=short -q`；核对 Ruff CI 的仓库级检查要求。

## 风险与回滚

- 保守去重会留下无法可靠确认的跨平台重复，这是避免误合并的取舍；以后可以在明确的跨平台映射数据基础上扩展规则。
- 上游列表会随热度和更新变化，offset 分页无法提供互联网数据快照；会话索引能去掉重复，但不保证捕获搜索期间发生移动的全部项目。
- 多平台搜索增加网络请求和内存使用，以上并发、轮数、TTL 与容量限制必须落实。
