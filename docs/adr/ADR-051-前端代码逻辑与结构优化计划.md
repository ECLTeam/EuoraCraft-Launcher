## 背景

`frontend/src/` 经过多次迭代，积累了一些结构性问题：

- `types/api.ts` 膨胀到 2084 行、135 个 export，成为巨型单文件
- `api/client.ts` 322 行承担了 IPC 调用、事件、配置、文件系统、图片加载等多重职责
- 不同 feature 的目录结构模式不统一
- 各 store 的 loading/async 状态管理各自为政
- 缺少数据请求缓存/去重层，每个 store 手动实现
- `valibot` 已引入但未在 API 层做输入校验

前端开发者仅一人，不需要做向后兼容的过渡方案，直接一次性迁移。

## 计划项

### P1：拆分 `types/api.ts` 为领域类型文件

**现状**：单文件 2084 行，所有 DTO 都挤在一起。100 个文件 import 自 `@/types/api`，但每个文件只用到其中一小部分类型。

**方案**：

```
types/
├── index.ts              ← 统一导出入口（在其他模块全部改完后删除）
├── api.ts                ← 保留：ApiResponse, JsonDict, COMMAND_NAMES,
│                             CommandPayloadMap, CommandResponseMap,
│                             BackendEvents, BackendEventName, ConfigSection
├── config.ts             ← LauncherConfig, BackgroundConfig, GameConfig, 等配置
├── accounts.ts           ← MinecraftAccount, AuthProvider, 等账户类型
├── instances.ts          ← InstanceProfile, ScannedVersion, GameInstance, 等实例类型
├── connect.ts            ← ConnectorStatus, RoomCode, 等联机类型
├── plugins.ts            ← PluginManifest, PluginSlot, 等插件类型
├── mods.ts               ← Mod, GameResource, McmodData, 等 Mod 类型
├── game.ts               ← MinecraftVersion, LoaderType, VersionRunStats, 等游戏类型
├── system.ts             ← JavaInstallation, SystemMemoryInfo, 等系统类型
├── fs.ts                 ← FsEntry, FileContent, PathInfo, 等文件系统类型
└── events.ts             ← 事件相关类型
```

**迁移策略**：一次性操作。新建领域文件 → 从 `api.ts` 搬出对应类型 → 全局替换所有 `from '@/types/api'` 为具体模块路径 → 类型检查通过即完成。

**影响文件**：100 个 import 方 + 新建 ~10 个类型文件。

**风险**：低。纯机械搬移，`pnpm typecheck` 可验证完整性。

---

### P2：重构 `api/client.ts` 为 `api/client/` 目录

**现状**：`backend` 对象在一个文件里同时管理 IPC 调用、事件、配置、文件系统、图片加载、模式切换。

**方案**：

```
api/client/
├── index.ts              ← 组合导出 backend 对象（对外接口完全不变）
├── transport.ts          ← invoke / listen 底层
├── config.ts             ← backend.config.*
├── commands.ts           ← backend.command() + withTimeout
├── events.ts             ← backend.on/off + 订阅管理
├── fs.ts                 ← backend.fs.* + backend.file.*
└── runtime.ts            ← backend.runtime.* + swapToShowcase
```

**关键约束**：`backend` 的导出接口必须完全不变，所有现有调用方零改动。

**影响文件**：仅 `api/client.ts` 拆分为 6 个文件，调用方无感知。

**风险**：中低。接口不变，但需处理模块间内部状态共享（如 `transport`、`_eventCleanups`）。

### P3：引入 `@tanstack/vue-query` 统一数据请求

**现状**：当前模式是每个 API 函数直接调用 `backend.command()`，无缓存、无去重。store 手动管理请求状态（如 `instanceStore` 的 `scanRequests` Map）。

**本阶段决策与结果**：

1. 使用应用级 `QueryClient`，默认关闭窗口焦点、重连自动刷新与 IPC 自动重试；读取数据通过显式 `staleTime` 缓存。
2. 首批在 Pinia store 内调用 `queryClient.fetchQuery`，保留现有页面状态接口与请求竞态保护，降低迁移范围。
3. 查询键集中定义在 `src/app/queryKeys.ts`，避免各 feature 手写缓存键造成失效范围不一致。
4. 已迁移：游戏主页信息卡、Loader 版本和 Fabric API 版本；后续再将组件层逐步切换到 `useQuery` / `useMutation`。

**方案**：

1. 安装 `@tanstack/vue-query`
2. 在 `api/client/commands.ts` 或独立文件封装 `useQuery` / `useMutation` 包装器
3. 将高频读取类 API 迁移为 `useQuery`（版本列表、配置、账户列表等）
4. 将写入类 API 迁移为 `useMutation`，配合 `onSuccess` 做缓存失效

**示例效果**：

```typescript
// 改造前
const versions = ref([])
async function load() { versions.value = await api.list() }

// 改造后
const { data: versions, isLoading } = useQuery({
  queryKey: ['instances'],
  queryFn: () => api.list(),
})
```

**影响文件**：逐步替换 `features/*/stores/` 和 `features/*/api/` 中的调用模式。

**风险**：中。需要逐步迁移，不能一次性全改。建议从读取密集但变更低频的场景开始（配置、版本列表）。

### P4：提取 `createAsyncState` 为共享 composable

**现状**：`accountStore.ts` 内定义了一个 `createAsyncState()` 辅助函数，但其他 store 各自用不同的方式管理 loading 状态。

**方案**：

1. 将 `createAsyncState` 提取到 `composables/useAsyncState.ts`
2. 一次性替换所有 store 中手写的 `status`/`isLoading` 对

```typescript
// composables/useAsyncState.ts
export function useAsyncState(initial: AsyncStatus = 'idle') {
  const status = ref<AsyncStatus>(initial)
  const isLoading = computed(() => status.value === 'loading')
  return { status, isLoading }
}
```

**影响文件**：`accountStore.ts`（移除内部定义）、`instanceStore.ts`、`settingsStore.ts` 等所有使用异步状态的 store。

**风险**：低。纯提取 + 替换，无行为变更。

---

### P5：在 API 层引入 valibot 输入校验

**现状**：`valibot` 已安装但未用于 API 输入校验。参数错误直到后端返回错误才被发现。

**本阶段实施结果**：

1. 新建 `src/app/validation.ts`，提供 `assertParams` 辅助函数，统一封装 valibot `safeParse` 错误格式化，避免各 API 文件重复写错误处理逻辑。
2. 在 `instanceInstallApi` 的 `getLoaderVersions`、`getFabricApiVersions`、`install`、`uninstall` 中增加参数校验，校验失败时抛出明确错误消息，不发起 IPC 请求。
3. 在 `accountsApi` 的 `addOffline`、`addAuthlib`、`resolveAuthlibServer` 中增加参数校验。
4. 使用 valibot 原生 `object`、`pipe`、`string`、`nonEmpty`、`minLength`、`picklist`、`optional` 等 API，不扩展现有自定义 validate 封装。
5. 新增 3 个测试文件验证校验分支。

**方案**：在 `features/*/api/*.ts` 中，对接收用户输入或复杂参数的函数，增加 valibot schema 校验：

```typescript
import { object, string, number, safeParse } from 'valibot'

const LaunchSchema = object({
  instance_id: string(),
  memory_mb: number(),
})

export const instanceRuntimeApi = {
  async launch(params: unknown) {
    const result = safeParse(LaunchSchema, params)
    if (!result.success) throw new Error('参数校验失败')
    return backend.command('game_launch', result.output)
  },
}
```

**影响文件**：逐个 API 文件增量添加，无强制截止点。

**风险**：低。按需增量引入，不影响现有功能。

## 实施顺序

| 顺序 | 项 | 工作量 | 风险 | 独立收益 |
|------|-----|--------|------|----------|
| 1 | P4 提取 useAsyncState | 小（几个 store 替换） | 低 | 立即可做，快速见效 |
| 2 | P1 拆分 types | 中（100 个文件改 import） | 低 | 消除巨型单文件，模块化 |
| 3 | P2 重构 client | 中（拆 1 为 6） | 中低 | 提升可维护性/可测试性 |
| 4 | P3 引入 Vue Query | 大（逐步迁移） | 中 | 长期收益最高 |
| 5 | P5 valibot 校验 | 小（按需增量） | 低 | 日常开发中顺手做 |

P1/P2 建议在 P4 之后连续做，因为三个都是纯机械重构，不涉及逻辑变更，适合一口气完成。P3 独立，建议在重构之后做。P5 没有截止点，日常开发中遇到复杂参数时顺手加就好。
