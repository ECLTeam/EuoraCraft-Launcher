## 1. 目标与方案选择

本次一起完成三项功能：

1. 插件开发模式：启用后检测插件目录中相关文件的变化，对允许热重载的目录插件自动重建并重启 Worker；插件可以明确拒绝热重载。
2. 统一插件设置：独立入口打开全屏弹窗，左侧插件列表，右侧配置项；界面、Worker、声明式面板及独立前端共用配置管理。
3. 完整开发文档：提供从最小插件、配置声明、界面、权限和业务 API，到热重载、排障、依赖与打包的开发手册和可运行示例。

### 1.1 已比较的授权方案

| 方案                   | 保存代码后的行为                                                               | 取舍                                                         | 选择       |
| ---------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------ | ---------- |
| 开发会话内信任目录变更 | 同一安装与目录、未改变授权边界时自动重载；新权限或依赖等敏感变化暂停并重新审阅 | 能连续开发；需独立的会话准入，不能把临时信任写成普通永久授权 | 用户已选择 |
| 每次内容变化重新审阅   | 检测后提示，批准新摘要才能执行                                                 | 保持现行逐摘要审阅方式，但不能实现连续保存即生效             | 不采用     |

用户选择仅确定开发信任规则；下述界面、协议、状态和测试为本次提交审阅的具体实施方案。

### 1.2 推荐技术路线

- 采用应用所属的轮询与防抖服务，沿用现有版本目录监听的工程方式，首版不引入文件监听依赖。
- 每次开发运行使用宿主管理的独立代码副本，编辑源目录不会直接改变正在执行版本的内容快照。
- 复用当前 Worker 停止、授权、任务、注入及窗口清理边界，实际停止后才启动下一代。
- 将现有第三方设置持久化逻辑收敛到一个领域服务，保留现有用户配置文件及安装身份。

轮询相较操作系统原生通知有一个扫描周期的延迟，但不增加三平台监听库与打包依赖，适合当前目录大小上限。后续若有实际性能证据，再单独评估原生通知；本轮不同时维护两套后端。

## 3. 开发模式的产品行为

### 3.1 开启与关闭

- 插件管理页提供“开发模式”开关和当前状态；与主窗口 UI 注入总开关分开。
- 本次启动器进程内生效，启动器重启后默认关闭，重新开启即重新确认开发会话。不会持久化可自动恢复执行的开发信任。
- 进入模式时列明受管理的本地目录插件。已批准且原本启用的插件进入开发运行；未审阅、缺必要权限或用户禁用的插件不自动启动。
- 同一安装在会话中后续被用户正常启用时，若符合条件，也进入监听与开发运行。
- 模式关闭后停止监听，撤销开发临时准入并按既有边界实际停止开发 Worker；不把最后一次开发代码自动批准为正式版本。用户需要在普通模式重新审阅并启用当前目录内容。
- 显示关闭导致相关开发插件停止的实际状态；清理尚未完成时保持 pending，不将开关关闭视为资源全部释放。

### 3.2 监听对象

- 首版覆盖已安装的第三方目录插件，不监听不可变的归档版本目录或内置系统插件。
- 以实际安装目录为编辑目标。现有“从目录安装”会复制代码到安装目录，文档和界面必须展示这一点，提供可信的“打开插件目录”入口，避免误以为在监听原始导入目录。
- 本轮不增加任意外部源码目录挂载、双向同步或新的独立工作区系统。
- 目录新增插件只会成为候选；继续遵守首次审阅及启用流程。删除目录时撤销监听并清理对应运行，不删除配置和私有数据。

### 3.3 插件明确拒绝热重载

清单增加 `supports_hot_reload`：

```json
{
    "api_version": 2,
    "name": "example",
    "entry_point": "main:Plugin",
    "supports_hot_reload": false
}
```

- 省略或 `true`：允许开发模式自动重载，符合“默认检测，插件显式退出”。
- `false`：不因源码变化自动重载，显示“插件已禁用热重载”；可手动重载。
- 字符串、数字和 null 拒绝，不依靠真假值转换。
- 活动监听仍观察清单的策略变化，使 `true → false` 停止后续自动重载；已有运行副本不执行尚未加载的新源码。`false → true` 恢复资格，但不越过缺失授权或人工禁用状态。
- 不使用插件 Python 回调探测是否支持，避免执行后才发现其拒绝，也不新增第二套等价退出开关。

## 4. 文件检测、代码副本与重载状态

### 4.1 文件集与检测

- 文件集包含清单、Python、包内前端、资源、锁文件及其他实际分发普通文件；开发文件集由监听与副本生成共用同一规则。
- 排除 `.git`、`node_modules`、虚拟环境、`__pycache__`、测试/格式缓存，以及明确的编辑器临时文件；插件应将运行数据写入宿主私有空间。
- 排除规则只用于开发输入，不在正式归档验证中悄悄放宽文件边界；协议写明开发输入和最终归档的差别。
- 初始建议轮询 750 ms、稳定等待 750 ms。先比较文件集合、身份和元数据，变化后按字节摘要确认，防止只更新时间戳就反复重载。
- 处理新增、修改、删除、重命名、编辑器原子保存和连续保存。文件暂时缺失或 JSON 尚未写完时等待稳定，超过有界准备预算后显示失败；等待后续内容变化或人工重试，不形成无限错误重试。
- 沿用现有文件数量和总大小上限；拒绝链接、越界、大小写冲突和不合法目录绑定。

### 4.2 运行副本

- 先取得源文件清单，再复制到该安装的独占暂存目录；复制后再次核对源与副本清单，防止拼接出不同保存时刻的混合版本。
- 新副本只有在完整性、清单、依赖准入及 Python 语法预检查通过后才可用于启动；准备阶段不执行插件入口。
- 运行路径由宿主维护，源目录和安装身份独立保存，不让现有权限查询错误地把执行副本当成新的安装。
- 副本稳定意味着宿主不原地更新它，不宣传为同用户攻击下不可修改的 OS 沙箱。
- 配置、私有数据和任务存储继续位于原安装空间，不复制到代码副本，不因一次源码重载创建新安装身份。
- 清理仅作用于本服务创建且边界已验证的暂存/运行副本，实际资源释放后再清理，不扫描删除用户源码或未知残留。

### 4.3 串行切换

状态表达待监听、等待稳定、准备新版本、停止旧运行、启动新运行、需要审阅、失败及等待清理。可从界面查看最近一次结果及明确的失败原因。

每个安装最多一个运行和一个待执行的新版本。连续变化合并到最新一版；手动重载、自动重载、禁用和卸载共用生命周期锁，旧事件不得重新启用刚被用户禁用的插件。

切换顺序为：

1. 稳定文件并准备有效副本，判断是否需要重新审阅。
2. 记录当前用户启用意图和监听代次。
3. 撤销旧运行准入，清理旧命令、订阅、面板、插槽、认证注册、联机会话与独立窗口。
4. 确认实际 Worker 和所属资源已结束；清理 pending 时等待并保留责任，不并行启动新版。
5. 再次检查用户意图、开发会话和候选版本仍有效，启动新 Worker 并重新注册能力。
6. 发布新状态和设置 schema，前端丢弃旧响应，必要时使用新的窗口引用。

已创建的游戏进程继续遵循现有生命周期，不因热重载强杀。运行内任务和资源引用不迁移给新 Worker；长任务按原有取消、真实效果和清理状态结束。

新独立窗口在重载时关闭，不自动恢复旧引用；新插件可在生命周期中按自己的逻辑重新打开。主窗口插槽由新运行重新登记，不对旧脚本进行局部模块替换。

准备失败且旧副本仍有效时，可保持旧版本运行并显示“新版本准备失败”；旧运行停止后新版启动失败时，明确进入失败状态，不自动执行旧版掩盖错误。下一次有效保存可重新尝试，用户手动禁用后不自动恢复。

## 5. 开发授权规则

- 每个被信任目录绑定宿主安装身份、目录物理身份、当前开发会话、已批准能力、资源选择和依赖边界。
- 普通代码和资源变化可获得本开发会话的新运行准入；不向新摘要写入永久 allow，不修改普通生产授权的摘要匹配规则。
- 权限声明、网络站点、资源选择、Python 依赖/锁/ABI、插件依赖关系以及身份和入口等受保护清单字段变化时，暂停自动启动，显示差异并要求审阅；不能以“依赖已在缓存”代替批准。
- `supports_hot_reload` 的退出策略不自动扩大执行权限；展示字段和普通文件变化可按会话信任处理。
- 仅把原已批准决定及仍有效的资源范围用于新运行；新的账户、Java、根目录或网络站点不能自动加入。
- 撤权立即影响当前及排队的新版本。再次授权不复活旧 lease、旧任务、旧窗口凭据和旧注册。
- 开发模式关闭、启动器退出、安装卸载/替换或目录身份变化终结对应临时信任。
- 原有授权监测继续检查正在执行的副本，不能通过关闭内容校验来实现热重载。

## 6. 统一插件设置

### 6.1 全屏界面

复用现有 `FullscreenModal` 和焦点/层级机制，提供单一“插件设置”入口。插件行内设置按钮打开同一弹窗并选中对应插件，不保留两套编辑实现。

```text
┌ 插件设置                                      关闭 ┐
│ 插件搜索              │ 插件名称、版本、运行状态   │
│ 插件 A                │ 设置说明                   │
│ 插件 B                │ 配置项与类型对应控件       │
│ 插件 C                │                            │
│                       │ 保存状态 / 冲突 / 重试     │
└───────────────────────┴────────────────────────────┘
```

- 左侧列出已安装的第三方插件，使用稳定安装身份，支持搜索、选择、状态和无设置标记；首次优先定位入口指定的插件。
- 右侧使用声明 schema 生成布尔、文本、数字和选择项控件，统一显示说明、加载、空状态、错误、保存中与保存结果。
- 左列表与右配置分别滚动，弹窗主体占满可用空间，保持统一边距；960×600 下仍保留左右布局和可到达的主要操作。
- 切换插件或热重载时旧请求失效。保存期间同一插件提交串行，切换不取消已经发送的真实写入；状态由实际结果更新，不能把 A 的提示或值显示到 B。
- 沿用有效修改后保存：文本提交/失焦保存，开关与选择即时提交，禁止无有效值的数字输入写入。错误保留用户输入并允许明确重试。
- 并发冲突显示当前情况并重新读取，不自动覆盖新值；不添加“重置全部”等未提出的数据删除能力。
- 没有设置的插件仍可选中并显示说明。未取得当前有效 schema 时提供启用/审阅入口，不通过偷偷执行插件读取配置定义。
- 可信系统插件继续保持内部管理，不暴露为可禁用或可任意写配置的第三方条目。

### 6.2 唯一配置维护者

新增 `ECL/plugins/settings.py` 中职责明确的 `PluginSettingsService`，实际调用方为 Broker、可信插件管理 API，以及经过它们访问设置的面板和独立窗口；不创建通用配置框架。

- 以安装身份区分设置，继续读取和原子写入既有 `plugin_settings_v2/<installation_id>.json`。不重置、不自动迁移、不复制出多份可独立写的值。
- 将当前 schema 校验、默认值投影、revision 冲突与文件锁归入该服务。Broker 保留自身权限、运行准入及事件交付；管理 API 保留可信主窗口身份检查。
- 持久保存经过实际注册验证的 schema 元数据及其内容/结构版本，和用户 values 分开，供统一管理读取。当前内容不匹配或从未登记时明确不可编辑。
- 同一已验证 schema 可在插件禁用后由可信设置界面使用；禁用不意味着删除配置。代码更新导致 schema 身份失配时先重新加载并验证，不能拿未知新代码猜配置结构。
- 开发会话中的新 schema 在新版成功加载后才成为当前定义；旧请求附带 schema 版本，定义切换后拒绝迟到写入。
- 新增项使用显式默认值；移除项的已有用户值保留但不显示，不后台删除；类型不兼容保留原文件并明确报告，不能悄悄用默认值覆盖。
- Worker、面板、独立窗口和设置界面的写入都检查同一 revision。成功写入后统一广播变化，各消费方只刷新自身有资格读取的值。
- 统一范围是第三方插件配置管理，不借本次功能迁移可信系统插件内部存储或开放宿主任意配置。

### 6.3 协议与前端接线

- 增加可信主窗口专用开发状态查询、开启和关闭命令，命令名称与模型在实现首步固定，并登记 `IpcLogPolicy`。
- 插件列表返回来源、是否支持热重载、当前开发/重载状态及最新结果；管理 UI 不从客户端字段决定身份。
- 设置读取/写入统一返回严格类型视图，包含安装身份、schema 版本、值 revision 和可编辑原因；所有生产方、消费者、前端 SDK 及测试同步更新，不保留无需求旧入口。
- Worker `settings.*` 仍只操作自身，独立窗口白名单不增加跨插件配置读写；统一界面属于可信管理页。
- 六语言同步新增所有状态、动作、错误、帮助与可访问名称。
