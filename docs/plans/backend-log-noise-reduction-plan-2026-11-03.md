# 后端日志按业务价值精简方案

日期：2026-11-03。状态：用户已审阅并批准实施，日志精简与本地验收已完成，未推送。

关联问题：[#106 精简普通操作和查询的成对调用日志](https://github.com/ECLTeam/EuoraCraft-Launcher/issues/106)。

## 1. 选定方案与验收目标

用户选择“普通操作只记录结果、普通查询成功保持安静、长任务保留必要阶段”的分级方案。

验收目标：

1. 保存设置、启用插件等普通操作不再机械输出“开始 / 完成”两行，只保留一处有意义的成功结果。
2. 本地读取、列表查询、缓存命中、界面状态同步和轮询成功默认不记录调用日志，包含 DEBUG 文件日志。
3. 未变化配置与重复操作跳过不输出成功结果；失败不因成功路径静默而被隐藏。
4. 下载、安装、游戏启动等长任务保留实际执行开始、重要阶段和最终结果，能够判断卡住的位置。
5. 同一失败只记录一次原因和稳定错误码；非预期异常只记录一次脱敏堆栈。
6. 不改变操作是否执行、配置持久化、请求次数、IPC 响应、错误呈现、事件和取消语义。

## 2. 当前证据与问题位置

调查基线为主仓库 `4f1f0db954e88b68fdf7c242806f45a7f565cd16`。原工作区另有前端 `MAPPING_TABLE.yaml` 删除及本地验收产物，实施前重新核查，不覆盖或纳入本轮提交。

- `ECL/api/bridge.py` 的 `guard_ipc_handler` 对非轮询操作和查询统一记录开始、成功；查询只是降为 DEBUG。
- 同文件的 `_guarded_call`、超时和异常响应方法会先记录失败，外层再根据失败响应记录一次，存在重复输出路径。
- `ECL/api/operation_logging.py` 部分操作标题接近完整接口说明，机械加上前后缀后过长。
- `ECL/utils/logging.py` 的文件日志保留 DEBUG，因此降低控制台级别不能消除文件里的成对调用记录。
- `OperationManager` 已记录任务提交、执行和终态；插件生命周期、更新、账户、联机和进程服务也有自身结果，可能与 IPC 外层重复。
- 2026-11-03 调查时，当前日志的 117 条记录中有 45 条以“开始”或“完成 / 结束”开头。该统计包含必要阶段，只说明现有阅读负担，不把全部前缀日志一律判为无价值。

## 3. 统一输出规则

| 情况                           | 成功或正常行为                                                                             | 失败或异常                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 轻量业务操作                   | INFO，一条具体结果；没有变化或未执行则不记录成功。                                         | 已知业务失败记录一次原因和稳定错误码。                           |
| 本地读取、列表、缓存、界面同步 | 不输出进入、退出或成功调用记录，包括 DEBUG。                                               | 失败可见；周期性读取的相同失败按既有机制限频。                   |
| 网络查询、扫描等诊断信息       | 不自动为每次调用打印摘要。已有排障价值的安全摘要可用 DEBUG，明确操作、结果或有意义的耗时。 | 保留请求失败、实际回退与恢复信息，避免重复记录同一异常。         |
| 轮询、心跳、进度查询           | 成功静默。                                                                                 | 同命令同错误沿用现有 30 秒间隔限频；错误变化立即记录，恢复一次。 |
| 下载、安装、游戏启动等长任务   | 实际执行方记录一次执行开始、重要阶段和终态；相同阶段的高频进度采样。                       | 执行方记录实际失败或停止；IPC 不把提交成功说成执行成功。         |
| 用户主动取消、未确认的取消请求 | INFO，区分请求取消、实际停止和排队任务取消。                                               | 超时、停止失败或资源未释放按实际影响记录，不能伪报停止成功。     |
| 重试、降级、部分清理失败       | WARNING，说明原因、影响和下一步；同一情况不逐次刷屏。                                      | 最终失败记录稳定错误码；意外异常保留一次堆栈。                   |
| 非预期异常                     | 不输出成功结果。                                                                           | ERROR，在实际捕获边界记录一次脱敏堆栈。                          |

取消或清理状态变化是不同业务事实，不能为凑“一行”合并成错误结论。业务失败的严重级别遵循已有错误语义；本次不将所有可恢复失败统一升级为 ERROR。

### 3.1 一件结果由一处负责

- 没有服务结果日志的普通同步操作，由 IPC 边界记录结果。
- 服务已有更具体的结果时，由服务负责，IPC 不重复追加通用成功行。配置以真正写盘成功为准，未写入的同值请求不输出“设置已保存”。
- 长任务由实际执行方负责阶段与终态。同步长操作只有在边界确实包围实际执行且没有内部重复阶段时，才由边界记录开始与结束。
- 已有任务提交事件继续保留。日志中取消重复的提交确认；确有排队诊断价值的提交信息只在一个位置保留，不要求每个任务打印提交、受理、开始三次。
- 错误转换与错误记录分开：异常转成响应、前端弹窗和错误确认流程继续执行，已经记录的失败不在外层再记一条。
- 日志通道不记录自身调用，避免日志读取和转发形成循环。外部程序原始输出不按中文前后缀批量过滤。

### 3.2 标题、内容与级别

- 标题使用“保存设置”“读取插件列表”“安装游戏”等短名称，不把 docstring 或接口职责作为日志标题。
- 结果表达实际行为，例如“设置已保存”“插件已启用”“当前已是最新版本”；省去无意义的“完成获取……”和“耗时：0 毫秒”。
- 耗时只用于网络、扫描、安装等有诊断价值的操作，复用现有计时上下文。
- 只使用已有安全白名单摘要，不输出完整返回对象、请求体、配置值、凭据、房间码、个人目录、完整命令或标准输入。
- 不通过简单降低所有级别、文本过滤或关闭文件 DEBUG 达到精简效果；不新增日志详细程度开关。

| 更新、账户、联机、进程及插件生命周期服务 | 审阅 IPC 直接调用链中的开始和结果，保留一个明确的结果负责人；保留阶段、重试、降级与异常，删除重复或无排障价值的过程描述。                      |
| 日志测试、相关领域测试与现行日志说明     | 更新日志条数和级别断言，补充失败去重、同值静默及长任务语义回归；同步相关现行文档，不重写历史验收记录。                                         |

成功结果归属与必要开始阶段在现有 `IpcLogSpec` 中用明确字段或枚举表达，普通调用方为注册命令；不按日志文字猜测归属，不以历史日志行数维持已废弃的输出行为。失败是否已记录采用调用内状态，不向 IPC 响应加入私有标志，也不使用全局“最近错误”缓存影响并发操作。

本次只整理主仓库自有日志生产与策略。Core、Florolding 等子模块日志和外部程序输出保留各自契约；前端日志显示、过滤控件和配置保存去重不作功能更改。若调查发现必须改变这些边界，先补充本文并提交用户审阅。

## 6. 测试与验收

### 6.1 必须覆盖的回归

- 普通成功操作只记录一个结果，无自动开始行；服务已记录结果时，IPC 不再追加成功。
- 未变化配置、缓存命中、普通查询和界面同步成功为 0 条调用日志；同时验证 DEBUG 文件记录，而不只检查控制台。
- 已知异常、直接返回失败、非预期异常和超时均只记录一次相应失败，错误码与原有前端错误事件保留；非预期异常堆栈为一次。
- 两个并发失败各自可见，同一操作上下文退出后不影响下一次调用；线程、异步和退出回调的关联与脱敏保持有效。
- 轮询成功静默；重复失败限频、错误变化立即可见、恢复只记一次。
- 提交后台任务不能输出执行完成；实际执行、排队取消、请求取消、停止确认和失败清理保持原有真实语义。
- 服务既支持 IPC 又支持后台直接调用时，两种路径均有适当结果，不因去除 IPC 重复而使直接调用失去诊断信息。
- 凭据、请求体、配置值、隐私路径与外部网络原文不泄露；日志转发及历史查询不产生递归日志。

主要测试包括 `tests/test_operation_logging.py`、`test_logging_frontend.py`、`test_logging_paths.py`、`test_config_noop_writes.py`、`test_operations.py`、`test_process_service.py` 和实际改动领域的用例。断言围绕结果、级别、次数与安全边界，不仅检查字符串替换。

## 8. 实施与验收结果

### 8.1 最终行为

- `IpcLogSpec` 显式区分 IPC、服务、任务与静默同步的结果归属，缩短命令标题。普通操作不再自动打印开始；查询成功在 DEBUG 文件与前端转发中也保持安静。
- 全局设置、下载设置、目录配置与实例独立设置由实际写盘处记录一条结果，同值跳过不记成功。目录读取与未变化写入的原有 DEBUG 流水一并移除。
- 错误记录集中在捕获边界。`OperationTrace` 按当前调用保存线程安全的失败记录状态，嵌套转换和外层响应不再重复输出；并发请求仍各自可见，IPC 响应未加入内部标志。
- 对被领域异常包装的程序缺陷仍保留一次堆栈；超时和取消继续区分请求状态与实际执行状态。主动取消为 INFO，预期业务失败使用稳定错误码，意外异常保留脱敏堆栈。
- 插件、账户、联机、进程和更新已有结果由执行方负责。插件命令线程实际返回后仍能记录结果，即使等待方先前已经超时；IPC 不再追加同一成功或失败。
- 后台任务不再重复记录提交与受理，保留实际开始、采样进度及最终结果；开始行不附加 0 毫秒耗时。同步日志导出等确有必要的长操作保留开始与计时结果。
- 没有修改 IPC 字段、业务执行、持久化格式、前端显示或子模块代码。主仓库工作期间其他任务的提交与前端未提交修改均保留，本轮不更新前端指针。
