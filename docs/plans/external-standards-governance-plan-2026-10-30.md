## 1. 目标与实施边界

在现有工程规则上建立“要求来源、适用范围、验证证据、失败处理、维护责任”的对应关系，使新增要求可以执行和审查。

本轮包括主仓库和前端子仓库的治理文档、编辑器配置、依赖审计、浏览器可访问性检查及 CI 接入。Core、Florolding 使用既有测试作为集成证据；涉及其内部修复时先遵循所属仓库规范，超出本方案的功能改动另行确认。

保留现有 Ruff、ESLint、Prettier、Conventional Commits、中文文档及提交约定。外部资料按明确选取的条目使用，不整体导入另一套编码风格；不改变配置格式、IPC、账户与实例数据策略，不做全仓格式化、依赖批量升级或用户数据迁移。

验收目标：

1. 每条采用的要求都能追溯到固定版本的来源或明确标记为本项目补充要求。
2. 每条要求都有适用模块、自动检查或人工验收方式、证据位置和维护职责。
3. 新增自动检查能区分通过、违规、扫描失败和覆盖不足，不用空报告或跳过冒充通过。
4. 新增违规受到阻止；存量确认、登记、有限期例外与复查有明确流程。
5. 浏览器自动扫描、人工键盘检查、真实启动器验收分别记录，不据局部通过宣称整项标准合规。

## 4. 要求映射与首批覆盖

长期资料放入 `docs/governance/`。以 Markdown 表维护适用性和证据，不开发通用合规框架、不复制整份外部标准。

每条记录包含：来源版本及条目、简要要求、适用对象、负责维护的领域、现有实现/测试入口、自动或人工验证、覆盖状态、例外及关联问题。状态统一使用“待调查、已覆盖、部分覆盖、不适用”；“不适用”必须说明业务原因，“已覆盖”必须有证据。

### 4.1 可访问性

首批映射 WCAG 2.2 的 1.1.1、1.4.3、1.4.11、2.1.1、2.1.2、2.4.3、2.4.7、2.4.11、2.5.3、2.5.8、3.3.1、3.3.2、4.1.2、4.1.3。保留各成功准则的适用条件和例外，不把项目紧凑布局直接等同于违规。

| 用户场景 | 验证内容 | 首批入口 |
| --- | --- | --- |
| 页面导航与设置 | 键盘可达、焦点顺序、可访问名称、标签与错误关联 | 主导航、设置页 |
| 模态交互 | 焦点进入、Tab 范围、Esc 约束、关闭后焦点恢复 | 账户登录、实例详情或设置弹窗、插件权限弹窗 |
| 后台任务与更新 | 状态反馈能被识别，播报不随每次高频进度刷屏 | 任务中心、更新内容弹窗 |
| 自定义主题 | 正文及必要控件边界的对比度，焦点可见且不被遮挡 | Classic/Folia 亮暗及背景组合 |

采用 Python Playwright 加固定版本的 `axe-core` 浏览器脚本，复用前端现有测试语言；`axe-core` 从本地开发依赖读取，不在浏览器中加载远端脚本。工具版本和浏览器版本在实施时验证后写入对应依赖与安装说明。

对实际运行的 Vue 页面扫描，保留明确的页面、状态、语言、窗口及主题信息。使用 axe 的 WCAG 2.0/2.1/2.2 A/AA 标签作为自动检查范围；各条目的工具覆盖能力在映射中单独记录。`incomplete` 进入人工复核，不按无违规处理；已确认且未豁免的 `violations` 阻止通过，不仅依据工具的 impact 字段决定是否忽略。

首批覆盖四种基础主题下的上述入口；布局使用 960×600、默认窗口实际尺寸和放大窗口。对主题、背景、透明度与模糊采用可说明覆盖关系的代表组合，并在高对比背景和透明状态下人工检查合成效果。六语言检查名称、标签及错误提示，长译文重点检查德语、俄语；不机械执行所有维度的笛卡尔积。

自动化之外，实际启动器执行键盘流程和 Windows 屏幕阅读器抽查；浏览器通过不能替代 WebView2、原生焦点及辅助技术验收。其他操作系统缺少真实验收时如实记为未验证，不外推通过。

实施阶段先从 ASVS 5.0.0 原文选择适用条目并核对编号。以下仅确定调查领域，不预先认定现有实现安全或有缺陷：

| 领域 | 重点边界 | 可复用证据入口 |
| --- | --- | --- |
| 外部内容 | Markdown/HTML 净化、危险链接、WebView 导航和远端内容的 IPC 权限 | 更新内容弹窗及其测试、WebView 创建与协议文档 |
| 账户认证 | OAuth 凭据刷新、失败后的数据保护、日志脱敏 | `tests/test_microsoft_auth.py`、`tests/test_accounts.py`、日志测试 |
| 插件调用 | 声明权限、逐次授权校验、资源范围、生命周期和回收 | `tests/test_plugin_permissions.py`、网络及实例写入相关测试 |
| IPC 和网络输入 | 运行时校验、拒绝越界、大小及超时限制、明确错误 | API 模型、Transport 校验和插件网络测试 |
| 文件及安装 | 归档路径穿越、符号链接与 Windows 重解析点、原子替换及失败回滚 | 整合包、实例事务、更新及 Core 集成测试 |
| 子进程 | 参数与 shell 边界、超时和取消、进程实际退出及凭据脱敏 | 启动参数、无头进程和插件进程测试 |

桌面文件系统、原生进程、插件直接执行能力属于本项目补充边界，单独标注，不伪造 ASVS 对应关系。先读取当前插件协议和实现，区分受控 API 权限与插件进程自身能力，不将权限声明描述为操作系统沙箱。

本轮交付领域映射与已有回归覆盖索引；发现测试不足则补充有实际行为价值的边界用例。确认缺陷先按现有贡献指南查重登记，独立功能修复另行提出方案；不借治理对账户、安装或插件架构作未经确认的修改。涉及敏感漏洞时不公开细节或凭据，报告渠道只使用已经核实的项目入口。

### 4.3 编辑器与依赖审计

主仓库增加 `.editorconfig`：UTF-8、空格缩进、文件末尾换行；Python 4 空格，YAML/JSON 等按现有约定，Markdown 保留有语义的行末空格。换行约定先与 Git 属性和既有文件核对，不批量规范化历史文件；前端 `root = true` 继续独立生效。

前端使用当前项目 pnpm 10 支持的 `pnpm audit --json`，分别保存生产依赖与完整依赖的结果；Python 使用独立工具环境运行 `pip-audit`，审计干净项目环境实际解析的依赖，不扫描开发者日常环境，不运行自动修复参数。

Python 在 Windows 与 Linux 分别盘点运行依赖和开发/构建依赖，记录环境标记、解释器和解析版本；不能用 Linux 环境结果代表 Windows 原生包。保留锁文件或实际解析清单作为证据，本轮不顺带改造项目依赖锁定策略。原生轮子内嵌库、运行时下载的 Java/游戏资源和未覆盖平台均注明扫描局限。

`pip-audit` 不具备与 pnpm 完全相同的严重程度筛选接口，因此门禁不以两个工具的原始退出码直接比较等级。统一规则是：新增且未获有限期例外的有效漏洞报告阻止通过；工具失败、报告损坏和未解释的跳过阻止本次审计通过。无修复版本不自动豁免，漏洞库暂时不可用也不显示“安全”。

## 5. 门禁、存量与例外

分阶段启用，不重置已有质量要求：

1. **盘点阶段**：新增检查先报告，输出完整结果和扫描范围；本阶段不得声明治理已经落地。现有门禁仍必须通过。
2. **启用阶段**：逐条复核结果并登记确认的问题，建立有限期例外后启用阻断；禁止用无限期 `continue-on-error` 作为最终交付。
3. **持续运行**：新增违规、过期例外、无效报告及覆盖意外下降均失败；依赖和工具升级时重查对应覆盖。

例外使用一个主仓库维护的 `docs/governance/exceptions.json`，由简单校验函数读取，不新增注册表或通用策略引擎。记录精确的规则/漏洞标识、包和版本或页面/状态、适用仓库、原因、关联问题、批准依据、负责角色及 ISO 日期到期日；不允许整页忽略、包名通配或全局禁用规则。

依赖使用生态、包、实际版本和公告标识匹配；可访问性使用规则、页面、状态和稳定业务定位匹配，定位改变需要复核。过期、缺字段、重复及无匹配的失效例外都必须处理，禁止静默扩大匹配范围。

现存问题默认复查期限：严重/高危或可能影响凭据、越权、用户文件安全的问题最长 7 天；其余依赖问题最长 30 天；可访问性问题最长 30 天。缺少可靠严重程度或可达性证据时按 7 天复核。期限从确认或批准日计算，延长须有新的审查依据；关键风险不能只凭“存量问题”自动进入例外，须向用户报告并取得明确处置决定。

CI 比较 PR 基线时使用目标分支对应提交，主分支运行使用已批准例外；不将扫描输出重新生成的快照当作自动批准。例外变更必须在 PR 或提交中解释，AI 不自行认定风险可接受。对普通、不涉及风险接受的“确认为误报/不适用”，保存证据后按规则排除。

CI 失败结果保留结构化摘要和必要报告，默认产物保存 14 天。证据包含主仓库 SHA、全部 gitlink、工具及浏览器版本、扫描日期和覆盖范围；测试只使用合成数据，截图与日志脱敏，不上传账户、真实目录或完整配置。

`ECL/tooling/governance.py` 采用普通函数及明确的边界模型，由 CI 和本地命令共同调用；它解决审计工具退出码语义不同、例外到期和报告范围检查的问题，不抽象通用扫描插件。报告校验仅依赖 Python 标准库，可直接作为脚本运行，不导入应用启动依赖，前端独立检查无需安装整个后端。按实际实现将新增生产 Python 文件的文件头、中文多行文档及 Ruff 要求一并落实。

实施顺序：

1. 核对工作区和子模块；补齐适用性表、工具版本及责任范围。角色按前端、账户、插件、安装、发布领域填写，不虚构具体人员或强制 CODEOWNERS。
2. 完成编辑器配置和长期文档，将正式要求写回原有规范章节。
3. 先验证报告校验与例外失败路径，再接入两个生态的依赖扫描；网络/API 失败使用离线夹具覆盖，避免测试依赖在线漏洞库状态。
4. 补实际页面浏览器测试，验证至少一个有意制造的违规确实失败；确认测试运行真实 Vue 组件、可以到达目标弹窗和状态。
5. 运行首次报告并人工复核。确认的问题按用户影响归并登记，列明待修复事项；独立产品修复未获批准时不直接实施。
6. 处理批准的有限期例外，启用新增门禁。先验证并提交主仓库治理工具及规范作为基础提交，再让前端独立检查固定引用该提交，最后更新主仓库前端指针，避免循环引用。前端独立运行仅检出该固定提交的治理规范和工具，不使用浮动 main 或重复维护第二份例外；主仓库集成运行直接使用当前提交，后续治理更新同步前端固定引用。
7. 完成全量工程检查、受影响真实启动器验收，分别提交前端和主仓库，并完成安全的本地 main 集成。

CI 以只读权限运行，不使用 `pull_request_target` 执行不可信 PR 代码、不使用发布凭据；明确超时并保留失败证据。PR 与 main 运行治理检查，定期审计每周一次（UTC 周四 19:00，即上海周五 03:00），支持手动复查；定期任务只产出检查状态，不自动发消息或批量建单。新增治理检查不触发完整打包，也不改变标签发布语义。

代码层面让治理工作流以失败状态结束；远端分支保护是否将它设为 required check 属于仓库设置，先读取实际权限和配置，再单独报告，不把工作流存在等同于已禁止合并。

## 7. 测试与验收计划

### 7.1 当前方案文档

按 `AGENTS.md` 第 6.1 节“文档、注释及纯格式整理”，检查内容、Markdown 结构、相对链接、现行章节引用及 `git diff --check`。本次不运行功能测试、类型检查、构建或启动器验收。

### 7.2 批准后的实施

治理工具、依赖及 CI 变更属于高风险或公共变更，执行受影响仓库全量检查，不按局部文案/测试调整处理。具体命令以实施时更新后的 `AGENTS.md` 第 6 节为唯一入口，保留现有要求：

- 主仓库 Ruff 检查与格式检查、适用的根目录 Ruff 检查、全量 pytest。
- Core 既有 Ruff 和测试以及主仓库集成测试；不为样式规则改写 Core。
- 前端 `pnpm check`、新增浏览器治理检查；依赖/运行入口变化后执行 `pnpm build` 并实际启动启动器。
- 依赖审计分别覆盖 Windows/Linux，门禁校验覆盖 Windows/POSIX 路径与进程退出码。
- 实际启动器覆盖受影响公共界面及第 4.1 节矩阵，记录环境和未验证平台。

门禁回归至少覆盖：干净报告通过；新增违规失败；有效且范围精确的例外通过；过期/重复/无效例外失败；报告空缺、损坏或扫描进程失败不会误报成功；原生包扫描跳过必须明确；目标页面未打开、控件缺失或扫描范围为空不会通过；既有每日检查和版本构建触发规则保持成立。

人工验收至少覆盖：键盘进入及退出模态、执行中 Esc 关闭约束、关闭后焦点恢复、长译文名称、失败反馈、透明背景的可读性及窗口缩放后的操作可达性。自动扫描通过仅表示已检查的条目和状态通过。

## 8. 交付、回退与完成标准

按 `AGENTS.md` 第 7 节，在通过相应验证后提交，中文 Conventional Commits。按职责拆分文档、前端检查及主仓库治理提交；先集成前端本地 main，再更新主仓库指针并集成本地 main。保护其他工作树和无关改动。

远端推送、发布和仓库设置变更分别报告授权状态，本方案批准不授权推送或发布。发生问题时回退本轮工具、工作流、依赖及 gitlink，保留既有质量门禁；报告产物按保留期清理，不读写用户游戏数据。

系统化治理完成须同时满足：

- 来源版本、适用性、维护职责与证据入口已落入长期文档，规范章节没有重复维护命令。
- 首批实际页面与安全领域有明确覆盖结果；待调查项和局限未被标记为已覆盖。
- 新增门禁实际能失败，现存问题有登记和批准的有限期处置；不存在无限期仅报告模式。
- 全量检查和适用的真实验收通过，前端及主仓库本地集成完成。
- 本地验证、远端 CI、分支保护设置和发布状态分别说明。未获推送授权时不声称远端门禁已经生效。

若确认缺陷或关键风险导致无法达到上述条件，交付已完成部分和具体阻碍，保留治理未完成状态；不自动扩大本轮为全仓功能整改。
