# 有头与无头统一入口实施方案

日期：2026-10-13（Asia/Shanghai）。

状态：用户已确认实施 B「统一入口，按角色初始化」，功能代码与专项测试已完成。用户随后要求直接提交；全量与实际运行验收状态见第 11 节。

## 1. 目标与本期范围

同一套启动器发行物支持正常桌面启动和无 UI 任务执行。无头入口复用主程序所携带的 Python 环境、已打包依赖和资源，为未来插件子进程提供启动基础。

本期建议先实现运行基础，不迁移现有插件、不恢复已取消的 Worker 隔离方案，也不提供完整后端常驻服务。以下具体行为随本文一起提交用户确认，选择 B 本身不代表已经批准这些细节。

本期交付：

1. 默认桌面启动，新增互斥的 `--gui` / `--headless` 模式参数。
2. 参数校验完成后分流，无头路径不进入桌面启动器和完整应用组合根。
3. 单独的无头运行上下文、任务契约、退出和结果输出逻辑。
4. 一个实际可执行的内置任务 `runtime-check`，验证发行物中的运行环境和代表性依赖可用，执行后退出。
5. 源码子进程测试、实际打包产物测试和桌面启动回归验收。

未来插件 Worker 的通信协议、权限代理、依赖目录挂载、插件生命周期、宿主断开处理和进程监督另行制定方案。本期不对外开放尚未实现的 `--role plugin-worker` 参数。

## 2. 调研结论

| 位置 | 当前行为 | 对设计的影响 |
| --- | --- | --- |
| `main.py` | 导入 `ECL.cli.run_launcher` 并返回退出码 | 保持入口简洁，不在根脚本堆叠角色逻辑 |
| `ECL/cli.py` | 定义 `LaunchOptions`；解析成功后延迟导入桌面启动器 | 在这里增加模式解析与分流，保留帮助、版本和参数错误的提前退出 |
| `ECL/launcher.py` | 初始化时探测已有实例、初始化日志；随后维护数据、处理更新标记、创建应用并运行 Tauri | 无头任务必须绕开整个桌面入口，不能只跳过 `Adapter.run()` |
| `ECL/application.py` | 创建账户、游戏、联机、插件、进程、更新等服务；启动单实例监听、更新检查和可选开发者通道 | 保留完整桌面上下文；不把全部服务变成可选字段来服务无头模式 |
| `ECL/foundation/runtime.py` | 解析源码、PyInstaller、Nuitka 的程序、资源和数据路径；支持 CLI 与环境变量的数据路径覆盖 | 两种模式共用路径解析，解析数据路径本身不创建数据目录 |
| `ECL/host/single_instance.py` | 复用 CLI 解析转发请求，处理窗口置前和启动动作 | 桌面接收端也要拒绝无头请求，不能仅依赖发送端不移交 |
| `ECL/plugins/environment_pool.py` | 准备 wheel 安装目录，当前插件仍共享宿主解释器 | 本期不修改插件加载语义，运行基础也不自动把插件依赖加入导入路径 |
| `docs/plugin-worker-isolation-implementation-plan.md` | 明确标注历史草案已取消 | 不能把选择 B 理解为批准整套插件隔离迁移 |
| `.github/workflows/build.yml` | Windows / Linux 用 Nuitka，macOS 用 PyInstaller；另有 Arch 打包任务 | 需对实际平台产物增加无头检查，保留既有桌面与插件检查 |

`ECL/__init__.py` 和 `ECL/foundation/__init__.py` 当前会导入基础模块；`ECL/host/__init__.py`、`ECL/utils/__init__.py` 有较多聚合导入。新增无头模块放在独立包中，测试需覆盖传递导入，避免依赖“函数里才创建窗口”这种弱保证。

## 3. 命令行契约

### 3.1 正常启动

```powershell
python main.py
python main.py --gui
python main.py --gui --launch <现有实例>
```

未指定模式时等价于桌面模式。显式 `--gui` 与已有桌面参数兼容，单实例移交、快捷启动和原有退出码保持现有含义。

### 3.2 无头任务

```powershell
python main.py --headless --task runtime-check
python main.py --headless --task runtime-check --result-file .\runtime-result.json

# 最终发行物使用实际文件名；下面是 Windows 本地构建产物示例。
.\build-nuitka\main.exe --headless --task runtime-check --result-file .\runtime-result.json
```

- `--headless` 必须指定 `--task`，缺少任务以参数错误退出；不启动空闲守护进程，也不把空跑报告为任务成功。
- 本期仅接受内置的 `runtime-check`。未知任务在导入执行模块前报错。
- `--task`、`--result-file` 仅用于无头模式；与桌面模式组合时报错。
- 无头模式允许 `--data-dir`、`--debug`、`--log-level`；模式和任务选项不保存到设置。
- 无头模式拒绝 `--frontend-dist`、`--open-page`、`--dev-channel`、`--disable-plugins`、`--launch` 及全部游戏启动选项。不能静默忽略这些参数，也不因某个布尔选项显式为 false 而漏掉校验。
- `--gui` 与 `--headless` 互斥。既有 `--help` / `--version` 继续按 argparse 的提前退出规则处理。
- 帮助文本说明本期无头模式是任务入口，暂不支持无 UI 启动游戏或完整服务常驻。

### 3.3 参数模型

在现有 `LaunchOptions` 增加类型明确的运行模式、任务名和结果文件路径字段，默认模式为桌面。用枚举或受约束类型表达模式与任务，路径采用 `Path | None`。保留现有 `forwarded_argv` 和游戏覆盖语义，不在本期大规模重写现有配置模型。

任务标识是内置枚举值，不能用参数直接导入任意模块、执行任意脚本或表达式。未来支持插件入口时，应先增加对应领域的验证与启动契约。

## 4. 运行结构与服务边界

```text
main.py
  -> ECL.cli.run_launcher
      -> 解析与校验
      -> desktop：延迟导入 EuoraCraftLauncher -> ApplicationContext -> Tauri
      -> headless-task：延迟导入 run_headless -> HeadlessContext -> 指定内置任务 -> 退出
```

模式描述是否有 UI，执行角色描述进程职责。本期落地桌面角色与有限任务角色；未来插件 Worker 是新的无头角色，有自己的组合根，而不是给桌面上下文增加大量开关。

### 4.1 无头运行上下文

新增独立的 `ECL/runtime/` 包，包入口保持轻量：

- `contracts.py`：定义无头任务选项、任务结果、探测结果和 `HeadlessRuntimeError` 等类型契约；数据使用 dataclass 或明确类型，不以 `Any` 穿过内部边界。
- `context.py`：构造 `HeadlessContext`，持有解析后的运行路径、任务参数和自身拥有的日志资源。资源关闭幂等，初始化失败回收已创建资源。
- `headless.py`：执行一次无头任务，统一处理任务结果、异常、取消、输出和关闭。
- `tasks.py`：实现 `runtime-check` 和明确的任务分派。首期用显式分支，暂不引入动态插件注册器或任意模块入口。

共用现有运行路径解析、标准库 logging、可用的原子文件写入与日志脱敏工具。复用公共工具前确认其聚合导入不会进入 UI、业务服务或插件加载；确有导入耦合时只提取必要的基础工具，并保留原有调用入口。

### 4.2 无头入口不得产生的副作用

无头任务不导入 `ECL.launcher`、`ECL.application`、`ECL.host.tauri`、`ECL.api` 或 pytauri 相关模块，不创建窗口、托盘、WebView，不访问前端构建产物，也不等待 `frontend_ready`。

不初始化 `ConfigStore`、账户、游戏、联机、插件管理器、自动更新或开发者通道；不读取账户内容，不载入插件，不更改用户设置，不执行待处理维护或更新标记清理。

不探测、修改或清理桌面单实例发现文件，也不占用桌面日志轮转文件。除显式指定的结果文件及其父目录外，环境探测任务不创建持久化文件或目录。

同一数据目录可并行执行多个无头任务。结果文件应由调用者给每个并发任务指定不同目标；对同一文件不提供多进程结果合并语义。

## 5. 第一项任务与结果协议

`runtime-check` 用来验收运行基础，它应完成实际检查：

1. 解析运行环境，取得程序版本、Python 实现与版本、系统、架构和冻结运行标记。
2. 在任务执行阶段验证代表性宿主依赖 `httpx`、`pydantic`、`psutil` 可导入，记录明确类型的检查结果；不执行网络访问或业务服务初始化。
3. 检查本进程没有进入被禁止的 UI 与应用入口模块；发现越界加载视为失败。
4. 返回结构化结果后退出；不能仅打印一句“环境正常”作为验收依据。

结果包含协议版本、任务名称、成功标记、稳定错误码，以及成功时的白名单探测字段。结果不包含配置、账户、环境变量、完整路径、启动参数或构建秘密。使用明确模型序列化，不返回内部对象。

`--result-file` 是调用者明确指定的输出文件。校验空字符、目录目标、已存在目标及父目录类型；拒绝把既有文件作为结果覆盖，避免覆盖用户数据。正常写入使用同目录临时文件和原子替换，失败清理临时文件。调用者需为并发任务准备不同的未占用文件名；不宣称对恶意抢占目标提供安全沙箱。

- 指定结果文件时，以结果文件和退出码作为权威结果；成功结果写入失败必须返回非零退出码。
- 未指定结果文件且 stdout 可用时，输出一份 JSON，stdout 不混入人类日志。
- 没有结果文件且 stdout 不可用时，任务开始前返回明确失败。无控制台发行物应使用结果文件，不允许静默丢失结果后返回成功。
- 日志在 stderr 可用时输出，按已有中文字段、脱敏和级别规则处理；stderr 不可用时不创建共享日志文件、不主动弹出控制台。结构化错误保留可判断的错误码与安全说明。
- 任务失败在输出通道可用时产生失败结果。参数解析错误按现有 argparse 规则处理，不承诺额外生成任务结果文件。

这是一项有限任务的结果协议，不是未来插件 RPC。插件 Worker 应通过专用本地通信通道传递请求，不复用 stdout 承载 RPC，也不把探测结果文件当作通信会话。

## 6. 退出与异常

| 场景 | 无头退出码 |
| --- | ---: |
| 任务与要求的结果输出全部成功 | 0 |
| 无头初始化、任务或结果输出失败 | 1 |
| 参数错误、未知任务、参数组合不合法 | 2 |
| Ctrl+C / `KeyboardInterrupt` 后完成清理 | 130 |

桌面现有退出码保持不变。无头退出码定义在独立契约中，不导入桌面 `LauncherExitCode`；新增项目枚举成员与固定值按仓库命名规范使用小写语义名称。

`run_headless` 在真实执行边界处理预期领域异常和未预期异常；未预期异常只在捕获边界记录一次脱敏堆栈。所有路径通过 `finally` 清理任务持有的资源与日志处理器，不采用 `os._exit()` 结束正常任务。

本期任务不创建常驻事件循环、网络客户端或工作线程。不提前引入没有使用方的通用调度器、进程监督或通信框架。未来长驻角色必须另行明确 shutdown、超时、实际停止和宿主断开语义。

## 8. 测试与验收

### 8.1 参数与功能测试

- 无参数与 `--gui` 进入桌面入口；`--headless --task runtime-check` 只进入无头入口。
- 帮助、版本、模式冲突、缺少任务、未知任务和非法参数组合在两类运行入口导入前结束。
- `--data-dir` 保持高于 `ECL_DATA_PATH` 的优先级，无头探测解析路径但不创建数据目录。
- 正常探测确实导入代表性依赖；依赖导入失败能返回稳定错误，且不会误报成功。
- 成功、初始化失败、任务失败、输出失败和取消均关闭已拥有资源；重复 close 不重复释放。
- stdout 只有 JSON，日志进入 stderr；标准流为 None 或不可写时按契约处理。
- 结果文件原子写入、既有文件保留、目录目标拒绝、父目录失败及临时文件清理。
- 桌面单实例接收端拒绝无头参数，窗口置前事件和启动队列都没有变化。

### 8.2 独立进程验收

用新启动的 Python 进程运行真实 `main.py`，在进程中安装测试侧 import 拦截器，禁止 UI、桌面与完整应用入口导入；不能仅通过 monkeypatch 跳过 `Adapter.run()` 来证明无头成立。

在隔离数据目录预置设置、单实例发现文件、待处理维护与更新标记；运行任务后比较文件内容和目录清单，验证没有修改。测试夹具不使用真实账户或令牌。

在测试侧实际创建单实例监听，运行同数据目录的无头进程，验证未收到置前或启动请求，发现文件内容保持不变。并发运行多个无头进程，各自结果和退出码正确；测试启动的进程必须设置有界超时并明确清理。

### 8.3 最低质量门禁

按主仓库与前端 CI 执行，不降低现有检查范围：

```powershell
.\.venv\Scripts\python.exe -m ruff check ECL tests
.\.venv\Scripts\python.exe -m ruff format --check ECL tests
.\.venv\Scripts\python.exe -m ruff check . --output-format github
.\.venv\Scripts\python.exe -m pytest --tb=short -q

# 对应后端 CI 的子模块门禁，在所示目录执行。
# ECL/game：ruff check .
# 主仓库：python -m pytest ECL/game/tests --tb=short -q

# frontend 目录：先 check 通过，再 build。
pnpm check
pnpm build
```

优先运行新增及入口、运行路径、单实例、应用上下文、架构等相关用例定位问题，完成后执行上面的完整门禁。涉及启动流程，即使不修改前端，也执行 `pnpm check`、`pnpm build` 并实际启动启动器。

### 8.4 实际运行与打包

- 源码桌面启动：默认模式、显式 GUI、已有实例移交、窗口可用与正常关闭；使用隔离测试数据。
- Windows：本地 Nuitka 构建后执行无头任务；验证控制台开启和隐藏配置，隐藏配置通过结果文件取结果，并检查不会出现启动器窗口。
- Linux / Arch：构建工作流中的实际 Nuitka 产物执行无头任务；测试清除图形会话环境，不使用 Xvfb 或桌面会话包装作为无头成立的前提。
- macOS：直接执行 PyInstaller `.app` 内的主可执行文件运行任务；验证结果与退出，不走 Finder 桌面启动路径。
- 每个平台保留已有插件动态安装与原生扩展产物测试；无头检查新增步骤不能替代这些用例。
- 产物测试使用显式配置的当前构建可执行文件，不借用旧产物；构建工作流必须验证该路径存在。新测试使用独立的 `ECL_HEADLESS_SMOKE_EXECUTABLE` 测试环境变量，不更改现有插件测试变量的语义。

本机只具备 Windows 实测条件时，明确记录 Windows 结果，其他平台由相应 CI 验证。没有取得对应结果前，不宣称所有平台完成验收；若尚未获授权推送触发 CI，报告待验证项并由用户决定后续推送。

## 9. 影响与风险处理

- **导入边界**：新包只依赖基础契约，增加独立进程导入拦截和实际产物检查；不能以“没显示窗口”替代 UI 未初始化的证据。
- **启动行为兼容**：默认桌面、`main.run_launcher`、已有参数与单实例快捷动作均有回归用例。
- **控制台与 UI 是不同概念**：`--headless` 控制应用 UI，不改变构建时控制台策略。开发产物可以显示终端；正式无控制台产物用结果文件完成任务验收。
- **资源与构建**：无头运行不需要前端文件，但发行物仍包含正常启动所需 UI 资源；本期不新建发行渠道或裁剪 UI 依赖。
- **进程复用边界**：复用代码、库、资源和解释器版本；不共享 Python 对象、模块缓存或进程锁，也不承诺通用 Python 的 `-m` / `-c` 行为。
- **插件兼容**：现有插件保持主进程加载；未来执行外部插件、加载 wheel 和原生扩展仍需独立的真实产物验收，`runtime-check` 通过不代表全部插件可在子进程执行。
- **onefile 启动成本**：本期不承诺绕过打包引导或解压，也不修改打包器私有环境变量；未来高频子进程按实际耗时决定常驻或专用分发策略。
- **工作区交叉修改**：当前已有数据层、前端和相关测试的未提交改动。实施不覆盖、不恢复、不提交无关内容；完整检查失败时定位到具体改动并报告，不降低门禁。
