# 插件主进程运行与依赖安装目录隔离实施方案

状态：用户已确认，功能实施完成。验收范围与平台限制见第 13 节。

后续决策：插件机制尚未发布，旧命令 SDK 没有需要维持的已发布契约。本文原先保留 SDK 兼容的决定已被[插件 SDK 统一方案](plugin-sdk-unification-plan.md)取代；依赖安装及用户数据保留策略不变。

本方案依据 2026-09-30 的最新选择：所有插件在启动器主进程运行，仅隔离依赖的安装目录，不追求同名依赖不同版本同时运行。确认后，本文替代旧方案中插件专用运行时、venv、Worker 和跨进程 SDK 的设计；旧方案保留为历史记录。

## 1. 目标与边界

- 不再构建、发布、下载插件专用 CPython 运行时资产。
- 不创建插件 venv，不使用插件 Worker 进程，也不引入子解释器。
- 保留 `.eclplugin`、逐文件完整性检查、完整依赖锁、包内离线 wheels 和允许联网时自动补齐依赖。
- 依赖只安装到数据目录，不写入系统 Python、启动器安装目录或启动器自身的 site-packages。
- 相同完整依赖锁与宿主兼容目标共用一个只读使用的依赖目录；不同锁共享 wheel 下载缓存。
- 插件与启动器共享解释器、模块缓存和进程资源。不承诺依赖运行时隔离、强制停止线程、资源限制或安全沙箱。
- 不恢复 Ed25519 验签。继续提示来源未验证，并要求安装确认；哈希不作为作者身份认证。
- 不改插件权限政策，不取消插件主动调用既有 ProcessService 的能力。取消的是启动器为运行插件而创建的 Worker。

## 2. 当前实现与变更范围

目前 `packaging/build-plugin-runtime.py` 把 CPython、uv、Worker 和命令 SDK 打进一个 ZIP，整个 ZIP 的摘要作为运行时身份。`environment_pool.py` 创建 venv 并通过 uv 同步依赖；`package_preparation.py`、`package_activation.py` 和 `manager/packages.py` 负责准备运行时、创建 Worker、活动指针和生命周期。目录插件则通过 `manager/discovery.py` 在宿主直接加载。

前端安装弹窗及 IPC、Dev Channel 都包含离线运行时包参数。主构建工作流的常规矩阵和 Arch 路径分别生成、测试、上传插件运行时资产。因此本次不能只删构建步骤，必须同时迁移安装、加载、恢复、生命周期、SDK 兼容和前端协议。

## 3. 数据目录

```text
<数据目录>/
  plugin_packages/<插件名>/
    pkg-<归档摘要>/             已校验的代码版本
    active.json                已提交安装版本及启用状态
  plugin_deps/<依赖键>/
    site-packages/             仅在此处提供 Python 导入
    data/                      wheel 的其他数据
    headers/                   wheel 的头文件
    requirements.lock          完整锁副本
    installed.json             包版本、wheel 摘要和文件归属
    ready.json                 完整校验后原子写入的就绪标记
  plugin_cache/wheels/<sha256>/
    <文件名>.whl               按内容摘要复用的 wheel
```

依赖键由安装布局版本、宿主 Python 实现及 ABI、系统和架构、完整锁字节计算，不包含插件名、Worker/SDK 版本或整份启动器摘要。宿主 ABI 变化时重新安装，不尝试复用旧 ABI 的原生扩展。无依赖插件不创建空 venv 或专用依赖目录。

`active.json` 表示磁盘上已提交的安装版本；管理器另行记录本次进程实际加载的版本。安装新版可以成功并提示重启，但不能把磁盘版本误报为已经在内存运行。

## 4. 依赖安装方式

### 4.1 建议采用的工具

使用 PyPA `installer` 的公开接口安装 wheel，使用现有 `packaging` 解析包名、版本、需求、环境标记和兼容标签，沿用项目的 HTTP 客户端及后台任务边界。新增 `installer` 作为启动器生产依赖，但不嵌入 pip 或 uv 可执行程序，也不下载其他解释器。

这里实现的是固定锁下的文件选择、下载、校验和安装编排，不重写 pip 的依赖解析器。已确认使用 `installer==0.7.0`。

### 4.2 保留完整锁契约

- 沿用现有每个目标的精确版本与 SHA-256 锁文件；必须包含全部传递依赖。
- 启动器不在安装时重新选版本，不自动升级依赖，不接受源码构建、editable、任意 URL 或包内索引配置。
- 每个 wheel 校验文件名、内部元数据的名称和版本、宿主兼容标签、Requires-Python、归档结构、RECORD、文件路径和哈希。
- 根据 wheel 的 Requires-Dist 校验完整依赖闭包；按宿主环境求值标记，并处理由直接依赖及传递依赖激活的 extras。锁缺项或版本不满足时拒绝准备，不把缺项误当成无需安装。
- 不把依赖源码目录或压缩包直接加入导入路径来代替安装。

目标从实际宿主 Python 得出，不再无条件写死为 cp312。现有 cp312 插件包在 cp312 宿主上保持可用；其他宿主需要对应锁和 wheels，不能伪装兼容。

### 4.3 离线与联网

依次查找包内 wheel、共享 wheel 缓存；只有显式允许联网时才访问包索引。首版使用固定的 PyPI Simple JSON 接口查找锁定版本且摘要匹配的兼容 wheel，不开放私有索引、认证或多源配置。索引能力不足时返回明确错误，不临时扩展为自制通用解析器。

下载使用 HTTPS、有限重定向、超时、有限重试及响应/文件大小上限；下载 URL 和重定向目标均做来源检查。索引摘要不能替代插件锁内摘要。下载到临时文件，完整哈希校验通过后进入缓存。损坏缓存重新获取；禁止联网时明确报告缺失项，不偷偷联网。

### 4.4 原子准备与 wheel 特殊内容

在同一数据文件系统上的暂存目录安装，验证后原子提交到最终依赖键目录。已就绪目录禁止增量覆盖；单个 wheel 安装失败、文件冲突或校验失败时，整个新目录都不能取得 ready 标记。并发安装按依赖键加锁，磁盘和下载操作不占用 UI 事件循环。

purelib 和 platlib 都落在隔离的 site-packages 下；data、headers 等安装路径均约束在依赖目录内。使用成熟安装库处理布局和安装记录，不自行把 wheel 当作普通 ZIP 解压。

首版不提供依赖的命令行程序执行能力。不得生成指向冻结启动器并假装它是 Python 解释器的脚本包装器；未支持的 console_scripts、脚本或前缀布局需求必须在安装结果中明确说明。若包运行必须依赖这些能力，应拒绝并提示不支持，而不是报告完全兼容。

不执行依赖目录中 `.pth`、sitecustomize 或 usercustomize 的初始化代码；需要这些机制才能工作的依赖必须明确报告不支持。原生扩展只有宿主 ABI 和动态库实际兼容时才支持，不能仅凭 wheel 文件名保证可加载。

## 5. 主进程加载与冲突策略

依赖目录隔离不提供私有 import 语义：兼容的已启用插件依赖目录统一登记到宿主导入路径中，位于受保护的宿主包路径之后。禁用插件的目录不新增到导入路径；同一共享目录只登记一次。关闭前端等待不能被解释为强制停止正在执行的插件代码。

采用下列默认策略，不引入 import 重写、全局模块缓存切换或隐藏的自动版本覆盖：

1. 安装准备只写文件，不执行插件代码；允许保存与当前活动组合不兼容的插件，但必须显示冲突并保持禁用，不能误报启用成功。
2. 启动和启用前，比较完整锁、宿主依赖清单、本次进程已占用的模块及其他已启用插件的依赖需求。
3. 同一包必须有相同精确版本；不同包提供同名导入模块时也检查碰撞。无法确定兼容性时不静默放行。
4. 禁止插件依赖替换标准库、ECL、SDK、pytauri 及宿主依赖。相同宿主版本可复用宿主包，但不得通过优先级覆盖它。
5. 启动恢复先整体预检依赖组合；对互相冲突的社区插件保持禁用并显示原因，不以遍历顺序决定胜者。宿主优先。
6. 冲突诊断列出包名、版本及冲突插件，不覆盖、不清空 sys.modules、不偷偷升级其他插件的目录。

宿主依赖清单在构建时从实际生产依赖生成并随包携带，包含包版本与导入归属；不把整个开发环境当作生产基线。源码运行使用同等模型进行检测。对于无声明依赖的旧目录插件，只保留既有行为，不承诺能完整识别其动态导入冲突。

## 6. 生命周期、更新与旧数据迁移

- `.eclplugin` 安装或更新先完成归档检查和依赖准备，再原子提交活动指针，默认重启后加载新版本。这样无需为安装预检执行插件，也不会把主进程里的旧模块当作已经替换。
- 启动时复核活动指针、代码完整性、依赖就绪和兼容性，再接入现有宿主插件发现、插件间依赖排序、注册和生命周期；安全模式不执行任何社区插件。
- 启用可以调用现有生命周期，但新增或切换依赖版本必须先通过冲突检查；若本次进程仍占用旧模块，则提示重启。
- 禁用和卸载撤销注册项与未来加载资格，但不宣称能卸载进程内第三方模块。首版保留代码、依赖与历史记录，不自动删除目录；后续清理必须在进程结束后检查活动/历史/待生效引用。
- 重载仅保留现有代码级生命周期语义，不承诺重载第三方依赖或原生扩展；依赖变化走重启。
- 提交活动指针前失败保留旧版本和旧指针。提交后插件 on_load 失败可恢复文件指针并提示重启，但不能承诺回滚已经发生的主进程副作用。
- 为 active.json 增加安装模式和记录版本。迁移旧 Worker 指针时，复核原始代码与锁，在新目录中重新准备依赖，成功后才替换记录；不把旧 venv 直接加入 sys.path。
- 迁移缺少 wheel 且不允许联网时保留旧记录并显示待迁移，不执行旧 Worker，也不删除旧代码、venv 或运行时缓存。
- 首版不自动删除旧运行时与 venv；以后通过明确的清理操作或经过引用检查的启动清理回收，避免升级失败导致数据丢失。

## 7. SDK 与现有插件

目录插件继续使用 `ECL.plugins.plugin.Plugin` 和原有 framework、命令、事件、设置、前端资源等能力。归档中的宿主插件入口也接入同一路径，不再单独走 Worker 命令代理。

原先为旧命令 SDK 保留无参数构造与实例适配的决定已废弃：“已发布示例需要兼容”的前提不成立。目录插件与归档插件统一使用 `from ECL.plugins import Plugin`，删除旧转出口和适配器，保留宿主基类已有的构造参数与权限声明。不允许通过命令 API 任意调用未登记方法。

## 9. 实施顺序

1. 验证 installer 在现有依赖目录布局中的安装、宿主动态导入和打包收集能力，尤其是原生扩展及包资源。
2. 增加保留 wheel 哈希的锁模型、缓存和原子安装目录，先以离线测试证明无需额外解释器或安装子进程。
3. 接入固定锁的在线 wheel 获取，验证闭包、extras、平台、路径及安装记录。
4. 实现宿主依赖清单、活动组合冲突检查和主进程发现；后续 SDK 统一方案取消旧命令适配。
5. 迁移活动指针和生命周期，完善待重启、禁用、卸载、失败恢复与安全模式。
6. 同步前端、IPC、Dev Channel、作者文档和格式示例。
7. 清理构建与运行时/Worker 死路径，执行全套验证。阶段中不得把新依赖目录错误交给旧 Worker 路径。

## 10. 验证计划与验收

新增或更新 `tests/` 中归档、锁、依赖目录、准备、激活、管理器和 API 用例；替换旧 Worker/运行时的行为测试，不仅删除测试。重点覆盖：

- 包内 wheels 完全离线安装；缓存离线复用；联网补齐；禁止联网时零请求；超时、损坏和缺包失败。
- 两插件同锁复用、不同锁分开、并发同锁只提交一次、任何安装均不写宿主或系统目录。
- 错误哈希、错 ABI、错版本、伪造元数据、闭包缺项、extras、重复模块、wheel 路径穿越和解包预算。
- 宿主依赖冲突、插件间精确版本冲突、同名导入模块冲突、禁用后旧模块占用，及启动冲突不依赖扫描顺序。
- 安装后待重启、重启后主进程执行、统一宿主 SDK、插件依赖排序、注册清理和安全模式。
- 新安装失败不影响旧指针；旧记录迁移中断可重试；未知记录版本失败关闭；旧目录不被提前清理。
- Windows 与 POSIX 路径、锁、原子替换和清理分支。
- 在真正 Nuitka/PyInstaller 产物中安装并导入纯 Python wheel、包资源和至少一个原生 wheel；确认无插件运行时下载及 Worker 进程。原生库如无法通过真实产物验证，不声明通用兼容。

提交前执行主仓库 CI 最低标准，并完成项目额外规范：

```powershell
.venv\Scripts\python.exe -m ruff check ECL tests
.venv\Scripts\python.exe -m ruff format --check ECL tests
.venv\Scripts\python.exe -m pytest --tb=short -q
```

前端执行 `pnpm check`、`pnpm build`，随后实际启动启动器验证安装弹窗、主进程加载、冲突提示和重启生效；涉及子模块时补主仓库集成验证。真实打包测试不能仅以源码启动代替。

确认实施后直接在 main 按功能边界完成测试并使用中文 Conventional Commits 提交；不夹带无关文档或其他子模块指针，不自行推送或发布。未通过测试的阶段不作为完成功能提交。

## 11. 已确认项

用户已确认主进程运行及安装目录隔离，包含：

1. 使用轻量 `installer` 加固定锁下载编排，不嵌入 pip/uv，也不提供现场源码构建和通用版本解析。
2. 冲突插件可安装但不启用，禁止替换宿主依赖；不提供不同版本的并行导入。
3. 归档安装/更新默认重启后加载；禁用、卸载不保证移除已经导入的依赖。
4. 首版保留现有完整锁要求，联网自动安装不等于作者只写版本范围即可自动解算。
5. 脚本、`.pth` 初始化及特殊安装前缀需求不承诺通用兼容；真实打包验证结果决定原生扩展支持边界。

确认后在 main 实施，不自行推送或发布。

## 12. 参考依据

- [Python 导入缓存](https://docs.python.org/3/reference/import.html#the-module-cache)：同一解释器的普通 import 共享模块缓存，目录隔离不等于版本运行时隔离。
- [PyPA installer](https://installer.pypa.io/en/stable/)：提供 wheel 安装的公开接口，不负责通用依赖解析。
- [Wheel 格式规范](https://packaging.python.org/en/latest/specifications/binary-distribution-format/)：安装包含目录分配、脚本与安装记录等，不是单纯解压。
- [Simple Repository API](https://packaging.python.org/en/latest/specifications/simple-repository-api/)：包索引文件发现使用标准接口；精确版本与锁内哈希仍由安装层执行。
