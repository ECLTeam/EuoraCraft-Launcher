# 头像缓存完整修复实施方案

日期：2026-10-11。

状态：已完成实施、原生验收和原工作区本地 main 集成；没有远端推送。

## 目标与验收边界

解决头像反复请求的问题，复用现有图片磁盘缓存，区分账户列表变化与材质变化，并合并同一外置登录账户的材质查询。

- 同一账户在账户卡片、列表、详情中显示不同尺寸头像时，共用同一份皮肤图片。
- 切换账户、收藏、置顶、重复打开页面，不因这些操作再次下载已缓存的皮肤。
- 重启启动器或重载 WebView 后，缓存有效期内的图片从磁盘读取；IPC 读取缓存不计为网络下载。
- 外置登录的材质元数据在当前前端会话内共享；缓存有效期内，同一账户的不同尺寸、并发组件和衣柜查询合并。前端重载后允许重新查询一次元数据，图片仍复用磁盘缓存。
- 手动刷新账户、上传或重置皮肤、修改离线皮肤时，仅更新受影响账户；同 URL 内容改变也能够更新。
- 网络失败有默认头像或旧缓存回退，恢复后能够重试；失效前的迟到请求不能覆盖新结果。

## 已核实的现状与证据

当前主仓库为 `b0581e7`，记录的 frontend 指针为 `2d9de83dd56083f60ced346fb2db8b2e0f28edb1`。本工作树子模块尚未初始化，调研读取了原工作区中与该指针一致的前端源码；实施时在本工作树初始化子模块并隔离修改。

1. `frontend/src/composables/useAvatarRenderer.ts` 已有 `fetchTextureDataUrl`，包含按 URL 的内存缓存和在途合并，但 `renderAvatar` 直接调用 `renderSkinAvatar(resolved, size)`，远程 URL 随后直接赋给 `Image.src`。
2. 头像结果缓存键包含尺寸，皮肤下载没有独立接入缓存层，因此不同尺寸分别加载远程图片。相同尺寸且缓存未失效时，头像结果缓存本身能够命中。
3. `frontend/src/app/runtime/useAppRuntime.ts` 对每次 `accounts_changed` 调用 `clearAvatarCache()`；后端切换、收藏、置顶等也发送该事件，导致无关账户头像一并失效。
4. Authlib 皮肤地址在头像结果缓存未命中时通过 `accounts_texture_urls` 获取，未按账户共享在途请求；`ECL/services/account/authlib.py` 每次查询都会访问会话服务器。
5. 衣柜使用 `fetchTextureDataUrl`，但上传、重置后也清空所有头像和皮肤缓存；衣柜材质元数据查询尚未与头像统一。
6. `ECL/api/files.py` 的 `image_fetch_data_url` 已有按 URL 的持久化缓存：7 天有效期、128 个文件、96 MiB 总量，网络失败时可返回过期缓存。当前没有显式刷新参数。
7. 执行当前源码的模拟验证：同尺寸重复渲染、不同尺寸渲染和清缓存后渲染共触发 3 次远程 `Image.src` 赋值，图片缓存接口调用为 0；同一 Authlib 账户两种尺寸并发触发 2 次材质查询和 2 次远程图片加载。直接使用已有图片缓存方法时，并发加重复调用仅产生 1 次缓存接口调用。

模拟验证证明调用路径与去重缺口，不代表实际 HTTP 下载次数；实际浏览器可能命中自身 HTTP 缓存。原生验收必须分别统计 IPC、会话服务器请求、图片下载和磁盘命中。

## 选定方案

复用现有图片缓存接口与磁盘目录；前端统一皮肤图片获取和账户材质解析，后端事件明确携带材质失效的账户列表。保留现有头像裁剪方式与页面交互，不新增缓存设置页面。

### 1. 头像接入现有图片缓存

- `renderAvatar` 先解析皮肤来源，再通过 `fetchTextureDataUrl` 获取 Data URL，最后交给 `renderSkinAvatar` 裁剪。
- `data:` 与 `blob:` 图片保持本地处理，不调用远程图片接口；无后端的浏览器展示模式沿用已有行为。
- 图片缓存按规范化后的完整 URL 共享，与账户和显示尺寸分离；不随当前账户切换清空。
- 头像结果缓存仍按账户身份、皮肤来源、渲染版本和尺寸区分，并明确记录所属账户，避免用字符串前缀匹配来删除缓存。
- 维持内存缓存 30 分钟与 100 条的现有上限；替换同键结果不误删其他条目。在途请求完成或失败后释放引用。

### 2. 外置登录材质查询共享

- 在头像缓存模块内提供可供头像和衣柜共用的账户材质读取方法，返回明确的 `AccountTextures` 类型。
- 元数据缓存以账户 ID 与账户身份信息区分，至少覆盖账户类型、UUID 和认证服务器；尺寸不参与键。
- 成功结果在当前会话内缓存 30 分钟；同账户相同代次的并发读取共用一个 Promise。
- 没有材质或暂时失败时，采用短暂的 30 秒回退窗口，避免多个组件持续重复请求；默认头像不得作为完整 30 分钟成功结果缓存。后续读取到期重试，显式刷新立即重试。
- 不添加前端 localStorage 持久化层。重载后的 Authlib 元数据允许查询一次，远程图片继续由后端磁盘缓存负责。
- 衣柜预览读取共用元数据入口，保留同步皮肤到衣柜这一显式下载操作的既有职责。

### 3. 按账户通知材质失效

- 保留既有 `accounts_changed` 事件名及 `accounts`、`current` 字段；事件载荷新增必填的 `textureInvalidatedAccountIds: list[str]`，普通列表变化发送空列表。
- 前端使用独立的账户变更事件类型，账户列表查询响应仍使用原来的 `AccountListData`。事件标记不写入账户文件、全局配置或查询缓存。
- 后端 `_emit_changed` 接受明确的受影响账户列表：资料刷新、离线皮肤修改、皮肤上传或重置后的成功刷新标记对应账户。删除账户清理对应缓存；新增或身份变化由快照对比处理。
- 切换账户、收藏、置顶等发送空失效列表；相同快照重复通知不清空缓存。快照对比仅关注账户身份与皮肤来源，不把收藏、置顶、当前选择作为材质版本。
- 插件账户资料刷新成功也提供明确通知，避免现有提前返回漏掉刷新语义。
- 前端先协调快照变化与显式失效，再应用新快照，确保渲染使用新资料。账户删除和替换释放相关元数据及头像结果；共享图片缓存继续保留至 TTL 或容量淘汰。
- 移除运行时和衣柜的无条件全局清理，材质变更统一由后端成功事件触发，避免一次操作多次失效。全量清理函数仅保留给测试和确有全局重置需要的调用方。
- 活跃头像组件依据自己的账户代次更新，失效 A 不触发 B 的重新查询或渲染。没有账户 ID 的调用根据自身皮肤来源和属性变化处理。

### 4. 同 URL 刷新与失败回退

- 为既有 `image_fetch_data_url` 增加可选布尔参数 `refresh`，默认 `false`；增加请求校验模型并登记到现有请求模型表，前端命令类型同步更新。
- 普通查询保持现有 7 天磁盘缓存行为；明确的账户材质刷新在重新解析来源后，针对对应图片请求使用 `refresh: true`，即使 URL 相同也重新下载。
- 前端为受影响账户记录待刷新状态，在材质解析和图片刷新链完成后消费；多尺寸或多组件共用对应 URL 的在途刷新。
- 强制刷新先保留旧磁盘文件，新图片下载与校验成功后原子替换；刷新失败沿用已有旧缓存回退。失败不清空旧文件，不把回退结果当作成功刷新长期缓存。
- 不给所有 URL 附加随机参数，不删除整份缓存，不触碰其他账户图片。HTTP 请求仍受现有超时和大小限制约束。
- 按账户和 URL 维护失效代次，失效后的旧请求不能回填新内存结果、删除新在途请求或覆盖较新的磁盘图片。后端同 URL 并发读写也必须有明确的合并或串行保护，避免普通下载晚于强制刷新时覆盖新文件。

## 影响与交付

影响账户头像、衣柜材质读取及现有图片缓存接口；头像绘制外观与操作入口保持既有行为。前端重载后 Authlib 元数据仍可能有一次网络查询，这与重复下载图片分别统计。

已知风险是缓存失效与并发顺序：既要减少请求，也要保证显式刷新、同 URL 更新和失败恢复不显示长期旧图，以针对性回归和原生请求计数验收。

本次按用户选定方案并确认实施后完成前后端提交、验收与本地集成。远端推送与发布需另获明确指令。

## 实施结果

- 头像先通过现有图片缓存接口获取皮肤，再完成裁剪；不同尺寸共享纹理，图片与头像内存缓存保持容量限制。
- 新增共享的账户材质读取入口，账户头像、详情和衣柜共用元数据及在途请求。初始账户加载与事件快照都维护材质身份，认证服务器变化不会沿用旧身份缓存。
- `accounts_changed` 载荷明确携带 `textureInvalidatedAccountIds`；切换、收藏、置顶保留缓存，刷新、换肤、删除只失效受影响账户。插件账户刷新也发送通知。
- 活跃头像与衣柜预览订阅自己的账户代次；旧请求不能回填新缓存、清除新在途请求或恢复已删除账户。
- 图片读取支持校验过的布尔 `refresh`；同 URL 刷新保留旧文件，校验成功后原子替换。失败短暂回退 30 秒，再次显式刷新可以立即重试。
- 原生 IPC 与开发者通道存在不同事件循环，因此后端用受锁保护的共享 Future 合并同 URL 请求，保证旧普通下载结束后再执行显式刷新；关闭时取消全部在途下载。
- 原有图片校验夹具已改为有效 PNG，新增跨事件循环、取消等待、关闭、损坏图片拒绝与并发刷新测试。

集成前检查：前端 `pnpm check` 838 项通过、1 项既有 todo，`pnpm build` 通过；后端 `ruff check ECL tests`、`ruff format --check ECL tests` 通过，完整 pytest 1332 项通过、7 项跳过，后续图片校验及文档调整的相关 82 项回归通过。Core 子模块 Ruff 与 12 项测试通过。
