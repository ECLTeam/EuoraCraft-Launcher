# 任务中心游戏安装阶段与下载进度实施方案

日期：2026-10-25。

状态：用户已选择方案 B；本文供实施审阅，尚未获准修改生产代码。

关联问题：[安装游戏下载时任务中心仍停留准备阶段 #67](https://github.com/ECLTeam/EuoraCraft-Launcher/issues/67)。

## 1. 目标与调查基线

让用户在任务中心清楚看到安装正在执行什么、实际下载了多少、哪些步骤已经完成，以及失败或取消发生在哪一步。

调查基线：

- 主仓库：`d7f262bae97a32302ea2fcb097c75076440dfd27`。
- frontend：`3e23d11f43e6bceffec8899b98f4565832751a38`。
- Core：`2b5b961244fbdd33f62db958cf9f40f6791823f8`。

以上问题已通过代码调查定位；尚未执行用户所遇具体版本的真实游戏下载复现。实施开始前重新检查工作区、子模块规范及最新调用方，避免与同时进行的工作冲突。

### 1.1 已确认的原因

1. `ECL/services/game/install.py` 在 `build_*_download_list` 返回后才建立下载进度回调。Forge／NeoForge 的 Core 构建方法内部已经下载客户端、安装器、安装依赖并执行安装处理，前端在此期间只能保留早先的准备文案。
2. `ECL/game/Core/LoaderInstaller.py` 的内部下载只通过 `log_callback` 输出速度和进度。主仓库 `base.py` 将该回调接到日志，没有接入安装进度事件。
3. `NetLibs.py` 的客户端和安装器下载使用整份响应读取，未提供分块下载进度。
4. `TaskQueuePanel.vue` 的实时下载卡优先按文件数计算百分比，任务卡由 `useAppRuntime.ts` 按 `done/total` 计算，二者可能分别显示文件和字节百分比。
5. `Downloader.py` 任意文件大小预检失败后整体使用文件计数，大文件传输期间完成文件数不变；预检本身也没有明确的任务阶段反馈。
6. 前端用同一 `progress` 表示不同阶段的局部比例，存在强制至少显示 1% 的处理；新增子阶段不会自动完成之前的活动阶段。
7. 整合包 `_ensure_base_version` 的 `report` 丢弃下载明细，反复上报固定 26%，基础版本安装同样无法呈现真实下载过程。

## 2. 选定方案与范围

采用方案 B：打通 Core → 主仓库安装协调 → 事件／操作快照 → 前端队列 → 任务中心的完整安装进度链路。

包含：

- 原版、Fabric（含可选 Fabric API）、Quilt、Forge、NeoForge 的普通安装。
- 整合包导入及在线安装中复用 `install_blocking` 的基础版本安装；继续放在原整合包任务内展示，不另建重复任务。
- 下载预检、已有文件检查、内部下载、安装处理、补下载及备用源重试的阶段反馈。
- 共享队列模型的直接消费者和其他任务类型的回归，六语言及真实启动器验收。

范围边界：

- 沿用既有任务管理服务和任务中心结构，不另建通用任务平台；普通安装本轮仍使用安装事件，不整体迁入 `OperationManager`。
- Java 安装、自定义下载、插件任务和游戏启动保留既有业务流程，只验证共享队列变更不会破坏其显示。
- 不新增下载历史持久化、暂停续传、安装调度或整套安装事务；保留既有文件、实例及失败恢复语义。
- 新增状态字段同步更新生产方、消费方、类型、校验、测试和文档，不增加旧字段别名、双协议或历史数据迁移。
- 工作区已有的插件游戏安装／启动方案独立保留；未来接入者应消费同一安装进度接口，本次不提前实现插件能力。

## 3. 用户可见行为

### 3.1 收起的任务卡

任务标题下始终显示当前步骤，例如“下载游戏本体”“下载加载器依赖”“执行加载器安装”。显示“步骤 3 / 8”，表达执行位置，不将步骤数解释为耗时百分比。

进度条表示当前步骤的进度，并在附近明确标注步骤名称：

- 已知可信总字节数：显示当前步骤百分比、已下载／总量、完成文件数及速度。
- 仅已知文件总数：显示已完成／总文件数及速度；同时展示实际传输量，避免大文件传输时只有静止的文件计数。
- 当前总量未知：显示活动进度条、已传输量和速度，文案为“总大小未知”；没有依据时不显示百分比或剩余时间。
- 元数据请求、文件大小预检和无法量化的安装处理：显示活动进度条及具体动作，不强制填充 1%、3% 等数值。
- 下载步骤达到 100% 后，若仍有安装步骤则明确切换步骤；只有实际安装成功才显示任务“已完成”。

示例：

```text
安装 Minecraft 1.21.1 · NeoForge
进行中 · 步骤 4 / 8 · 下载加载器依赖
当前步骤 42%    84 MB / 200 MB    31 / 96 个文件    8.2 MB/s
```

阶段切换后局部比例允许从零开始，标签同步切换，不冒充整次安装的连续百分比。任务完成后保留可识别的最终结果。

### 3.2 展开的步骤列表

- 根据加载器的真实执行路径生成有序步骤，展示待执行、进行中、已完成、跳过、失败、已取消状态。
- 不强行让所有加载器共享同一顺序。原版在最终文件下载阶段获取客户端，Forge／NeoForge 则在加载器安装前下载客户端。
- Fabric API 未选择、已有文件无需重复下载等情况按实际步骤计划省略，或在已经展示的步骤中标记跳过；失败后的未执行步骤保持待执行，不能误标完成。
- 阶段转换由后台确认；前端不通过文案关键词、日志解析或计时器推测下一阶段。
- 普通安装失败时展示具体失败步骤和现有错误信息，允许用户从安装入口重试；不新增缺少后端支持的通用“重试”按钮。
- 取消请求显示“正在取消”，执行方实际退出后才显示“已取消”。后续步骤不启动，迟到事件不能恢复终态。

### 3.3 实时下载区域

- 与任务卡读取相同的当前步骤数据及计算规则，不再独立优先选用文件数。
- 只为当前实际处于下载阶段的任务显示下载曲线。进入安装处理时清零速度并移除过期下载指标。
- 多任务时保留既有单个实时详情区，按确定规则优先保持当前下载任务；该任务退出下载阶段后才切换到另一个活动下载任务。每张任务卡仍展示自己的指标。
- 当前步骤耗时从步骤开始计时；仅可靠总量和有效速度同时存在时估算当前下载步骤剩余时间，不估算整次安装剩余时间。
- 速度采样按任务及步骤身份维护，普通进度事件不能反复清空曲线；面板关闭时停止曲线采样，后台安装及应用级订阅继续工作。

## 4. 阶段计划与状态归属

### 4.1 阶段标识

使用稳定的业务标识和六语言名称，具体文案不从后台日志推导。以下是允许的阶段集合，步骤计划只包含当前安装路径实际需要的项目：

| 标识 | 用户名称 | 上报来源与说明 |
| --- | --- | --- |
| `resolve_metadata` | 获取安装信息 | 查询游戏、加载器版本和描述；必要时补充具体子动作 |
| `download_client` | 下载游戏本体 | Forge／NeoForge 安装前下载；原版由最终文件下载阶段覆盖 |
| `download_loader` | 下载加载器安装器 | Forge／NeoForge 的安装器文件传输 |
| `download_loader_libraries` | 下载加载器依赖 | LoaderInstaller 内部下载 |
| `install_loader` | 执行加载器安装 | 处理器逐项执行，只有已完成处理器才能计入完成数 |
| `check_resources` | 检查游戏资源 | 读取资源索引、检查本体／依赖／资源，分别报告当前动作 |
| `resolve_fabric_api` | 获取 Fabric API 信息 | 仅选择附带 API 的 Fabric 安装 |
| `download_game_files` | 下载游戏文件 | 清单中的游戏本体、运行依赖、资源和可选 API |
| `finalize_install` | 完成安装 | 现有收尾、结果检查和最终成功确认 |

阶段集合不是统一固定时间线。Core 根据实际执行顺序报告步骤，安装协调器在开始时构建对应加载器的步骤计划；新增步骤必须更新对应计划及测试。

下载预检、等待重试、备用源补下载是所属下载步骤的子状态，不重复创建同名步骤。获取元数据与资源索引期间的网络等待也必须有明确动作反馈。

### 4.2 唯一状态维护者

- 主仓库 `InstallCoordinator` 为每次安装创建独立的进度记录，维护步骤计划、当前步骤、修订号和最终状态。普通安装和整合包基础安装复用同一记录逻辑。
- Core 通过调用参数传入的结构化回调报告事实：阶段开始／结束、下载统计、处理器完成、失败及取消检查；不持有全局任务队列。
- `base.py` 的 Core 上下文按目录和来源缓存，同一上下文可能被并发复用。因此不得在共享 `games`、`api_client` 或 `loader_installer` 对象上临时替换回调。回调及取消信号必须沿本次调用显式传递。
- 回调跨下载器分发线程时，由所属安装记录加锁更新并生成一致快照；锁内不调用网络、文件操作或前端事件监听器。
- 前端只保存最新快照及面板展开等展示状态，百分比由数据派生，不保存另一套可独立变化的安装进度。

## 5. 结构化进度契约

保留现有任务标识和事件入口，为游戏安装增加明确的 `installation` 快照；整合包通过现有 operation 的 details 及查询快照传递相同结构。

| 字段 | 含义与约束 |
| --- | --- |
| `revision` | 每次安装内递增的修订号，用于拒绝迟到快照 |
| `status` | 安装 pending／running／completed／error／canceled，由执行方确认 |
| `cancellationRequested` | 已请求取消但尚未实际结束，与最终取消状态分开 |
| `currentStageId` | 当前步骤；终态可保留最后执行步骤供诊断 |
| `stages` | 有序步骤快照，每项含稳定 ID、状态、具体动作及进度 |
| `progress.unit` | bytes／files／items／unknown；items 用于可确定数量的安装处理器 |
| `progress.completed`、`progress.total` | 同一单位的当前完成量、可信总量；总量未知时为空，不以 1 代替 |
| `download.completedFiles`、`download.totalFiles` | 文件完成数与清单去重后的文件总数 |
| `download.transferredBytes` | 当前下载步骤实际网络传输量，可包含失败重试消耗，不等同成功完成量 |
| `download.speedBytesPerSecond` | 当前真实速度；离开下载步骤或任务终止时归零 |
| `startedAt`、`updatedAt` | 步骤开始及最后更新时刻，毫秒时间戳 |
| `errorCode` | 保留稳定业务错误码，失败消息沿用脱敏边界 |

落实时使用主仓库 dataclass／明确模型和 Core 自身规范允许的类型定义，前端同步定义 TypeScript 模型与边界运行时校验。上表字段名作为本次内部契约，不提供同义旧字段。

普通安装的展示以 `installation` 为权威，停止同时发送或维护重复的旧安装阶段／百分比数据。事件通道中其他下载生产方仍按各自现有契约发送，由前端明确区分事件类型，不能按字段缺失猜测旧安装格式。

整合包仍由外层 operation 确认最终安装成功。基础安装快照只代表内部步骤；基础版本 100% 不能使整合包任务完成。外层原有粗略百分比不再覆盖基础安装的局部进度。

只把本次安装快照投影到桌面任务模型，不改变插件权限、任务所有权和对插件暴露的快照白名单。

## 6. 下载、重试与执行语义

### 6.1 可观察下载

- `NetLibs.py` 的客户端及安装器文件下载改为有超时的流式写入，接入本次调用的进度与取消检查。使用目标旁临时文件及 replace；失败保留既有目标，清理本次临时文件。
- `PreferredApiClient` 显式转发本次下载回调和取消信号，保持既有来源选择及有上限的重试，不新增备用实现。
- `Downloader.py` 保留文件清单身份和速度统计，补充预检状态与实际传输字节统计；预检并发受已有下载并发设置约束，逐批反馈检查数量，不能一次启动全部 HEAD 请求。
- 有可信完整总字节数时使用字节比例；部分文件大小未知时使用文件完成数，并持续报告传输字节和速度。不靠额外无限预检获取百分比。
- 速度采用实际网络字节采样；字节比例不能直接用含重试的网络累计量计算。失败重试清除失败尝试的完成贡献，保留实际传输累计量，并明确显示“正在重试”。
- 下载量修正或总量变化按实际值呈现，不能用前端取历史最大值掩盖失败、重试或新增待下载文件。
- 首选源失败后在原下载步骤内标记备用源补下载，按唯一目标文件统计完成数，已经成功的文件不重复计入；等待退避也有明确状态且速度归零。

### 6.2 安装处理及取消

- LoaderInstaller 内部依赖下载与处理器执行分别报告；处理器总数已知时按处理器数量显示进度，单个处理器内部不可量化时仍明确显示其执行状态。
- 取消信号检查覆盖元数据请求返回、下载分块、重试等待、处理器开始前和结果提交前。已运行处理器若无法安全中断，保持“正在取消”直至执行方退出，再报告最终取消。
- 调整 `_run_install` 的等待方取消路径：设置取消请求、停止当前下载器，并继续追踪工作线程结果；不能继续沿用等待方先发 `INSTALL_CANCELLED` 而线程仍执行的终态语义。
- 不扩展为全局进程重构或强制杀安装器。应用退出时遵守现有资源关闭边界，明确记录尚未结束的清理状态。
- 进度变化按约 200 毫秒合并；阶段切换、失败、取消请求和最终结果立即发送。结束前提交最后一个完整快照，不因下载器分发队列残留而丢失终态。

| `useAppRuntime.ts`、`useTaskQueue.ts`、`applicationOperationStore.ts` | 接收权威快照，拒绝旧修订及终态后事件，处理阶段切换和指标清理 |

实施步骤：

1. 核对三个仓库现状及规范，梳理所有安装进度生产者、整合包消费者和测试替身；为现存缺陷补充能在修复前失败的定向回归。
2. 定义阶段与快照模型，列出五种加载器的实际步骤顺序，以及取消和失败状态迁移；先完成 Core 回调和主仓库集成。
3. 完成主仓库进度归集及整合包适配，确保并发、未知总量、重试和线程实际退出语义正确。
4. 同步前端边界校验、队列与界面，更新六语言和 showcase；复用现有 UiProgress 的 processing 模式，不为本页改造公共主题或组件。
5. 执行下节对应的全量检查和真实验收，发现失败先修复，不以静态测试替代实际布局和安装验证。
6. 验证通过后按仓库边界提交、子仓库优先集成本地 main，再更新主仓库 gitlink 并交付原工作区本地 main。

## 8. 测试与验收

### 8.1 风险分类

本次涉及下载文件写入、Core 公共接口、事件契约、共享队列状态和取消并发，属于 `AGENTS.md` 第 6.1 节的全量验证范围。实施完成后对受影响仓库执行全量检查，不归类为局部 UI 修复。

本文当前仅为方案文档，提交本文只检查内容、链接和 `git diff --check`，不运行应用测试或构建。

## 9. 风险与交付

- **跨仓库接口同步**：Core 参数、主仓库来源包装和全部调用方必须一起更新；固定提交集成，不加入属性或签名探测维持旧调用方式。
- **下载正确性**：字节统计和原子写入不能改变来源、目标路径、已有校验和失败恢复；用户文件保留，以隔离目录和故障注入验证。
- **共享上下文并发**：本次回调必须通过调用参数传递，独立记录加锁，避免两个安装互相覆盖状态。
- **取消不可立即生效**：执行中处理器可等待其退出；界面如实显示请求状态，不能提前发布终态掩盖后台仍运行。
- **步骤进度归零**：通过明确步骤标题和步骤位置解释局部进度，避免使用虚构阶段权重制造总百分比。
- **整合包与其他任务**：新增安装快照只作用于相关任务，保留其他任务的进度解释和 operation 最终状态所有权。

Git 交付遵循第 7 节：提交采用中文 Conventional Commits，关联 `Refs #67`；子仓库使用完整 `Refs ECLTeam/EuoraCraft-Launcher#67`。保护工作区无关的已暂存、未暂存及未跟踪文件，先提交并集成 Core 和前端本地 main，再提交主仓库指针及改动并集成本地 main。

本次方案选择和后续实施批准仅授权本地工作；远端推送和发布需针对当前变更单独授权。Issue 在仅本地交付时保持打开，不提前使用 Fixes／Closes。
