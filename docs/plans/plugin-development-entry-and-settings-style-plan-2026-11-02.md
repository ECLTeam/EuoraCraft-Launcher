## 1. 需求与选定方案

用户要求插件开发模式通过启动参数或配置文件的非必填项启用，插件页不再放置开发模式开关；插件设置应与项目整体样式一致。

本轮提供了保留全屏并统一样式、改用普通居中弹窗两种方案，用户选择 **A：保留全屏并统一样式**。

实施目标：

1. 插件开发模式支持启动参数和可选配置，默认关闭，插件页移除切换入口。
2. 保留统一全屏设置入口及行内定位入口，调整内部导航、卡片、间距和设置行。
3. 保留当前配置读写、冲突保护、异步响应隔离、插件授权与热重载安全约束。

本文替代[上一轮实施方案](plugin-development-mode-and-settings-plan-2026-11-02.md)中关于插件页开发开关、仅能手动开启和设置弹窗局部视觉实现的约定。上一轮方案保留为历史记录，开发监听、稳定副本、会话授权及统一设置服务的其他契约继续沿用。

## 3. 开发模式启动契约

### 3.1 参数与配置

新增桌面启动参数：

```text
python main.py --plugin-dev
python main.py --no-plugin-dev
```

两个参数互斥；未指定时内部值为 `None`，用于区分“不覆盖配置”和“明确关闭”。参数只影响当前进程，不写入配置文件。

在数据目录的 `setting.json` 中允许手动加入：

```json
{
    "plugins": {
        "allow_ui_injection": true,
        "development_mode": true
    }
}
```

以上仅展示相关配置分区，编辑时保留文件中的其他内容。`development_mode` 非必填，省略等同 `false`；首次生成配置不要求写入该项，也不因读取缺省值而补写文件。

该项只接受 JSON 布尔值，不把字符串、数值、数组、对象或 `null` 转为布尔值。非法值明确报配置校验错误并保留文件，不通过恢复整份默认配置掩盖此错误。复用现有配置校验错误机制，不新增无业务用途的配置框架。

生效优先级：

| 条件                                    | 实际行为                                                               |
| --------------------------------------- | ---------------------------------------------------------------------- |
| `--disable-plugins`                     | 本进程不启动开发监听，优先于开发参数和配置；保留既有安全模式的其他行为 |
| 显式 `--plugin-dev` / `--no-plugin-dev` | 分别开启 / 关闭，覆盖文件配置                                          |
| 无开发参数，配置为 `true` / `false`     | 按配置开启 / 关闭                                                      |
| 无开发参数，字段省略                    | 关闭                                                                   |

配置在进程启动时读取。运行中修改文件或保存其他插件选项不切换本次开发状态，重启后生效。修改其他配置时保留手动设置的该字段，不把命令行覆盖写回文件。

不与 `--debug`、Vite 开发构建、`--dev-channel` 联动。新参数不支持无头任务；第二次启动携带这些选项不能切换已有进程，转发路径应明确拒绝相关启动期请求，避免表现为已切换成功。

### 3.2 初始化与退出

在插件自动启用之前确定有效模式，使符合条件的目录插件直接按现有开发运行流程加载，避免先启动普通 Worker 再立即换代。具体接入已有管理器初始化顺序，不新增第二个监听服务或开发状态副本。

只接纳已经批准、按正常规则启用的第三方目录插件；不自动批准插件，不扩大权限，不监听归档或系统插件。禁用、卸载、撤权、声明变化及 `supports_hot_reload: false` 继续按现有契约处理。

配置为 `true` 可以让下次启动再次进入开发模式，但不保存或恢复上次的临时开发凭据。源码变化后新进程仍须满足现有审阅要求，不把持久化模式开关解释为永久信任变化的源码。

退出复用现有开发服务的停止与清理路径。需要普通模式时以 `--no-plugin-dev` 重启，或修改配置后重启；当前配置和插件私有文件保持原有保护。

### 3.3 页面与 IPC 清理

移除插件页开发模式开关、切换请求、执行锁和仅服务该开关的错误重试区。普通模式不占用工具栏位置；开发模式中保留插件行的监听、失败、需审阅等有实际用途的状态及既有手动重载操作。

删除 `plugin_development_set` 的生产方、消费方、请求模型、命令注册、日志策略和废弃测试；不保留旧入口转发。只读 `plugin_development_get` 若供实际状态展示使用则保留，访问边界不放宽；无消费方的查询轮询不继续保留。

## 4. 全屏设置的视觉与交互

### 4.1 页面结构

继续使用现有 `FullscreenModal` 的标题栏返回、模态栈、焦点进入与恢复机制。内部保留左侧插件导航、右侧设置内容，沿用项目设置页的紧凑节奏。

- 左侧采用紧凑导航列表，搜索框使用现有小尺寸控件；插件名称为主信息，标识为次级信息，长文本可查看完整内容。
- 选中项使用当前主题导航的强调色背景和文字，悬停与选中清楚区分，键盘焦点可见；不再让两者共用一个灰色块。
- 右侧保留插件标题、版本和打开目录操作，设置按项目现有“说明在左、控件在右”的设置行组织。
- 空设置状态在右侧可用内容区合理居中，避免只挤在标题分隔线下面；加载、失败、不可编辑和保存反馈仍有明确位置。

复用已有公共控件和样式入口。现有 `SectionLayout` 带路由选择语义，插件选择仍保持弹窗内状态，不为复用外观强行引入路由，也不改造公共布局 API。局部组合现有导航和表面即可，不新增无调用需求的组件框架。

### 4.2 样式归属与布局

- 卡片继续使用 `.ecl-surface`，移除覆盖公共卡片契约的局部圆角和外边框，跟随 `--ecl-card-radius`、公共边框、透明度与模糊。
- 页边距、区域间距与内边距取当前项目变量；不另设一套固定 16/20/24 像素节奏，不覆盖用户外观变量。
- 左侧宽度按内容和窗口约束适配，避免比例宽度随大窗口无限扩张；右侧占满剩余宽高。
- 外层固定在可用内容区，导航列表与右侧内容分别滚动，不产生额外页面同向滚动；搜索、标题和主要操作可达。
- 长插件名、长说明、较长译文和窄内容区允许合理换行，输入控件不撑破边界，列表最后一项可完整到达。

保留现有设置 schema、值保存、revision 冲突、保存中关闭约束、切换目标后的迟到响应保护及订阅释放。此次不改变设置存储格式或另造一套设置编辑逻辑。
