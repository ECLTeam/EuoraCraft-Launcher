# 第三方插件剩余能力三批实施总方案

日期：2026-10-31（Asia/Shanghai）。状态：第一批已完成并集成本地 `main`；第二、三批尚未实施，继续沿用已批准的批内授权。

用户希望将剩余工作归并成三次直接实施和交付，避免逐个小功能反复制定方案、确认和重复验收。本方案供一次审阅；用户批准三批实施后，批内依赖适配、错误处理、回归、文档与本地集成包含在同一授权中，不按内部步骤重新请求批准。远端推送、发布、线上服务部署与提供生产凭据仍是独立动作。

## 1. 盘点基线和完成定义

主仓库本地 `main` 为 `3e25df2`，前端 `d5b9bdf`，Core `e8aacb50ca82b8719f91f4f88ed26f9477172b64`，Florolding `80d037e73923e93cf961119932a117d3a04c297b`。开始每批时复核实际基线与无关改动，不按旧文档的阶段编号推断完成情况。

本方案讨论可安装的第三方 Python Worker。系统插件已有的宿主进程内接口、设计表里的方法、测试辅助代码及未合入工作树，均不计为第三方已实现。

当前已接通：

- 插件包与 Python wheel 依赖准备、安装/更新/卸载、内容审阅、启用/禁用/重载及 Worker 生命周期。
- 自有命令、设置、设置变化订阅；插件管理页及设置、命令、授权操作入口。
- 私有文件读取、新建、删除、替换与恢复；只读网络请求和私有空间下载；自有任务查询与取消。
- 获准游戏目录与实例查询、实例别名/描述/收藏/标签修改，Minecraft 目录/加载器查询、安装、启动、运行查询及停止本运行启动的游戏。
- 简化权限与一次审阅启用流程。当前主要业务权限为 `instances.read`、`instances.manage`、`network.read`，基础能力由 `plugin.base` 提供。

证据入口：[当前 Broker 分派](../../ECL/plugins/runtime/broker.py)、[运行平台检查](../../ECL/plugins/worker_service.py)、[现行包与权限协议](../protocols/eclplugin-package-format.md)。第三方 Worker 当前明确限制 Windows x64；私有文件和实例资料事务还依赖 Windows/NTFS 实现。

Java 查询/校验存在另一工作树提交 `6a52497`，但该提交不是当前 `main` 的祖先，当前 Broker 也没有 Java 分派。可复用经过核对的领域实现，不能整体合并该工作树的历史或恢复旧细分权限。安装尚需单独的真实业务接线。

当前未接通或不完整：Java、游戏资源管理、受限账户/公开配置查询、自定义操作面板与独立前端、实例/启动/崩溃扩展、第三方认证/联机、跨插件命令与更多事件、受监管工具进程、Linux/macOS Worker，以及在线分发和可信签名。归档手动更新已经存在，缺少的是在线发现、版本检查和受信更新闭环。

## 2. 路线与交付边界

| 路线 | 取舍 |
| --- | --- |
| 一次改完全部 | 确认次数少，但原生边界、共享业务和跨平台问题混在一起，失败难定位，无法提供中间可用结果 |
| 分后端、前端、测试三次 | 表面是三次，实际前两次都不构成可用功能，最后仍可能大量返工 |
| 按业务闭环分三批 | 推荐；每批同时完成所需后端、前端、SDK、测试和本地集成，内部按依赖顺序推进，不逐项打断用户 |

三次交付依次为：**游戏与 Java 业务能力 → 界面与扩展能力 → 跨平台与分发闭环**。第二批基于第一批，第三批验证前两批的完整能力。三批是交付单位，不强制挤成三个巨大提交。

## 3. 第一批：游戏与 Java 业务能力

目标：第三方插件能完成实际游戏管理，不必绕过 Host API 自己操作启动器目录。

| 工作项 | 修改位置与实施内容 | 可观察验收 |
| --- | --- | --- |
| Java 查询、验证、目录与安装 | `ECL/java/`、Broker、运行资源引用、任务所有者及可信审阅界面；核对已有工作树实现，查询使用登记快照，显式验证才运行选定 Java；安装固定来源与目标，合并任务前检查来源归属 | 查询不隐式扫描/执行全部 Java；安装成功登记并能用于启动；重复提交不重复安装，不能取消用户或其他插件任务 |
| Java 与游戏启动接线 | `services/game/plugin_games.py`、启动服务及最小启动参数模型；允许获准的当前运行 Java 引用，不接受裸路径或命令 | 同一游戏使用所选 Java 启动；过期或越界引用拒绝，已有安装/启动/停止行为保持 |
| 模组管理 | 复用 `services/game/mods.py`、资源搜索与下载；开放授权实例内的列表、安装、启用/禁用和删除，写入走所属任务与文件规则 | 真正改变选定实例的模组状态；版本冲突、同名文件、下载失败、撤权和重试都有明确结果，不误删其他文件 |
| 资源包与光影 | 复用 `services/game/resources.py` 等所属服务；列表、安装与删除限定已选实例数据目录 | 隔离实例和共享目录按现有业务归属放置；符号链接、路径越界、同名覆盖与失败清理回归通过 |
| 整合包 | 复用 `modpack_preparation.py`、`modpack.py`、`modpack_export.py`；导入识别、预览、安装任务与导出，归档先校验再进入业务层 | 实际导入并启动代表性整合包，导出可重新识别；取消按真实副作用报告，不宣称增量安装原子回滚 |
| 公共查询补齐 | 公开配置仅映射明确字段；账户摘要仅返回经批准范围，不透传账号文件、令牌或提供方私有数据 | 插件取得稳定受限 DTO；隐私字段不进入结果、日志及事件，账号变化后旧引用失效 |

实施顺序：资源与 DTO/授权 → Java 查询及安装 → 启动接线 → 游戏资源与整合包 → 真实示例及整批验收。已有 Minecraft 安装与启动不重写，只补当前调用缺口。

权限沿用现有简化方式：游戏内资源复用查看/管理游戏及所选目录，不为每个模组操作恢复一套细分开关。全局 Java 和账户属于不同资源，必须有明确的领域准入、用户可见范围和撤销处理，不能从基础启用或管理游戏推导全部访问。协议与六语言界面同步更新，不增加历史权限迁移。

交付：真实可安装的 Java/资源/整合包示例，覆盖成功、拒绝、取消、冲突和恢复；SDK、协议、主仓库与实际变更子模块一同集成本地 `main`。

## 4. 第二批：界面与扩展能力

目标：插件能提供自己的可操作功能界面，并通过受控扩展参与启动器流程。

| 工作项 | 修改位置与实施内容 | 可观察验收 |
| --- | --- | --- |
| 声明式操作面板 | 前端插件组件、schema 渲染器、Worker 注册与 UI 事件；采用文本、按钮、设置字段、列表、任务进度与分组等有界节点 | 插件实际显示并执行自己的命令、更新自己的设置；加载/失败/空状态与六语言、键盘焦点、主题布局通过，不在主窗口执行第三方脚本 |
| 自定义前端和独立窗口 | 按[原生隔离设计](../designs/plugin-native-webview-isolation-design.md)建立固定来源的原生构建与最小接口、可信壳、专用桥和窗口生命周期；先满足 Windows 必需控制，其他平台在第三批实现等价边界 | 原生导航、子 frame、网络及消息来源验证全部通过，才加载第三方代码；撤权或窗口关闭后端口/凭据失效，不能靠 CSP 或顶层导航回调冒充隔离 |
| 实例识别、启动与崩溃扩展 | 给现有 `instance_compat.py`、`launch_hooks.py`、`crash_extensions.py` 接入第三方远程注册/回调；DTO 与修改白名单替代裸服务对象、路径和完整启动上下文 | 实例扩展可识别代表性数据；启动前后/退出回调实际发生；必要前置失败阻止创建，后置失败不杀游戏；崩溃扩展不泄漏凭据 |
| 第三方登录 | `auth_providers.py`、账户服务、Worker RPC、动态登录界面；提供方只处理自己的认证材料与不透明持久数据 | 登录、重启后凭据解析、提供方禁用和失败重试完整；不能读取其他提供方或微软账号凭据，不记录认证材料 |
| 联机与联机扩展 | 联机服务、`plugins/connector.py` 及实际 Florolding 公开接口；会话带来源与代次，远程回调有界 | 插件实际建立/加入/离开自己的会话；不能关闭用户现有房间，迟到回调不覆盖新会话，底层资源真实停止或明确待清理 |
| 跨插件调用与事件 | 当前 Broker 的命令导出、发现/调用及事件登记；只公开允许的命令与事件，明确双方准入及订阅归属 | 调用已导出命令成功；未导出/未获准/已禁用目标拒绝，重载后旧引用失效；事件订阅不会在禁用后残留 |
| 受监管工具进程 | supervisor、工具声明及所属进程/终端服务；固定受审工具身份、参数模型、输出预算和控制所有者 | 实际工具进程有进度/输出和可确认退出；只能停止自己的工具树，不把用户 Minecraft 纳入插件工具监管 |

实施顺序：声明式面板与回调通道 → 实例/启动/崩溃 → 认证与联机 → 互操作/事件/工具 → 自定义前端原生门禁 → 整批示例和冻结验收。内部可以拆模块与提交，但不以每个注册方法为由重新询问实施权限。

现有系统插件继续使用其明确支持的宿主接口，新增第三方远程适配不把其全部对象暴露出去。新敏感领域采用明确准入与资源范围；不将插件能直接调用 Python 系统 API 描述为已经获得 OS 安全沙箱。

交付：至少一套实际可安装的面板/窗口插件与一组领域扩展示例，覆盖第三方完整链路；相关前端、原生构建、主仓库与实际修改子模块通过验收并集成本地 `main`。

## 5. 第三批：跨平台与分发闭环

目标：前两批能力可在目标平台运行，插件可通过明确来源发现、安装与更新，开发者有完整可用的 SDK 和工具。

| 工作项 | 修改位置与实施内容 | 可观察验收 |
| --- | --- | --- |
| Linux/macOS Worker | 将 Windows 专属传输、身份认证、进程树监管、文件身份和事务实现放回平台边界；实现 POSIX 对应路径，不以删除平台检查代替支持 | 在对应系统真实完成安装、启用、业务、撤权、停止及重启恢复；跨来源控制、子进程残留、符号链接与原子替换验收通过 |
| 跨平台自定义窗口 | 为各平台实际 WebView 实现同等来源、导航、网络和消息边界；不在导入时无条件读取 Windows API | 各平台达到自定义前端相应门禁；不具备真实证据的平台明确待验收，不把 Windows 结果外推 |
| 在线发现与版本更新 | 客户端插件目录、搜索/详情、版本及平台兼容检查、下载与更新确认，复用现有安装事务 | 使用测试源完成发现→安装→更新→重启→重新审阅；断网/损坏包/不兼容版本保留现有可用安装和用户数据 |
| 签名与可信来源 | 包格式、发行人身份、信任根、签名校验、撤销及来源展示；明确无签名本地开发包与受信源包的处理方式 | 篡改、未知或被撤销签名拒绝；有效签名不自动授予业务权限，不能以归档哈希替代作者身份 |
| SDK、制作工具与完整发行回归 | 整理 SDK、接口与错误目录、开发模板、制作/检查工具、完整示例；按现有发行目标维护 wheel/ABI、源码/PyInstaller/Nuitka 适用矩阵 | 全链生命周期及升级失败恢复通过；没有空实现、只有声明的能力或需旧接口才能工作的示例；文档与当前分派一致 |

分发默认完成启动器客户端与来源协议，使用本地测试目录/模拟源完成验收；不自行创建线上商店后台、发布目录、信任真实发行人或部署服务。线上运营系统属于需要地址、账户及运营规则的外部范围，不能把本地客户端完成说成公共商店已经上线。

跨平台开发需要对应系统或可运行的构建/验收环境。当前本机 Windows 不能证明 macOS/Linux 原生验收成功；可以完成实现及 CI 接入，但缺少环境时须将准确的剩余平台验收记录为未完成，不通过跳过测试结束整批。远端 CI 所需推送不包含在本方案默认本地授权中。

交付：三平台的实际证据及能力表、分发客户端、签名工具与协议、完整 SDK/示例和本地集成；外部环境未就绪时分别报告已实现、已验收和受阻部分。

## 6. 共同实施和验收方式

1. 本方案批准后，三批按顺序实施。已列明能力所需的 DTO、领域 API、资源归属、前端、原生绑定及子模块修改均在对应批内，不逐个方法重新审批；发现业务选择存在直接冲突、需要删除用户数据、增加本方案之外的产品能力或缺少不可代替的外部信息时才向用户确认。
2. 每批先细化本批契约和方法清单，并保存在所属协议/设计中，然后完整接线。内部细节按既有规则决策，不把细化文档作为再次等待用户的关卡。保留来源、资源范围、错误、去重、超时、取消与实际清理语义，不返回空成功掩盖未接通。
3. 失败场景与真实调用方一起覆盖。开发中使用与修改相符的定向反馈；按用户实施后的最新要求，只运行新增行为和直接影响链路的必要回归、改动文件质量检查，以及适用的构建与真实界面验证；不为凑流程重复全量检查，不为内部每个小功能重复同一整套矩阵。
4. 新增功能提供能安装到真实启动器的示例，至少覆盖成功、拒绝、失权/失效、取消和失败后重试；涉及资源修改增加冲突与恢复，涉及回调增加断线/迟到/重载。冻结/平台验收按实际构建目标记录，不将源码或 jsdom 通过泛化为发行物通过。
5. 每批清查旧接口、清单、类型、文档和示例。没有真实需求不新增旧字段别名、迁移或动态接口探测；保留用户文件、事务恢复与失败回滚。
6. 验收通过后提交相关改动，先集成前端或其他实际变更子仓库本地 `main`，再集成主仓库；保护所有无关修改，不推送、打标签或发布。一次完整交付只向用户汇总该批成果与剩余项。
7. 完成三批后用实际 Broker 方法、SDK、示例与平台证据逐项核销本清单；最终结论区分本地功能完成、平台验收、远端交付和线上运营，不使用笼统的“插件全部完成”掩盖缺项。

## 7. 仍不作为缺陷补做的边界

本方案不包含任意读取/修改宿主配置、导出通用账号令牌、直接调用全部 IPC、操作任意用户路径、强制停止其他来源游戏/房间、全局 Java 删除清理或恶意 Python 的操作系统沙箱。这些不是“漏写几个接口”，也不因为增加插件能力而默认开放。

主窗口界面注入原属本节排除项，用户已于 2026-11-01 明确选择纳入第二批，改按[主窗口注入决策](../designs/plugin-main-window-injection-decision.md)实施；该决策同时规定权限门禁、代次失效与通用桥隔离要求，本节其余边界不变。

原有设计里的 P11—P19 用作历史依赖索引，本方案按当前实现归并交付；已完成的游戏安装/启动不回退重做。三批总方案批准后替代对上述批内小切片逐项确认的默认实施方式，但不会自动满足缺失的技术验收条件。
