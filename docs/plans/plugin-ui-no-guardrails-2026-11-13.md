# 插件界面不新增防护的决策

- 日期：2026-11-13。
- 状态：用户已定，不再讨论。
- 关联：[权限简化方案（方案 B）](plugin-permission-simplification-plan-2026-10-30.md)、[内核门面收敛方案](kernel-facade-convergence-plan-2026-11-13.md)批 4。
- 取代：本文替换 `plugin-ui-boundary-and-fault-isolation-plan-2026-11-13.md` 与更早撤回的 `ui-capability-trust-tiering-plan-2026-11-13.md`，两份均已删除。

## 1. 决策

用户两次明确表态，口径一致：

1. 不再限制插件能力，只保留启动器自身数据安全与防崩溃。
2. 不再提供这些权限的防护功能。

综合为一条：**插件界面能力不设准入、不做防护、不新增容错机制。** "不再提供"指未来不新增，现有实现保持原样。

本决策与权限简化方案（方案 B）的立场一致：该项目不把插件视为需要防御的对手，权限只是能力范围声明，不是安全沙箱。

## 2. 取消的项

早先两轮方案中的以下内容全部取消，不再实施：

| 项 | 取消原因 |
| --- | --- |
| `ui.inject` 能力与逐插件授权 | 等于把已砍掉的授权项装回来，违背方案 B |
| 三级信任分级（Tier 0/1/2） | 同上，且 Tier 2 依赖尚不存在的内置标识体系 |
| 通道 B 收进 iframe + postMessage | 后端本就能读凭据文件，前端隔离不改变威胁模型，只增迁移成本 |
| 脚本语法黑名单或静态分析 | 挡不住混淆，只会制造"看起来安全"的假象 |
| `PluginSlotHost` 与路由出口包 `ErrorBoundary` | 属新增容错机制，本决策明确不新增 |

## 3. 现状保持不变

这些是既有代码的形态，不是本轮要维护的承诺；后续如需删除，单独决策。

## 4. 客观后果

记录事实，不作劝阻：

- 插件组件在**渲染期**抛错时没有边界接管，错误会沿组件树冒泡，可能让所在区块（侧边栏或内容区）白屏，需要刷新启动器恢复。编译期与脚本求值期已有兜底，渲染期没有。
- 插件路由页面异常时会与宿主路由共用同一棵渲染树，故障范围同上。
- 后端不受影响：插件崩溃在 Worker 进程内，主进程存活。

这是有意选择的取舍。插件质量由作者负责，不通过宿主防护来补偿。

## 6. 仍需处理的一件事

`docs/designs/plugin-declarative-panel-design.md:13` 现写"不在主窗口执行第三方脚本……这与系统插件的 Vue 插槽机制是两条路径"。这句话把通道差异描述成了安全边界，与代码不符：不存在"系统插件"标识，`external_plugins/` 与第三方走同一安装路径。

它与本决策不冲突，属表述修正，建议改为：

> 面板是"无需提供代码即可获得界面"的路径，只由宿主渲染受限节点。主窗口插槽是"完全开放"的路径，插件的模板与脚本由宿主在同源上下文编译执行。两者的差别是表达方式，不是信任级别。

这是文档准确性问题，不是防护问题，可单独确认后修改。
