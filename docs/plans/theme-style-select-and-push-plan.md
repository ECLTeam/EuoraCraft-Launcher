# 主题风格下拉框与推送实施方案（已实施）

## 目标与验收

- 设置页「外观 → 主题风格」改为下拉框，仍提供「经典」和「Folia」两个内置主题，选中后立即应用并保存；重新启动后保持所选主题。
- 控件及弹出菜单留在窗口范围内，文案随现有语言翻译变化。亮暗模式、主题配色及其他外观选项保持原行为。
- 功能验证通过后，将前端子模块和主仓库的所有本地未推送提交安全合入各自远端 `main`，核对远端指针，最后执行 Windows 关机。

## 当前项目情况

- `frontend/src/views/settings/AppearanceTab.vue` 用 Naive UI 的分段 `NTabs` 展示内置主题；`BUILTIN_THEMES` 在 `frontend/src/config/theme.ts` 中定义两项，切换经 `setThemeId(..., false)` 即时更新，再由 `settingsStore.patchUiTheme` 持久化。
- 同一页已有 `NSelect`，主窗口样式下拉框的弹层挂在 `#app`；`SettingRow` 负责左右布局。主题名称已有六种语言译文，无需新增文案。
- 前端当前位于 `codex/window-titlebar-mode`，本地主题相关提交和下载页预取提交尚未推送；前端远端 `main` 比共同祖先多 4 个提交，本地多 10 个提交，双方已分叉。
- 主仓库当前位于 `main`，远端 `main` 比共同祖先多 3 个提交，本地多 13 个提交，双方已分叉。远端主仓库的前端指针为远端前端 `bc89e45`，本地指针为 `294939e`。两个仓库工作区目前干净。

## 可选方案与取舍

| 方案 | 主题控件 | 历史整合 | 取舍 |
| --- | --- | --- | --- |
| A（推荐） | 使用现有 `NSelect` 样式，只显示本地化主题名称 | 分别合并远端 `main`，保留双方提交，再按前端、主仓库顺序推送 | 改动小、布局统一；会出现合并提交。 |
| B | `NSelect` 自定义选项与选中值渲染，保留现有图标 | 将本地提交变基到远端 `main` 后推送 | 视觉信息更多、历史线性；代码更复杂，且会重写本地提交标识并牵动子模块指针。 |

## 推荐方案的实施步骤

1. 在 `AppearanceTab.vue` 中将主题风格的 `NTabs` 换成 `NSelect`，选项值直接沿用 `classic` / `folia`，继续调用现有主题切换与配置保存函数；使用现有下拉框宽度和弹层挂载约定。仅在布局需要时调整 `AppearanceTab.css`。
2. 针对主题控件的选项、持久化调用和窗口边缘布局做有意义的验证。执行 `cd frontend && pnpm check`、`pnpm build`，再实际启动 Windows 启动器验证切换与重启恢复。
3. 先在前端仓库单独提交这项变更。把已获取的远端 `main` 合入前端当前分支；如遇冲突，仅按两边原有意图解决，并在合并后重新运行必要的前端检查。确认可以快进更新远端 `main` 后，推送当前前端提交到 `origin/main`，禁止强推。
4. 主仓库合入远端 `main`，将子模块指针指向已推送的前端合并结果；检查远端 README 等更新保留完整，必要时运行后端 Ruff 与相关 pytest。按同一功能单独提交主仓库文档及子模块指针；完成合并验证后推送主仓库 `main`，禁止强推。
5. 核对两个远端 `main` 均指向预期提交、主仓库子模块指针可从前端远端获取，且工作区无意外改动。全部成功后执行 Windows 正常关机命令。

## 风险与失败处理

- 远端在推送期间若再次前进，重新获取远端并合并，继续快进推送；不覆盖他人提交。
- 检查、构建、启动验证或任一推送失败时，停止后续推送与关机，保留日志和当前状态供处理。
- 关机前关闭本次验证启动的进程；关机会结束本机其他运行中的程序，请提前保存其他应用中的未保存内容。
