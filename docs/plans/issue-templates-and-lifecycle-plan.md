## 4. 表单字段与填写要求

### 4.1 缺陷报告

标题预填 `[问题] `，提示使用具体行为，例如「切换实例后仍显示上一个实例的下载结果」。不用「有 bug」「启动不了」作为唯一描述，不设置自动标题检查。

| 字段 | 必填 | 内容要求 |
| --- | --- | --- |
| 提交前确认 | 是 | 已搜索已有 Issue；提交内容不含令牌、凭据或未经脱敏的个人信息 |
| 问题描述 | 是 | 一个可以独立跟踪的问题；说明触发条件与影响 |
| 启动器版本或提交 | 是 | 发布版本填写完整版本；源码运行填写提交 SHA；子模块相关时补充子模块 SHA；确实无法获取时说明原因 |
| 操作系统 | 是 | Windows、Linux、macOS、跨平台或尚未确认 |
| 环境补充 | 否 | 系统版本、架构、运行方式；按需填写 Minecraft、Java、加载器或插件信息，不索取完整私人路径 |
| 复现步骤或代码证据 | 是 | 用户填写操作步骤；开发者可填写代码位置、调用路径及错误依据；暂不能复现时说明已尝试的步骤和已观察到的证据 |
| 预期结果 | 是 | 正常情况下应发生什么 |
| 实际结果 | 是 | 实际发生什么、是否可重复、影响范围 |
| 日志与截图 | 否 | 可用时提供相关片段和截图，日志字段使用代码格式，截图单独放置，避免格式阻止附件展示 |
| 补充信息 | 否 | 临时绕行方式、关联 Issue 或其他有助定位的信息 |

字段 `id` 保持唯一、稳定，输入提示使用 `placeholder` 或说明文字，不预填能够绕过必填检查的示例答案。只使用所需的普通字段类型，不依赖远端标签、组织 Issue 类型或自动分配处理人。

### 4.2 功能建议

标题预填 `[建议] `。必填提交前查重确认、使用场景、目前的问题、期望效果；已有替代方式、建议实现和补充资料选填。提交者无需先设计技术方案；功能建议仍需按第 0 节完成方案确认，Issue 本身不构成实施批准。

### 4.3 表单约束的边界

`blank_issues_enabled: false` 用于引导普通用户走表单。GitHub 仍向有写入及以上权限的维护者保留空白入口；通过 API 或 CLI 创建 Issue 时也不会自动执行这些表单必填校验。因此贡献指南和项目规范同时要求维护者、AI 助手通过这些入口提交时提供等价信息，不声称已经实现所有入口的技术强制校验。

模板在进入远端默认分支后才会出现在正式选择器中。本地提交不等于线上模板已生效。

## 5. Issue 登记、修复与关闭规则

### 5.1 登记对象与归属

- 在已授权的调查、开发、评审或验收中发现已确认缺陷时，先搜索已有 Issue。已有相同问题则补充证据与影响范围；没有则创建缺陷 Issue。即使本次暂不修复，也要登记并说明待处理状态。
- 只有猜测、没有定位依据的情况先调查，不把推测写成已确认事实。提交者尚无法复现的报告可以登记为待确认，后续补充证据。
- 默认在 `ECLTeam/EuoraCraft-Launcher` 集中登记启动器问题，使用表单正文说明前端、后端、Core、联机组件或其他涉及模块。发现子仓库已有相同 Issue 时优先关联它；确有主仓库集成验收需求时，在主仓库建立关联记录并明确分别满足什么关闭条件，避免重复维护同一份进度。
- 一条 Issue 对应一个可独立验证的问题；多个独立问题拆分，保留必要的关联链接，不把同一缺陷的多个表现机械拆成重复 Issue。
- 在用户已经授权的问题处理范围内，创建、补充及按本方案条件关闭关联 Issue 属于该任务的必要协作操作，无需逐条重复请求授权。该约定在正式规范实施后生效，不授权修改范围外的问题、向他人发送通知消息、推送代码或发布版本。
- 网络或权限导致无法登记时，保留问题内容并明确标记待登记，不编造 Issue 编号，也不宣称已提交到 GitHub；可继续不依赖远端登记且已经获准的本地工作，恢复后补齐，交付时说明尚未完成的登记事项。

### 5.2 修复与验证

1. 登记后说明问题证据、涉及模块与当前处理状态；Issue 描述与讨论不替代第 0 节的方案和实施批准。
2. 获准修复后，在关联提交正文或 PR 中使用 `Refs #编号` 记录关系；跨仓库使用完整的 `ECLTeam/EuoraCraft-Launcher#编号`，避免引用到子仓库中相同编号的问题。
3. 按第 6 节增加适用的回归验证并执行相应检查；记录实际执行的命令、结果及尚未完成的真实界面或集成验收，不能将某一检查通过泛化为全部通过。
4. 本地提交与本地 `main` 集成完成后，更新 Issue 为「本地修复完成，待远端交付」并提供可追踪的提交 SHA 和验证摘要；这里的状态使用正文或评论表达，不依赖新增标签或看板。
5. 修复跨主仓库与子模块时，记录子仓库修复提交及主仓库集成提交，关闭以完整的启动器交付结果为准。

### 5.3 关闭条件

- 以「已修复」关闭前，修复必须进入远端默认分支，且第 6 节所要求的测试与验收均已完成。涉及子模块时，必须同时满足第 8 节的远端可获取性要求，主仓库默认分支已引用修复指针，并完成受影响集成验证。
- 只完成工作树提交、本地 `main` 集成或子仓库合入时保持主仓库问题打开。尚未推送、尚未完成验收或只修复一部分时，说明剩余事项。
- `Fixes #编号`、`Closes #编号` 等关键字只用于合入远端默认分支后即可满足全部关闭条件的最终交付。子模块提交、分阶段修复以及合入后仍有验收待办的 PR 使用普通关联，避免自动提前关闭主仓库问题。
- 满足条件后，优先在 Issue 中留下修复提交或 PR 链接、验证摘要，再按「已完成」关闭；若使用自动关闭，确保这些证据已经在关联 PR 或 Issue 中可见。没有 PR、直接推送默认分支的交付，在完成验收后补充结果并手动关闭。
- 重复问题必须链接到原问题；无法复现的问题说明环境、尝试过程和缺失信息；决定不处理或不接受的建议说明理由。关闭原因使用 GitHub 提供的相应原因，不能将这些情况描述为已修复。
- 后续确认同一问题仍存在时重新打开原 Issue 并补充证据；原因独立的问题另建 Issue 并关联。

这里不要求每个修复都创建 PR，不改变现有直接提交、本地集成、推送批准或 Beta 发布流程。修复进入远端默认分支与对外发布版本分别报告，关闭 Issue 不等于用户已经可以从 Release 下载修复版本。

## 6. 正式文档的组织方式

`AGENTS.md` 继续作为工程协作的唯一强制入口。在第 0 节现有流程之后增加「问题登记与跟踪」子节，说明登记范围、查重、归属、授权及失败处理；第 7 节补充提交关联、远端交付和关闭条件。测试与子模块核验分别引用第 6、8 节，不复制命令，不为 Issue 流程另起与已有职责重复的顶层章节。

`CONTRIBUTING.md` 提供面向人的步骤、标题与填写示例，解释问题报告与功能建议的区别，并链接现行工程规范。PR 模板只保留关联 Issue、具体变更、实际验证、待完成事项四部分；不强制纯文档 PR 虚构缺陷编号，也不预填有效的自动关闭语句。

README 增加贡献指南和 `issues/new/choose` 入口，保留现有文档站入口；不把尚未核实的私密安全报告渠道写入文档，也不将凭据或敏感漏洞细节引导到公开 Issue。

## 7. 实施步骤

1. 提交本方案供用户审阅；明确获得「开始实施」或同等批准后再执行下列步骤。
2. 复查工作区、当前文档与 Git 基线，记录并保护无关改动，仅暂存本次文件。
3. 编写两份 YAML 表单与选择器配置，核对字段、中文提示、必填项和外部链接。
4. 编写贡献指南与 PR 模板，按第 6 节约定更新 AGENTS 和 README，不改变其他规范含义。
5. 按第 8 节完成本地定向检查，回看「普通用户填写」「开发者代码证据」「子模块修复」「只有本地交付」「重复关闭」五类流程是否一致。
6. 在本文件记录实际修改、检查结果与待远端验证项，按第 7 节完成相关提交和安全的本地 `main` 集成。可以将纯说明文档与模板配置分别使用 `docs`、`chore` 提交，确保每次提交职责清楚。
7. 仅获得针对本次变更的明确推送授权后，按第 8 节核验全部子模块指针并推送；再执行正式表单验收。缺少推送授权时停止于本地交付，明确线上尚未生效。

## 8. 验证计划与验收标准

本次属于协作模板配置及文档变更，不修改 CI 或应用运行代码。对新增 YAML 做定向配置检查、对文档做结构与链接检查；无需全量 pytest、前端类型检查、构建或启动启动器。

本地必须完成：

- 检查三份 YAML 可解析，拒绝重复键，核对表单顶层字段与 GitHub schema 所需的结构、字段类型及唯一 ID；不新增项目运行依赖或永久检查工作流。
- 核对必填字段、复选框要求、标题前缀、没有预填示例答案、日志与截图可以分别提交，以及 `blank_issues_enabled` 是布尔值 `false`。
- 检查 Markdown 结构、内部链接、现行章节引用及外部链接地址；正文中的规划路径不误写成已经存在的文件链接。
- 按上述五类流程检查规范一致性，尤其确保子模块修复与仅本地提交不会提前关闭主仓库问题，API 提交提供等价信息。
- 执行 `git diff --check`，检查实际暂存差异，并验证无关修改和全部 gitlink 保持原样。

经授权推送后才可完成的正式验收：

- 在 GitHub 的 `issues/new/choose` 确认两份表单、显示顺序与文档入口可用。
- 打开两份表单，确认字段渲染与必填校验；验证缺少必填项时被阻止，填写合规内容后可以进入正常提交准备状态，不实际提交测试 Issue。
- 当前账户具有管理权限，会保留维护者空白入口；普通用户入口行为按平台文档核对，有可用的只读身份时再进行实测，不将管理账户观察结果当成普通用户验收。
- 若没有推送授权或无法执行浏览器验收，明确报告「本地检查通过，线上表单待验证」，不得宣称线上流程已生效或真实表单验证通过。
