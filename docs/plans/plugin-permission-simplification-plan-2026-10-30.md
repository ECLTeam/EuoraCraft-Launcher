# 插件权限简化实施方案：方案 B

状态：用户已选择 B（底层合并为少数大权限），等待审阅本文件并确认开始实施。当前仅完成调查、问题登记和方案，不修改运行代码。

关联建议：[#74：简化插件授权以降低普通玩家的启用门槛](https://github.com/ECLTeam/EuoraCraft-Launcher/issues/74)。基线：主仓库 `ed3a536`，前端 `8b9f40d`。

## 1. 目标与取舍

让基础玩家按“插件要做什么、可以访问哪个游戏目录”完成启用；插件作者只声明少数业务权限。底层同步移除命令、设置、文件读写及游戏各操作的细分授权，不保留一套隐藏的旧权限开关。

合并意味着一次同意包含的能力更多。例如允许管理游戏后，插件可以在所选目录安装实例、修改实例资料和启动游戏；确认界面必须直接说明这些后果。范围之外的实例、其他插件的数据和进程仍不可通过 Host API 访问。

本轮调整权限契约和启用流程，不新增游戏卸载、存档修改、任意命令执行、第三方 Java API、POST 请求或自定义前端。现有 Worker 也不提供恶意 Python 的操作系统文件或网络沙箱，文档不得将 Host API 授权描述为系统级隔离。

## 2. 现状及影响范围

- `PluginHostBroker.implemented_capabilities` 当前包含16项权限。
- `PluginPermissionsModal` 按每个声明生成勾选项，并为读取、修改资料、安装、启动、停止分别创建资源选择器；保存后只刷新列表，需要再点击启用。
- `PluginGrantSession`、资源服务、私有文件、网络、下载、资料修改和游戏操作适配器直接依赖这些细项；将界面合组不能完成方案 B。
- 自身任务的执行准入、结果投影、文件暂存和恢复依赖原始许可与运行代次，合并时必须一起改动，不能只删除入口检查。
- 现行授权记录按安装标识和完整内容摘要分文件保存；改变清单会产生新的摘要，已有机制可以要求重新确认，不需要格式迁移。

## 3. 新权限契约

### 3.1 随启用获得的基础能力

启用当前已确认内容后，插件可以：

- 注册、执行自身命令，读取和修改自身设置，订阅现有开放事件。
- 查询宿主公开游戏版本和加载器目录。
- 在自身专用数据空间读取、新建、替换和删除文件；沿用现有配额、路径限制、版本冲突及恢复机制。
- 查询和取消自己本次运行提交的任务，读取自身运行信息。

上述能力不再出现在清单和玩家授权选项中。内部统一使用 `plugin.base` 运行准入，绑定安装、内容、运行及授权代次；它不是可由清单请求或玩家独立开关的权限。插件未启用、已关闭、内容变化或运行失效时，基础准入同样失效。

### 3.2 只保留三项可申请权限

| 清单权限 | 玩家名称 | 包含的实际能力 | 授权范围 |
| --- | --- | --- | --- |
| `instances.read` | 查看游戏 | 扫描实例、读取公开摘要和资料、查询允许读取的自身游戏运行状态 | 用户确认的游戏根目录 |
| `instances.manage` | 管理游戏 | 查看游戏，以及安装新实例、修改现有允许修改的资料字段、启动实例、停止自己本次运行启动的游戏 | 用户确认的游戏根目录 |
| `network.read` | 联网 | 现有 GET/HEAD 请求及下载数据源访问 | 清单声明并由用户整组确认的精确站点 |

管理游戏直接包含读取，不再同时要求独立读取、修改、安装、启动和停止许可。操作及结果交付使用实际取得的管理准入，不在操作完成后换取另一个许可补救旧任务。

插件可将查看游戏列为必要、管理游戏列为可选，以支持拒绝管理后的只读模式。两者同时声明时，界面合为一个游戏访问区、共用一次目录选择，管理授权包含该范围内的查看能力；有效范围和必要权限判断由授权服务统一计算。

游戏授权统一选择根目录，包含该根下现有及以后新增的实例。移除逐操作、逐实例授权入口；管理权限不允许停止用户手动启动、其他插件或本插件先前运行创建的游戏。目录被替换、移出配置或授权撤销后仍须使对应引用失效。

联网保持目前实现的站点及请求限制；合并权限不开放任意地址、宿主凭据或其他 HTTP 方法。该权限控制插件指定站点的请求；基础游戏目录查询仍通过宿主固定来源完成，不接受插件指定 URL。下载需要联网许可和基础私有数据准入，不再要求独立文件写入许可。

### 3.3 清单、查询与旧声明处理

- `api_version: 2` 和现有 Host API 方法名保持当前契约；权限声明只允许上表三项。旧权限声明明确拒绝并提示更新插件，不做别名转换、自动合并或双格式支持。
- 基础插件使用空 `permissions`；游戏管理示例只需声明 `instances.manage`，联网插件按需声明 `network.read` 及站点。
- `resources.list` 的 `capability` 收敛为 `plugin.base`、`instances.read`、`instances.manage`。前者只发现自身私有数据空间，后两者发现相应获准游戏根及运行引用；同步更新请求模型、路由、示例和文档。
- `permissions.list` 只列出已声明的三项可选业务权限；基础能力属于启用契约，在文档和简短启用说明中明确，不伪装成隐藏的16项授权记录。
- 更新所有主仓库维护的插件清单、测试清单和归档示例。清理旧授权检查时区分权限名称与同名 RPC 方法，如 `commands.register` 方法继续存在。
- 沿用按内容摘要分开的现有授权记录格式。新清单对应新摘要，重新确认后写入新摘要的记录；不扫描、迁移、删除旧记录或插件数据。损坏记录继续明确失败并保留文件。

## 4. 玩家操作流程

1. 安装流程继续说明来源和必要下载行为，安装本身不执行插件。
2. 点击启用时，如果插件仅使用基础能力，将该次明确启用动作作为内容确认，不再弹出空权限表。
3. 需要业务权限时，展示用途摘要、游戏访问级别与目录、联网站点。游戏目录默认选中当前有效目录，并在确认前明确展示名称；没有有效目录时要求选择或前往配置。
4. 游戏访问仅有一个目录选择区；有多个目录时可明确追加选择，不展示五套资源列表。管理范围常驻说明“包含此目录中现有和以后新增的游戏”，以及安装、资料修改、启动和自身游戏停止的实际能力。
5. 主按钮为“同意并启用”。在已有可信主窗口权限更新成功后调用既有启用入口；实际启动失败时保留真实授权状态并提供“重试启用”，不显示成功，也不要求重复审阅。
6. 已启用插件的权限管理按钮为“保存修改”，避免保存操作误变成重启。默认记住授权，临时允许等设置放入详情；拒绝必要权限时清楚说明无法启用。
7. 重复点击只执行一次。保存后插件切换、窗口关闭或异步旧响应到达时，不得启用错误插件或覆盖当前界面；关闭进行中的启用流程沿用现有约束。
8. 内容更新仍按当前完整内容身份重新确认，不借本轮增加签名信任、跨版本自动继承授权或后台自动扩大范围。

## 5. 后端与前端改动点

| 范围 | 主要修改 |
| --- | --- |
| `grant_models.py`、`grant_store.py` | 定义三项业务权限、基础运行准入和游戏管理包含查看的规则；按游戏根计算范围，保留主体、内容、代次和撤销检查 |
| `runtime/broker.py`、`runtime/models.py` | 更新实际开放权限与资源查询模型；自身命令、设置、事件、游戏目录使用基础准入；保留固定方法路由和去重 |
| `runtime/resources.py`、`worker_service.py`、`resource_catalog.py` | 合并游戏根审阅与发现；修改、安装、启动和停止通过管理根验证目标身份，移除仅供旧细分权限使用的范围状态 |
| `runtime/file_api.py`、`download_api.py`、相关文件模型 | 私有文件操作改用基础准入；保留原对象版本、配额、事务恢复、实际关闭及清理占位；下载仍复核联网与基础准入 |
| `runtime/instance_profiles.py`、`game_install.py`、`game_launch.py`、`game_queries.py` | 资料和游戏写操作使用一个管理准入；公开目录使用基础准入；读取和结果投影按新契约执行，不恢复已失效的旧任务准入 |
| 既有任务服务与应用绑定 | 继续复用唯一任务、进程和安装服务；仅在真实消费者需要时调整接口，不增加新执行器或另一份权限状态 |
| API 模型、管理 store 与 `Plugins.vue` | 更新根目录资源范围和“同意并启用”流程；复用现有权限更新及启用 API，保留可信调用来源校验 |
| 权限弹窗与资源选择器、六语言 | 最多三项业务权限、一个游戏目录选择区、用途说明、必要权限状态、启用结果及重试反馈 |
| 主仓库维护的示例、测试、协议与设计 | 同步清单、SDK 调用示例、有效范围、基础能力及撤销语义，标明取代 P12 中独立游戏许可的现行说明 |

不新增基类、权限框架或通用适配层。新的包含关系与基础准入归入现有授权服务；前端读取有效状态并提交用户选择，不维护一份独立的权限推导规则。

## 6. 实施步骤

1. 固定新清单、基础准入、游戏管理包含查看和根目录授权的测试预期，再同步修改声明与授权服务。
2. 切换基础 Host API、私有文件及目录查询，随后切换实例资料、安装、启动、停止和下载；移除原读写双许可组合。
3. 更新资源发现、权限管理 API 和全套示例；检查未知权限、旧声明、未实现方法及跨主体引用的失败结果。
4. 实现简化权限界面和启用流程，完成六语言与重复操作、失败重试、异步失效的回归。
5. 更新协议、设计及既有方案的现行边界说明，运行完整检查和真实验收；只在全部通过后提交功能。
6. 先提交并集成前端本地 `main`，再提交主仓库及指针并集成原工作区本地 `main`，保护无关改动。本轮方案选择不视为新一轮远端推送授权。

## 7. 测试及验收

这是权限模型、IPC、私有文件与共享状态变更，执行受影响仓库全量门禁。

- 主仓库：`ruff check ECL tests`、`ruff format --check ECL tests`、`python -m pytest --tb=short -q`；按现有 Ruff 版本执行适用根目录检查，并检查修改的示例文件。
- Core：不主动改变子模块指针，验证相关主仓库集成及 Core 测试；若实际实施触及 Core，再按其自身规范扩大检查。
- 前端：`pnpm check`、`pnpm build`。修改前先为旧流程中重复授权和授权后未启用的问题建立能失败的回归；同步替换已废弃权限预期。
- 权限行为：基础插件无需逐项授权；仅查看不能修改或启停；管理包含查看且只在所选游戏根有效；管理可选被拒时只读模式可用；联网不能由游戏管理或基础准入取得。
- 生命周期：旧内容、跨安装/运行、撤销后重新允许、任务提交竞争、结果交付、实际执行结束及清理失败仍按真实事实处理；基础准入也不能跨关闭或新运行复用。
- 文件与恢复：新建、读取、替换、删除、流式下载及现有恢复流程完整覆盖；合并许可不放宽对象身份、版本、事务、路径和配额校验。
- 启用流程：一次同意只启用一次；必要权限不足不能提交；保存失败不启用；启用失败保留已保存授权并能重试；切换插件后旧响应不启用或覆盖新目标。
- 平台：覆盖 Windows 实际运行及 POSIX 对未支持执行边界的明确拒绝，不以 Windows 通过推定其他平台通过。
- 真正 Worker：源码、PyInstaller、Nuitka 入口分别验证基础插件、只读实例、管理实例、联网与下载示例；不把 Broker 直调用例当作发行入口验收。
- 实际启动器：独立数据和账户，验证基础启用、拒绝/允许管理、查看降级模式及一键启用；通过真实插件完成安装、资料修改、游戏启动和自身进程停止，验证撤销后被拒与失败文件保留。
- 真实 UI：Classic/Folia、亮暗、六语言、背景/透明/模糊，960×600、默认及放大窗口；验证单目录选择、用途与后果可见、长名称、列表末项及操作按钮可达。

## 8. 完成标准

玩家侧没有自身命令、设置、私有文件读写和游戏各动作的独立授权项。插件作者只面对三项业务权限；运行实现不再依赖旧细项，也没有旧声明转换层。基础插件可直接启用，业务插件可在一次用途确认中选好目录并完成启用。上述完整检查和真实验收通过后，才标记本轮实施完成。
