# 游戏语言首次初始化实施方案

状态：策略已选定，待用户确认实施。

日期：2026-10-25。

关联问题：[首次启动游戏未初始化语言](https://github.com/ECLTeam/EuoraCraft-Launcher/issues/59)。

## 1. 目标与已确认策略

仅在游戏语言未配置时跟随启动器语言。已有语言选择始终保留，包括英文；启动器语言变化后也不重新覆盖。

“未配置”限定为实际游戏数据目录中的 `options.txt` 不存在、文件缺少 `lang` 键，或该键的值为空白。非空但无法识别的值也原样保留，不推断用户意图。是否存在存档不参与判断。

本次只增加启动前初始化，不新增界面选项或持久化配置字段，不改变字体、其他模组配置及用户已有语言值。

## 2. 当前实现与变更位置

- `ECL/api/game.py` 的 `game_launch` 已读取有效配置并调用 `launch_instance`，可在此读取本次启动所用的 `ui.locale`。
- `ECL/services/game/launch.py` 已确定最终 `game_directory`，并在线程中调用 `_apply_fullscreen_option`。当前只更新 `fullscreen`，没有语言初始化。
- `ECL/utils/config.py` 定义界面语言默认值 `zh-CN`。前端切换语言后通过现有设置接口持久化该字段。
- `ECL/game/Core/Libs.py` 有未使用的语言写入函数，但路径固定为隔离目录，且已有文件缺少语言键时不会追加。本次围绕主仓库实际启动目录实现，不接入该函数，不修改 Core 子模块。
- `tests/test_game_service.py` 已覆盖全屏、其他配置保留和隔离目录；`tests/test_frontend_api_config.py` 覆盖 IPC 到游戏服务的启动参数传递。

## 3. 实施步骤

1. 在 `game_launch` 从有效配置读取界面语言，通过明确的内部关键字参数传给 `launch_instance`；不扩展外部启动请求模型。检查桌面、快捷启动及无头启动调用链，确保经过同一入口，直接调用游戏服务的入口显式传递相同来源。
2. 由 `LaunchCoordinator` 维护类型明确的语言对应关系：`zh-CN → zh_cn`、`zh-TW → zh_tw`、`en-US → en_us`、`ja-JP → ja_jp`、`ru-RU → ru_ru`、`de-DE → de_de`。缺少界面语言时使用项目默认语言；非法配置值记录告警并跳过初始化，禁止拼接为游戏选项。
3. 使用扫描得到的实际原版版本及原版元数据判断语言代码格式，不使用可重命名的实例名称。1.1～1.10 使用大写地区码，1.11 起使用小写地区码；不支持语言选择的版本不写入语言。快照及特殊版本依据可确认的原版元数据判断；无法可靠判断时保留文件并告警跳过，不猜测版本。
4. 将启动前选项更新集中到一个职责明确的方法，一次读取并按需更新 `lang` 和既有 `fullscreen`，在线程中通过现有 `atomic_write_text` 一次替换。保留其他键、注释、行顺序及已有语言内容；只有语言确实未配置时才写入目标值。
5. 读取失败、编码损坏和写入失败必须保留原文件，记录脱敏告警，继续使用游戏已有状态。尤其不能在读取失败后按空文件重建，再由全屏更新覆盖原文件。无文件属于正常首次初始化；临时写入失败不得破坏旧文件。
6. 更新受影响模块的文件头、参数说明和中文多行文档；修改现有测试预期并补齐回归。方案、提交和问题记录只描述本项目行为。

## 4. 回归测试与验收

必须新增可在修复前失败、修复后通过的用例，覆盖：

- 文件不存在、缺少 `lang`、空白 `lang` 三种初始化场景，以及六种启动器语言。
- 既有英文、中文、未知非空语言值完全保留；切换启动器语言后再次启动仍保留游戏选择。
- 存档目录存在或不存在时行为一致。
- 版本隔离开启与关闭时，只修改最终游戏目录中的配置，不修改其他目录。
- 全屏开关与语言初始化同时生效，未知配置及原有语言不丢失，重复执行无额外变化。
- 旧版与新版地区码、无语言选项版本、快照及无法识别版本的明确处理。
- 读取失败、编码错误、原子替换失败时原文件保持完整；告警不暴露私人路径；故障不会被后续全屏写入绕过。
- IPC 读取当前有效语言并传递，直接调用方及无头入口行为一致；覆盖适用的 Windows 与 POSIX 分支。
