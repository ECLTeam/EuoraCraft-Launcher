## 1. 需求、范围与既有约定

统一启动器的数据读取、写入、事件同步和失效策略，减少无数据变化时的重复 IPC 与重复扫描，同时保证更新及时、写入顺序正确、失败可重试。

用户选择 C：全面梳理前后端数据层。此前比较过 A（优先治理配置、关于页、分类与扫描链路）和 B（仅修轻量重复查询）；C 范围更大，需要按数据域分阶段迁移和提交。

本方案承接现有 `frontend-startup-data-layer-plan.md`、`instance-route-cache-implementation-plan.md` 和 `backend-startup-cache-and-surface-correction-plan.md` 的已实现约定：复用 Vue Query 与 Pinia，保留路径身份和失效保护，联网缓存与预热由后端服务负责，不恢复前端开机批量查询热门列表。

纳入配置、账户公开信息、启动器信息、插件注册表与状态、本地实例与目录配置、实例分类/资料/资源、Java 清单、在线资源查询展示、运行实例与长任务状态。游戏引擎、认证协议、发布规程及无关 UI 风格不做重写。

## 3. 目标架构与职责

| 层次 | 负责 | 约束 |
| --- | --- | --- |
| Transport / IPC 边界 | 请求发送、超时、响应校验、稳定错误转换 | 不按命令名缓存全部 RPC，不合并启动/删除/保存等动作；超时不等于后端已停止 |
| 前端领域 API | 类型明确的读写接口、资源身份、写入影响范围 | 组件不直接绕过领域 API 重新封装 IPC；外部响应先校验再进入业务层 |
| 前端共享数据层 | 展示快照、同资源在途合并、失效与重读调度 | 使用现有 Vue Query，不再为同一份服务端数据同时维护多个独立有效期 |
| Pinia / 页面 composable | 选择、筛选、编辑草稿、加载/失败状态及订阅 | 可保留响应式展示，但不建立另一套互不知情的服务端缓存；编辑草稿与已确认快照分开 |
| 后端领域服务 | 文件和网络成本缓存、权威结果、原子写入及领域变更通知 | 继续复用 ResourceSearchService、ConnectorService、扫描器等；共享可变状态集中管理并受锁保护 |
| 事件桥与应用运行时 | 一次注册、明确退订、领域变更分发 | 单一变更不由多个入口各自启动全局刷新；已有 SDK 和窗口契约保持兼容 |

统一的是职责和刷新规则，不是所有数据使用同一 TTL：配置和分类主要靠变更失效；实时状态靠事件及有限轮询；联网结果有效期由后端掌握；编辑草稿、搜索分页展示与渲染媒体可以保留适用的页面状态。

## 4. 核心读写和一致性契约

1. 查询身份必须包含所有影响结果的参数：资源类别、来源、版本/加载器、语言（若影响结果）、规范化目录、实例、隔离模式等。复用现有 `gamePathIdentity`、后端 `rootKey/rootAliases`，保留 Windows/POSIX 语义。
2. 同一有效快照的并发读取共用在途请求。空数组、`null` 等合法空结果可缓存；错误、超时及未校验的结果不作为成功快照缓存。
3. 明确普通读取、数据变更失效、手动刷新和外部文件变化的区别。真实变更发生后，旧请求不得提交到新快照；同一变更的多入口通知合并，不用固定时间窗口吞掉后续真实变化。
4. 刷新执行期间记录新的失效需求；完成后如已有更新变化，至少再读取最终状态。仅删除 Promise 引用不能被当作在途 IPC 已经结束。
5. 写入沿用领域串行队列和原子落盘。独立操作分别执行，失败不伪造成功；可合并的自动保存仅在原有业务语义允许时合并尚未提交的草稿。
6. 写入结果包含权威快照时直接更新该资源；只返回确认时，安排一次相关资源重读。事件与写入响应不能各自再重复拉取一遍同一快照。
7. `config:updated` 的持久化分区不能未经处理就替代含环境变量和启动参数覆盖的运行配置。先确定有效配置契约，再决定事件更新快照还是合并重读。
8. 长任务“已提交”不代表文件或实例已经变更完成。缓存更新依据实际成功、实际领域变更和最终任务状态；页面卸载只退订，不停止下载、安装或游戏进程。
9. 全局查询返回只读快照或适用的防御性副本；账户凭据不进入展示缓存，不打印请求体、快照、目录身份或凭据。
10. 多窗口、前端重建、插件注册变化和展示模式切换均有明确的数据层生命周期。对未知旧事件执行安全的相关域失效回退，不让后台事件访问已释放的页面状态。

## 5. 分阶段实施与文件边界

### 阶段一：公共数据契约与刷新调度

- 扩展 `frontend/src/app/queryKeys.ts`，按数据域定义完整查询身份。
- 将 `app/data/index.ts` 的查询定义按域拆分为薄模块，保留现有导出兼容层，迁移结束后删除仅供内部使用的旧入口。
- 增加 `app/data/refreshCoordinator.ts` 及行为测试，统一相关域的在途刷新、失效保护和后续刷新需求。已有 Vue Query 承担缓存，不重复实现查询框架。
- 保留 `api/client/commands.ts` 的 Transport、错误呈现和操作观察职责；运行时边界使用现有 Valibot/响应校验设施，不通过 `any` 或无依据断言绕过。
- 形成读写接口与事件影响范围清单；仅对确认共享的数据迁移，不将必要轮询统一缓存成静态快照。

### 阶段二：配置读取、写入和事件同步

- 收敛 `settingsStore.ts`、`useTheme.ts`、`i18n/index.ts`、`useAppRuntime.ts`、资源目标选择及插件状态的配置入口。
- 同分区写入进入统一队列，保留未知历史字段、下载目标映射和有效配置覆盖规则；相同持久化结果不重复落盘或广播无变化事件。
- 后端核查 `ECL/utils/config.py`、`ECL/api/settings.py`、`ECL/host/frontend_events.py`：对有效快照建立明确边界，必要时补充经过校验的事件字段或快照接口，旧消费方保持可用。
- 原始事件分区若不能代表权威有效配置，则由调度器合并为一次读取，不直接用原始载荷覆盖运行状态。
- 需要协议扩展时同步 `ECL/api/models.py`、前端 API/事件模型和正式 IPC 日志策略；不添加日志关联编号。

### 阶段三：实例扫描、资料、目录配置和分类

- 迁移 `instanceInstallApi.ts`、`instancePathConfigApi.ts`、`instanceProfileApi.ts` 与 `instanceStore.ts` 的缓存所有者和刷新入口，保留现有路径别名、空结果、请求代次及选择失效回归。
- 目录变化只刷新受影响目录，不再无条件 `loadAll(true)` 扫全部已配置目录。同时保留真正的全局手动刷新。
- 分类使用一个共享数据源；分类写入成功后定向更新或失效，列表/详情/分类窗口订阅同一结果。
- 修改 `ECL/services/game/profiles.py`、`scan.py`、必要的 `instance_profiles.py`：协调本程序写入后的立即通知与文件监视通知，确认同一变化只发布一次，而外部新增/修改/删除仍被识别。
- 对资料字段、启动统计、文件结构变化区分影响范围；返回的资料不足以生成完整实例展示时，安排一次必要的定向扫描，不伪造完整实例。

### 阶段四：账户、启动器信息、插件与 Java

- `AboutTab.vue` 使用共享 `launcherInfoQuery`；运行信息按本次宿主生命周期共享，初次失败或空结果可恢复，不能永久缓存失败。
- 保留账户已有快照推送能力，移除消费者重复回读；`accountStore.ts` 和 `plugin-sdk/state.ts` 使用同一已确认账户数据。
- 插件注册表仍以完整快照更新；注册/禁用/卸载的批量事件合并刷新，公开 SDK 接口保持兼容。
- Java 清单以既有 `javaRuntimeStore.ts` 和后端运行时服务为基础统一查询/更新，不让设置、实例和管理窗口各自扫描系统。
- 登录、刷新凭据、启停插件、安装 Java 等写操作保持独立的执行锁、状态和实际结果；不纳入普通读请求去重。

### 阶段五：实例资源、在线查询及长任务

- `instanceWorkspaceApi.ts`、`localModsApi.ts`、`instanceSettingsApi.ts` 的查询按实例与资源类别接入同一数据机制，迁移后移除同域重复的结果 Map/Promise Map，保留适用的媒体生成和生命周期缓存。
- 各资源的成功写入/任务完成仅刷新对应实例与资源类别；关闭页面或旧响应返回时不污染新目标。
- `OnlineModSearch.vue` 的筛选、分页和展开状态继续属于页面；同条件在途读取统一调度，平台联网缓存继续交给后端 ResourceSearchService，不增加另一套前端联网 TTL。
- 依赖元数据、热门列表、目录和来源配置分别核查后端缓存与失效；不恢复启动时全平台预热，不把三个不同资源类型的相同命令合并。
- 运行实例及操作状态沿用事件与必要的有界轮询，应用级所有者统一管理同任务查询；保留请求取消与实际停止的区别。

### 阶段六：清理重复实现和工程验收

- 逐项核对领域清单，删除已无消费者的旧缓存和监听器，保留仍用于纯 UI、搜索展示或媒体资源的有效机制，不为统一风格清理无关代码。
- 核对所有改动域的加载、空数据、失败、恢复和成功状态，以及跨页面任务和订阅释放。
- 完成调用次数比较、前后端检查和实际启动验收；按同一数据域/阶段分别提交中文 Conventional Commit，不把整项重构和无关改动混为一个提交。

## 6. 新规范的落地要求

- Python 改动遵循统一文件头、多行中文 docstring、类型、原子写入和并发规则；内部稳定数据使用 Pydantic、TypedDict 或 dataclass，不长期传递 `Any`。常量与领域映射只在实际修改的模块内收敛。
- 新增或修改前端文案同步简中、繁中、英文、日文、俄文和德文；保留外部程序原始输出。UI 不展示缓存编号或数据层实现细节。
- 本方案不主动改变布局；实际修改页面仍核对主题、状态、键盘和焦点。涉及尺寸、滚动或可见性改动时增加真实浏览器布局验证，不能用 jsdom 结果代替。
- 正式查询仍按 DEBUG、轮询成功保持安静。保留必要的真实操作日志，不靠删日志或改级别掩盖重复请求。日志不打印任务编号、来源编号、完整参数或账户数据。

| 场景 | 验收目标 |
| --- | --- |
| 同一资源 10 个并发读取消费者 | 未变化时只产生 1 次真实读取；参数不同的资源分别查询 |
| 多入口消费配置/分类/运行信息 | 共用快照，未失效时不因重新挂载重复 IPC |
| 写入执行与变更事件相邻到达 | 最终状态一致，不形成“响应刷新 + 事件刷新”的重复链路 |
| 读取期间出现新变化 | 旧结果不提交；合并通知后继续取得最终状态，不能丢变化 |
| 写入失败、读取超时或初次空运行信息 | 不缓存失败，不误报成功，下一次允许重试 |
| 本程序资料写入与监视器检测 | 同一实际变化不重复广播/扫描；紧邻的外部变化仍得到处理 |
| 目录 A 变化、目录 B 未变化 | 只刷新 A，B 的缓存和选择不受污染 |
| 手动刷新、安装/删除、外部文件修改 | 明确需要的新读取仍执行，不能为了调用次数减少而返回旧数据 |
| 页面卸载、窗口重建、切换实例/来源 | 订阅释放，旧响应失效；后台任务继续按实际状态运行 |
| 启动与不同页面连续切换 | 对照相同行为脚本统计实际请求，而非只比较日志总行数 |

实际启动使用隔离数据执行主题/语言切换、账户管理、关于页重复进入、分类编辑、资料编辑、目录切换、外部文件变化及任务进度场景。核对 Classic/Folia、亮暗及相关背景设置；涉及界面改动时覆盖默认、960×600 最小和放大窗口。认证边界使用受控替身，真实联网或账户认证未测试的部分明确记为未验证。

## 8. 风险、回滚与提交推送

主要风险为错误的查询身份、遗漏失效、配置覆盖差异、旧请求回填、监听器重复，以及合并刷新时漏掉真实变化。通过明确的数据域、独立行为回归和阶段迁移控制，不以通用 RPC 拦截器一次改完所有操作。

每阶段以兼容的领域 API 迁移消费者，验证通过后移除该域旧实现。发生问题可按该阶段 Git 提交回滚；不创建长期双轨数据源或永久兼容开关。协议扩展保持旧调用可用，不修改账户、实例或用户配置文件格式来实现缓存优化。

前端协调器、领域入口与消费者存在编译依赖，以同一数据层功能的原子提交保持代码可构建；后端独立变化按域拆分提交，主仓库另提交前端指针与记录。保留此前账户颜色功能及其他功能的已有本地提交。本次推送或发布仍按用户后续指令执行；推送时先核验并推送所有引用的子模块提交，再推主仓库并验证全新递归检出。
