日期：2026-10-16。状态：用户已确认可改造无头模式并按需导入；本次入口整合已完成验收。

本文是 `plugin-worker-api-v2-implementation-design.md` 的入口与运行组织修订建议。用户最新目标是让插件子进程依赖 ECL 无头模式，复用同一发行物；此前选择的实例扫描、Java 检测、插件包检查不作为本次扩展范围。既有 IPC、用户授权和进程隔离决策继续有效，自定义前端原生隔离仍按用户要求暂缓。

## 2. 方案比较与推荐

| 方案 | 具体做法 | 取舍 |
| --- | --- | --- |
| A：只更换启动参数 | 新参数映射到旧内部引导，其他入口结构不动 | 改动最小，但容易保留两套模式判断、帮助与错误处理，整合程度有限 |
| B：统一轻量进程分流，增加无头插件角色（推荐） | 在宿主导入前统一识别桌面、无头任务、无头插件；插件角色复用已有 IPC、Job、快照与 SDK | 满足同发行物、正式无头启动与轻量运行目标；改动集中，可用现有真实进程测试验证 |
| C：插件子进程创建完整 ApplicationContext | 进入无头后直接创建桌面使用的全部后端服务 | 会引入账户、单实例、联机、更新与旧插件自动加载；重复服务和状态所有者，不能满足当前插件授权边界 |

推荐 B。复用协议和监管代码，不继续维护与无头模式平行的插件启动通道。不同进程仍拥有独立解释器、模块和内存；不会共享主进程 Python 对象。

这项改造不会凭空降低现有发行物体积：当前已没有独立 Worker 可执行文件。可验证的收益是统一运行入口、减少重复运行组织；内存、冷启动和 onefile 解包成本必须测量，不能由参数变化推断。

## 3. 命令与运行契约

### 3.1 三条运行路径

```text
ECL.exe
  → 桌面宿主

ECL.exe --headless --task runtime-check
  → 一次探测任务 → 输出结果 → 退出

ECL.exe --headless --role plugin --pipe-address <宿主端点> --host-pid <PID> --run-id <运行标识>
  → 无头插件子进程 → 认证 IPC → 等待授权加载 → 运行生命周期 → 清理退出
```

最后一条由宿主监管器生成，不是允许用户直接运行任意 Python 文件的 CLI。参数不包含插件路径、账户、授权决定或秘密。管道地址、PID 和 run-id 都不能单独赋予权限。

规则如下：

- 不提供 role 时，现有桌面启动和 runtime-check 用法保持原行为；`--role` 本次仅引入显式的 plugin 值。
- `--role plugin` 必须与 `--headless` 一起使用；不得与 `--task`、`--result-file`、桌面选项或业务启动参数混用。
- 管道、宿主 PID、运行标识为插件角色专属必填参数；普通任务和桌面模式拒绝这些参数。
- 插件角色拒绝未知参数、重复且冲突的角色或模式，不允许以缩写、参数顺序或 `--` 分隔绕过。角色控制选项采用完整名称；已有普通桌面参数的解析行为不顺带重写。
- 插件参数错误或认证失败直接非零退出，不进入 GUI、runtime-check 或完整宿主初始化。
- 插件模式通过 IPC 交付握手、回调和结果，不向 stdout 输出任务 JSON；失败时不弹出桌面错误窗。已有 runtime-check 结果协议和退出码保持原契约。
- 本次新增插件角色仍以 Windows x64 为验收范围；普通 runtime-check 保留原跨平台范围。

### 3.2 加载与退出顺序

1. 宿主选择当前可信发行 EXE；源码模式沿用 base CPython 与 `-S`。
2. 以新无头参数挂起创建进程，在恢复前分配并核验 Windows Job。
3. 子进程的轻量入口只加载标准库和插件运行所需的受信 SDK，不创建 ApplicationContext、WebView、单实例服务或开发通道。
4. 宿主和子进程通过现有管道边界互相核验，宿主持有真实进程句柄并核验实际执行进程及 Job 归属。
5. 宿主复核安装、内容摘要、依赖锁、用户审阅和必要权限后，才发送加载许可；子进程再次复核内容。
6. 在子进程中执行插件模块及 v2 生命周期；服务复用通过受限 Host API 完成。
7. 禁用、卸载、重载、断连和宿主退出分别结束相应会话，释放所属注册与句柄，最终由 Job 回收本运行进程树。已经进入宿主的业务任务仍须遵循既有任务所有者及撤销设计，不能以子进程退出代替任务停止。

自定义前端能力不随无头整合开放；本次也不改变未完成的 OS 沙箱范围。

## 4. 具体代码边界

### 4.1 统一轻量分流

- 新增根目录 `ecl_bootstrap.py`：仅标准库，定义不可变的进程路由结果和角色参数规则；不得导入 ECL、PyTauri、业务服务或用户模块。
- `main.py` 使用轻量分流结果选择模式。桌面和普通无头任务仍交给既有 CLI 与任务执行器；插件角色进入无头插件执行器。
- `ECL/cli.py` 复用轻量层的模式判定和校验规则，避免与主入口分别解释同一组角色参数。具体桌面业务选项继续由现有解析器处理。
- `ECL/runtime/contracts.py` 明确任务与插件角色是不同生命周期，不把插件运行塞入仅返回 RuntimeProbe 的任务模型。
- 不通过 `sys.modules` 删除、伪造 has_host_modules 或放宽安全握手掩盖导入越界。

不能直接从 `ECL.runtime.headless` 导入插件执行器：Python 会先初始化 ECL 包，而现有插件握手要求尚未加载 ECL。轻量分流放在 ECL 包之外是这一导入边界的实现需要，不是第二份运行环境。

### 4.2 无头插件执行器与宿主监管

- 将 `ecl_plugin_api/_worker.py` 的受信引导职责迁入无头插件执行模块，建议命名 `_process.py`。保留依赖快照、受限导入、双向 RPC 和生命周期实现，不复制一套。
- 新执行入口接收已经校验的插件角色参数，保留平台、管道、Job 和内容复核；参数不作为可信授权主体。
- `ECL/plugins/runtime/executable.py` 生成新无头命令；`supervisor.py` 从新入口获得相同握手、状态及失败语义。
- 删除旧 `--internal-plugin-worker` 启动分支；不添加长期兼容通道。旧参数明确拒绝，不能跌入桌面。
- 不为清理 Worker 名称而重命名所有类、协议错误码和文件；只有受影响入口及职责名称随本次迁移调整。
- 保留标准库 SDK 包与宿主服务模块的分离；不向插件传入管理器、ApplicationContext 或完整前端 IPC。

### 4.3 正式管理器接入的关系

入口整合本身不等于全部第三方插件迁移完成。后续继续原设计 P06：按宿主发现来源区分系统插件与第三方；第三方仅使用新无头角色，校验 v2 与用户授权后加载，不保留进程内降级路径。系统插件保持可信宿主路径。

正式管理器接入时，需要同时完成安装身份登记、授权管理 IPC 的真实调用来源、会话清理和前端状态更新；不能仅修改 `_create_instance` 的构造调用。Host Broker 的待完成写接口、任务来源和即时撤销仍按原方案分阶段验收。

## 6. 审阅边界

选定方案 B、`--headless --role plugin` 命令形式，以及“共用进程分流、区分普通任务与插件生命周期”的边界。

用户随后确认“可以改造无头模式，实现更多的无头功能，按需实现导入功能”。据此实施方案 B，首批接入现有 runtime-check 与插件角色；其他业务任务按后续具体需求扩展，不自行新增完整后台服务或实例/Java 业务命令。实施通过门禁后补充真实验收记录。

## 7. 实施记录

已增加标准库轻量入口 `ecl_bootstrap.py`。导入 main 不预载 ECL、SDK 或 PyTauri；只有选择插件角色才导入插件执行器。普通任务仍在参数校验后按需导入原任务执行器。非法混用、角色缩写、旧内部入口、错误连接参数均在宿主导入前拒绝。

原受信插件引导迁入 `ecl_plugin_api/_process.py`；监管器生成正式无头参数，沿用原有连接、Job、授权加载和双向 RPC。插件目录和依赖内容校验没有降级为用户可指定的脚本执行。Python Wheel 已检查包含 `ecl_bootstrap.py` 和新执行模块，不再包含旧 `_worker.py`。

当前检查：

- Ruff check 与 format 检查通过；源码后端完整回归 1575 通过、15 跳过。跳过项包含需要指定冻结产物或特定平台条件的测试；不将跳过视作已验收。
- 前端 `pnpm install --frozen-lockfile`、`pnpm check` 与 `pnpm build` 通过：162 个测试文件、889 项通过、1 项原有 todo；无前端源码及子模块指针改动。
- PyInstaller 6.22.3 新 onefile 产物通过 23 项联合验收：无头探测、源码及冻结插件引导、实际原始 EXE 解析、双版本依赖、原生 Wheel、生命周期和 Job 监管。
- PyInstaller 普通桌面以独立 data-dir、禁用插件启动。真实 PyTauri/WebView2 页面标题与原生桥可见，后端收到 frontend_ready，截图确认主界面可渲染，并通过原生窗口 API 正常关闭。未使用隔离账户替身，不将此次验收作为账户隔离或认证验证。公告联网发生超时回退，不将它记为联网功能通过。

单次本机、空测试载荷的进程观测结果：源码握手 141 毫秒，实际执行进程 RSS 27.20 MiB；PyInstaller 握手 938 毫秒，执行进程 RSS 28.05 MiB。PyInstaller 原始 EXE 引导 PID 与插件执行 PID 不同，执行进程经过 Job 核验；两种模式均确认回收。该观测不是完整插件负载基准，没有旧版本对照，不承诺性能下降比例。

Nuitka 同条件单次观测为握手 1297 毫秒、实际执行进程 RSS 81.66 MiB，原始引导 PID 与执行 PID 不同，执行进程未在握手前导入 ECL、确实位于 Job 内，退出确认回收。这说明复用一个 EXE 与按需导入并不消除每个解释器、编译运行时和 onefile 引导的内存成本；本次不宣称与独立精简发行物具有相同占用。

本地验收产物位于忽略目录 `build/acceptance/`；冻结构建日志为 `build/headless-pyinstaller.log` 与 `build/headless-nuitka.log`。入口整合不会自动完成旧 PluginManager、权限管理 UI、完整 Host API 或自定义前端安全边界。
