# 模组禁用后无法重新启用修复方案

状态：用户已选择推荐方案并明确要求开始实施。修复、完整检查、生产构建和真实 Windows 启动器验收已完成，待完成原项目目录本地同步。

## 1. 需求与复现

用户确认问题发生在禁用模组后重新打开模组开关，而不是启动游戏时。

调研基线：主仓库 `fd56d7f`，前端 `82025b3`。

真实启动器使用现有生产构建、真实后端及隔离测试实例复现：

1. 实例管理模组页读取 `test-mod.jar`，显示为启用。
2. 点击禁用，后端将实际文件重命名为 `test-mod.jar.disabled`，返回 `enabled: false`。
3. 前端只修改 `mod.enabled`，没有修改 `mod.filename`，列表仍显示 `test-mod.jar`。
4. 再次打开开关，前端使用旧文件名请求启用，后端返回“模组文件不存在”。

复现截图及日志位于工作区外 `../launcher-mod-toggle-research-20261002-105539/`。真实文件保留在该目录中的隔离实例里，不操作用户游戏文件。

## 2. 根因及影响范围

- `ECL/services/game/mods.py` 的 `toggle_instance_mod` 按现有规则添加或去除 `.disabled` 后缀，并检查原文件与目标文件是否存在。
- `game_instance_mod_toggle` 及前端 `instanceWorkspaceApi.toggleMod` 的既有返回契约只有 `enabled`。
- `frontend/src/components/instances/InstanceDetailModsTab.vue` 的 `handleToggleMod` 成功后只更新启用状态，没有同步文件名。
- 重新启用和禁用后删除都会继续提交旧文件名；刷新列表后重新获得实际文件名，因此可能暂时绕过问题。
- 当前没有其他模组管理组件执行这一启停处理；旧本地模组 API 是单独入口，不需要为了本次修复改动其协议。

## 3. 可选方案

1. **推荐：切换成功后同时更新文件名和启用状态。** 按现有 `.disabled` 后缀规则更新这一条模组；请求期间禁止重复操作同一条目。保留当前 API，不重新读取整个列表，大量模组时操作响应稳定。前端需要明确遵循现有后缀协议，并通过生命周期测试防止状态再次脱节。
2. 切换成功后重新读取整个模组列表，以磁盘列表更新条目。无需在前端推导文件名，但每次切换都需要重新解析所有 JAR；大量模组时增加等待，并触发整页加载及搜索、筛选下的内容重建。

用户已确认按方案 1 实施，以下步骤按该方案执行。

## 4. 具体改动

仅修改前端实例模组页及新增相关回归测试，不更改后端重命名规则或 IPC 返回结构。

- 成功禁用：将当前文件名从 `xxx.jar` 更新为 `xxx.jar.disabled`，同时更新 `enabled`。
- 成功启用：只去除末尾的 `.disabled`，恢复真实 `xxx.jar`，同时更新 `enabled`；不处理名称中间的相似文本。
- 操作失败：保留原文件名及启用状态，沿用已有错误提示，不提前乐观更新文件名。
- 同一模组请求未完成时，禁止重复切换及删除，避免并发提交仍未完成重命名的路径；完成或失败后恢复操作。其他模组可以继续操作。
- 后续删除使用更新后的真实文件名；列表 key、文件名说明、启用筛选和禁用筛选按原渲染逻辑更新。
- 保留搜索、图标、译名、滚动、现有行高、删除确认和在线详情。
