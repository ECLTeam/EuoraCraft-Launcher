# 全局弹窗切换时序修复实施方案

状态：用户已确认开始实施；代码、自动检查和 Windows 桌面验收已完成。

## 目标与验收标准

修复更新提示与 Microsoft client_id 缺失提示在切换时重合的问题。所有独立弹窗切换采用“当前弹窗完全退场，再展示下一弹窗”的顺序，由现有全局模态框栈管理。

1. 配置缺失提示先到、更新提示先到、二者同时到达时，均不会同时显示两个独立弹窗或叠加两层遮罩。
2. 配置缺失提示关闭后，更新提示继续展示；被抢占的更新提示保留其请求与业务状态。
3. 退场期间停止旧弹窗交互，维持必要的滚动锁；交接完成后焦点进入新的活动弹窗。
4. 账户管理、实例详情等父级与其子弹窗可以同时保留，只有顶层可交互；关闭子弹窗后恢复父级。
5. 更新已读记录只在用户实际关闭更新提示时保存。等待、隐藏或被抢占不能视为已经阅读。

## 当前实现与问题边界

- `ECL/api/bridge.py` 在前端就绪后发送 `microsoft-client-id-required` 警告，并补发已完成的启动更新检查结果；更新检查也可能稍后独立完成。
- `useLauncherPopupQueue.ts` 将配置缺失警告放入通知队列，默认优先级为 75；通知关闭后已有 2000 毫秒的过渡间隔及 blocker。
- `useAppRuntime.ts` 收到 `update:check_completed` 后直接开启共享更新弹窗开关，`UpdateResultModal.vue` 的优先级为 60。
- 二者都使用 `Modal.vue` 和 `useGlobalModalStack.ts`。全局栈已有优先级、父子关系、交互归属和滚动锁管理。
- `Modal.vue` 的独立弹窗在 `visible` 变为 false 时会立即 unregister；高优先级弹窗注册也会立即改变展示链。旧 DOM 的 Vue 退场动画可能仍在播放，新展示链就开始入场。
- `FullscreenModal.vue` 在关闭和外部隐藏时也直接 unregister，需要共同处理，才能覆盖全屏页面与独立提示之间的切换。
- 现有部分组件测试使用默认 Transition stub，只检查状态切换，不能证明真实动画期间没有重合。

上述是已确认的时序缺口。尚未在真实启动器中复现用户报告；实施开始后先记录现场，核对是否还有样式或事件重发因素。如果发现需要修改本方案范围以外的业务行为，补充方案后再确认。

## 选定设计

### 1. 在现有全局栈中分开请求与实际展示

继续以现有注册项、优先级和顺序计算目标展示链，增加当前实际展示链与待完成退场项的最小状态。优先级决定下一步目标，退场完成信号决定允许何时展示。

- 首个弹窗直接展示。
- 关闭或独立弹窗抢占时，先隐藏需要退场的展示项并禁止交互；待相关渲染组件报告退场完成，再按最新请求计算并展示目标链。
- 被抢占但仍请求显示的弹窗继续留在注册项中，不调用其业务关闭回调。
- 退场期间的新请求只更新下一目标；完成后重新计算，不展示已经被取消的请求。
- 当前退场项涉及的滚动锁和必要全屏布局状态保留到退场完成，避免背景在交接期间闪动或滚动。
- `activeModalId`、`interactiveModalId` 与实际展示保持一致；交接期间不允许尚未出现的弹窗响应 Escape 或获取焦点。

### 2. 普通弹窗与全屏弹窗报告真实动画完成

`Modal.vue` 与 `FullscreenModal.vue` 使用同一套全局生命周期入口，覆盖按钮关闭、Escape、业务修改 visible、优先级抢占和组件卸载。

- 将关闭请求与最终移除分开，实际退场后再释放交接状态。
- `afterLeave` 区分永久关闭与暂时隐藏：关闭完成清理注册项；暂时隐藏只完成本次退场。
- 未曾显示的等待项可直接取消，不等待不存在的动画。
- 组件卸载明确清理其退场记录；reset 明确清理交接状态，重复回调不会造成卡住或重复关闭。
- 动画取消、快速关闭再打开时处理旧回调，不能由过时回调移除重新打开的弹窗。
- 零时长动画和减少动画设置依靠生命周期完成交接，不添加固定延时作为动画完成依据。

实现时优先把共同生命周期逻辑收敛到现有 composable；只在两种组件确有重复时增加小型共享模块。

### 3. 按父子关系保留正常嵌套

切换展示链时保留仍需要显示的共同父级，只让离开的子层退场。新增子弹窗继续以父级作为背景，关闭子弹窗后父级在退场完成时恢复交互。

全屏页面切换全屏页面、独立错误抢占父子展示链、关闭父级并清理后代均纳入验证。不能用“全局只允许一个 DOM 弹窗”的规则破坏正常嵌套。

### 4. 与既有通知队列协作

保留通知队列的优先级、去重、缓存和 2000 毫秒间隔。队列间隔继续表示既有通知节奏，全局生命周期负责实际动画交接。

- blocker 可以暂停低优先级目标，但不能让仍在退场的弹窗与新弹窗同时入场。
- 更高优先级错误仍优先于普通通知；如已有退场，等待这次退场完成后展示。
- 必要时调整队列与全局栈的接口调用，确保等待动画不会丢失通知、留下 blocker 或重复触发关闭事件。
- 更新弹窗的自动与手动入口继续复用现有业务状态；本方案不整合为新的启动通知队列。

## 实施步骤

1. 获得用户对本文的明确实施确认后，重新检查主仓库、前端及原始本地 main 状态，保留无关工作。
2. 在真实启动器中观察更新与缺失配置提示，记录事件顺序、动画状态、实际可见遮罩和模态框数量。覆盖更新先到与警告先到。
3. 添加修复前会失败的测试：动画未结束时禁止下一独立弹窗入场，同时验证暂时隐藏不产生业务关闭和更新已读记录。
4. 实现全局展示交接，接入普通弹窗与全屏弹窗生命周期，按需要调整全屏接口与通知 blocker 协作。
5. 执行针对性回归，再执行前端 CI 对应的 `pnpm check`；通过后执行 `pnpm build`。
6. 用构建后的页面实际启动 Windows 启动器，验证本次场景、父子弹窗、焦点与退出。浏览器检查可作辅助，不能替代实际启动器验证。
7. 验证通过后提交前端中文 Conventional Commit，再提交主仓库相关文档和前端指针；前端先同步原始本地 main，再同步主仓库本地 main，检查并保留无关改动。
8. 汇报提交、测试、桌面验证及限制。远程推送需用户对本次变更另行明确要求。

## 测试矩阵

| 场景 | 验证点 |
| --- | --- |
| client_id 警告先到、更新随后到 | 警告活动，更新等待；关闭及退场完成后更新出现 |
| 更新已显示、client_id 警告随后到 | 更新先退场，警告再入场；更新请求保留，警告结束后恢复 |
| 两事件同一轮到达、交换顺序 | 最终按优先级展示，独立弹窗无重合 |
| 点击关闭、稍后、确认、Escape、外部设置 visible=false | 所有关闭路径采用同一退场交接规则 |
| 退场期间再收到警告或错误 | 按最新目标展示，旧弹窗不继续处理键盘或点击 |
| 等待中的更新请求被取消 | 不出现已取消弹窗，不产生已读记录 |
| 通知队列连续多条、最后一条关闭 | 既有间隔有效，低优先级更新不会提前出现，无残留 blocker |
| 父全屏 + 子弹窗 + 孙弹窗 | 父级保留，只允许顶层交互；逐层关闭后正确恢复 |
| 独立错误抢占父子展示链、全屏切换全屏 | 独立展示链不重合，恢复关系与页面布局正确 |
| 关闭父级、卸载、reset、重复完成回调 | 后代与退场记录清理完整，无重复关闭或永久等待 |
| 快速关闭再打开、退场被取消 | 过时回调不移除重新打开的请求 |
| 动画零时长、减少动画设置 | 顺利交接，不依赖固定动画等待时间 |
| 更新下载或应用阶段被隐藏后恢复 | 业务状态连续，关闭限制保持有效，防止重复提交 |

组件测试须显式启用或控制 Transition 生命周期，检查 `afterLeave` 前后的行为，不能只断言最终 activeModalId。实际页面检查还要计入正在退场但仍可见的 DOM，确认动画期间没有独立弹窗及遮罩重合。

## 风险与收敛

- 全局模态框栈影响账户、实例、插件、用户协议及错误提示，回归范围较广；以共享机制修复并覆盖现有父子交互测试。
- 高优先级提示可能等待当前弹窗的短暂退场动画；这段等待仅用于避免视觉重合，不添加额外固定间隔。
- DOM 动画与逻辑状态可能异步变化，重点验证快速重开、未显示取消、卸载和 reset，不增设无依据的超时或兼容分支。
- 本次优先验证切换时序。若实际运行持续重合而不是动画阶段重合，记录证据后调整诊断，不能仅依据源码推测宣布修复。

## 实施结果（2026-10-10）

### 实际修改

- 全局栈分开注册请求、展示链和正在退场的记录，只在实际渲染过的旧窗口完成退场后展示新窗口；共同父级继续保留。
- 普通弹窗与全屏弹窗在首次渲染前及入场时登记，在 `beforeLeave` 绑定本次退场记录，在 `afterLeave` 完成交接。绑定具体记录可防止已卸载实例的旧回调影响后来同名实例。
- 组件卸载释放渲染记录，退场期间维持滚动与全屏布局状态，暂停弹窗交互，完成后按最新请求恢复展示和焦点。
- 新增全局生命周期与真实更新/通知组件的回归测试，更新普通弹窗与全屏弹窗测试，使其显式启用 Transition 并等待真实退场完成。
- 原有全屏接口、通知队列及 2000 毫秒间隔已经可以配合新机制，本次无需修改这些模块，也无需修改后端业务代码。

### 验证证据

1. 修复前在隔离 Windows Tauri/WebView2 中，先显示更新再送达配置缺失警告，逐帧采样记录到 8 帧两个独立弹窗同时可见，约发生在第 50 至 167 毫秒。新增对应组件测试在原实现上失败。
2. 前端 `pnpm check` 通过：153 个测试文件通过，806 项测试通过、1 项既有 todo。格式、ESLint 和类型检查全部通过。
3. `pnpm build` 通过；仍有构建分包大小提示，不影响本次功能验收。
4. 使用构建产物的 preview 服务实际启动 Windows Tauri/WebView2，经原生 Tauri 事件系统发送受控更新结果和配置缺失通知，检查更新先到、警告先到、同一轮到达、确认关闭、稍后关闭与 Escape 关闭。8 段逐帧采样均最多只显示一个独立弹窗，重合帧数为 0。被抢占的更新成功恢复，隐藏期间已读版本记录保持不变。
5. 同一构建产物实测账户全屏与添加账户子弹窗：父级保留为背景且禁止交互，Escape 关闭子弹窗后父级恢复，焦点回到添加账户按钮。独立错误抢占账户全屏及随后恢复时最多只显示一个独立展示层。
6. 将实际页面的动画时长设为 0 后验证更新/警告交接与关闭恢复成功，无残留遮罩。测试覆盖快速重开、取消等待项、卸载、reset、旧回调及父子关系；未逐项手测所有平台和业务页面。
7. 主仓库集成测试通过：1297 项通过、7 项跳过；以 `PYTHONUTF8=1` 执行，未出现先前拉取验证中的 GBK 解码警告。
