# 发布与构建流程

本项目支持 Alpha、Beta、RC 和正式版。主仓库的版本标签触发完整构建与 GitHub Release 发布，子仓库随主仓库记录的提交一起交付。

## 发布类型与标签

| 类型 | 标签示例 | GitHub 发布标记 |
| --- | --- | --- |
| Alpha | `v1.2.3-alpha.1` | 预发布 |
| Beta | `v1.2.3-beta.1+20261025` | 预发布 |
| RC | `v1.2.3-rc.1` | 预发布 |
| 正式版（Releases） | `v1.2.3` | 正式发布 |

正式版的内部类型值为 `release`。各平台使用同一份核心版本、完整版本及发布类型；带有构建元数据的完整版本原样保留。

Alpha、RC 示例不新增序号或日期限制。Beta 必须使用 `vMAJOR.MINOR.PATCH-beta.N+YYYYMMDD`，遵守以下规则：

- `MAJOR.MINOR.PATCH` 遵循语义化版本；`N` 从 1 起递增，升级基础版本后重置为 1。
- 日期使用 Asia/Shanghai 的实际发布日期，且必须是有效日历日期。
- Beta 使用带注释标签；远端版本标签均不可删除、移动、覆盖或复用。

## 日常检查与完整构建

| 触发方式 | 执行内容 |
| --- | --- |
| `main` 推送 | `Backend Tests`：后端及 Core 检查和测试；`Frontend Checks`：当前子模块的 `pnpm check`（发布门禁依赖这两项成功记录，故推送不做路径过滤） |
| 面向 `main` 的 PR | 同一组检查按改动范围执行：后端路径改动跑 `Backend Tests`，`frontend` 指针变动跑 `Frontend Checks`，依赖清单变动跑 `Dependency Review`，治理相关文件变动跑 `Engineering Governance`，纯文档改动不触发 |
| 版本标签推送 | 发布条件校验、前端构建、Windows x64/ARM64、Linux、macOS、Arch 打包与发布 |
| 手动运行 `Build` | 完整构建并上传 Actions 产物；显式选择发布时创建版本标签并上传 Release |

日常推送不执行平台打包。手动运行可选择分支或版本标签，并可填写版本号与版本类型；不填写时，分支运行使用源码中的版本常量，标签运行使用标签版本，不把分支名当版本。手动运行默认不发布，只有勾选发布且满足全部门禁时才会创建标签并上传 Release。子模块同步工作流、插件平台矩阵与原生隔离检查按各自的路径触发条件运行。

### 手动构建输入

| 输入 | 说明 |
| --- | --- |
| `version` | 不含 `v` 的完整版本，例如 `0.3.0`、`0.3.0-beta.1`；勾选发布时必填，未勾选时留空则分支用源码版本、标签用标签版本 |
| `version_type` | `auto`、`alpha`、`beta`、`rc`、`release`；非 `auto` 时必须与 `version` 一致 |
| `publish` | 是否创建版本标签并发布 Release；仅允许从 `main` 分支勾选，且必须填写 `version` |
| `design_base` | 前端设计检查的主仓库基线提交 SHA；留空与上一提交比较 |

勾选发布时，工作流按顺序校验：已填写版本号、从 `main` 分支发起、`HEAD` 等于远端 `main` 当前提交、该提交最近一次 `Backend Tests` 与 `Frontend Checks` 成功、该版本高于已发布的最新版本、同名标签在本地和远端均未使用。校验通过后由工作流创建带注释标签并推送；Beta 未带 `+YYYYMMDD` 时按 Asia/Shanghai 当天补全，已带日期时必须等于当天。标签创建后任一平台构建失败，按新版本标签重发，不删除或移动旧标签。版本号不高于已发布最高版本时会被拒绝：更新检查只从最高版本中选择，低版本发布不会被用户获取。校验结果同时写入该次运行的摘要，发布前可在运行页面核对版本、类型与是否发布。

日常检查成功不等于安装包已经验证；需要提前验包时，在 Actions 中手动运行 `Build`。完整构建仍包含现有前端检查与构建步骤；成品启动、打包后无头运行、插件依赖安装与 Worker 等测试按需单独执行。

## 发布前置条件

1. 完成所需功能、测试和验收，提交全部相关修改，保持工作区干净。
2. 按 [项目规范第 8 节](../../AGENTS.md#8-子模块指针与推送顺序)核对全部子模块指针：先推子模块，再推主仓库 `main`，确认远端均可检出。
3. 等待同一主仓库提交由主分支推送触发的 `Backend Tests`、`Frontend Checks` 成功；以各工作流最近一次运行结果为准。PR、其他分支或其他提交的成功记录不能替代。
4. 确认标签将指向远端 `main` 的当前提交，且该标签在本地和远端均未使用。Beta 另外满足日期、序号和带注释标签要求。手动发布还须填写版本号，且版本高于已发布的最新版本。

发布门禁会拒绝不支持的版本类型、指向历史提交的标签、不高于已发布最高版本的版本，以及质量检查缺失、未完成、失败或取消的发布提交；不再要求主分支完整构建的成功记录。

## 发布命令

可以推送版本标签发布，也可以在 Actions 中手动运行 `Build`、填写版本并勾选发布；两者使用同一套门禁。以下以 Beta 的标签发布为例，执行前替换为实际版本和发布日期，并确认当前会话已授权推送与发布：

```bash
git -C ECL/game push origin main
git -C ECL/services/florolding push origin main
git -C frontend push origin main
git push origin main
git status --short
git log -1 --oneline origin/main
# 等待该提交的 Backend Tests 和 Frontend Checks 成功后创建标签。
git tag -a v1.2.3-beta.1+20261025 -m "v1.2.3-beta.1+20261025"
git push origin v1.2.3-beta.1+20261025
```

不要使用 `--force`、`--tags` 或 `--follow-tags` 批量推送标签。

## 完成判定与失败处理

标签推送后等待所有平台构建和 Arch 上传完成，在 Release 页面确认预期产物均可下载。前三种发布为 prerelease，正式版为正式 Release；仅工作流启动或部分产物上传不算完成。

发布结果记录标签、目标提交、子模块指针、工作流链接、产物及已知限制。基础设施临时故障可重跑同一标签的失败任务；需要修改源码或发布配置时，修复后使用新的版本标签，不改动旧标签。严重问题可在旧 Release 标记撤回建议，再发布修正版。
