# ADR-001：降低空闲错误补查频率并测量启动阶段耗时

- 日期：2026-11-07
- 状态：提案，待用户审阅具体方案后实施。
- 范围：第一批优化；错误补查调度、后端初始化与前端运行期启动计时。
- 推荐方案：B。用户已要求开始第一批工作；本文件供实施前审阅，不表示方案已经接受或代码已经完成。

## 2. 可选方案与取舍

| 方案 | 内容 | 收益 | 代价与风险 |
| --- | --- | --- | --- |
| A：缩小改动 | 可见与隐藏状态均改为 30 秒补查；只记录后端初始化总耗时 | 降低固定查询频率，改动较少 | 隐藏时仍持续查询；总耗时不足以定位服务阶段 |
| B：按可见状态补查并分阶段计时（推荐） | 可见时 30 秒补查；隐藏时暂停定时补查；恢复可见立即补查；记录后端阶段及前端启动阶段 | 保留事件实时通知，减少空闲查询，同时得到后续优化依据 | 需要覆盖可见性、请求并发和启停生命周期；需真实桌面验收 |
| C：同时调整初始化顺序 | 在 B 基础上延后联机、插件或其他服务创建 | 可能进一步缩短显示窗口前的等待 | 暂无瓶颈数据，涉及插件、认证和联机可用时序，范围与回归风险明显增大 |

建议先接受 B。启动数据收集完毕后，再另行判断是否需要 C；不在这一批预先引入服务懒加载。

## 3. 方案 B 的具体行为

### 3.1 严重错误补查

1. 保留 `launcher:error` 事件实时入队；隐藏窗口也继续接收事件。
2. 保留前端就绪后的首次补查。这次初始化读取不属于定时轮询；即使初始化时页面隐藏，也完成一次恢复。
3. 在可见状态下，补查完成后等待 30 秒再执行下一次。用可清理的单次定时器避免慢请求与固定间隔叠加。
4. `visibilitychange` 进入隐藏状态时清除待执行定时器，隐藏期间不再由定时器发起补查。已发出的请求正常结束，避免把“停止等待”误当作“执行已取消”。
5. 恢复可见时立即补查，并恢复 30 秒调度。快速切换可见状态只保留一个定时器和一个在途请求；若切换发生在请求中，合并一次后续补查需求。
6. 查到错误后仍按现有规则入队、去重并 ACK；失败或 ACK 失败不清空后端记录，后续补查能够恢复。
7. 查询失败由异步边界处理，保持后续调度，不产生未处理 Promise 拒绝；沿用现有错误记录机制，不额外制造周期性重复日志。
8. `stop()` 清理定时器与可见性监听。启动代次失效后，旧响应不得向新会话入队、ACK 或重新安排定时器；新启动可以独立查询。
9. 展示模式不建立真实后端补查定时器。保持现有启动幂等，防止重复注册。

调度状态归 `useAppRuntime` 当前实例所有，先使用局部变量和私有函数；不为单一调用方创建通用调度框架，不新增配置字段。

在请求及时完成、持续可见且没有额外恢复事件的理想条件下，周期查询由约每分钟 60 次变为约 2 次。该数字仅描述调用频率，不代表 CPU、内存或电量将按同比例下降。

### 3.2 后端初始化计时

- 在 `create_application()` 内使用单调时钟 `time.perf_counter()`，按现有业务阶段记录耗时：配置与环境、共享资源、账户与衣柜、游戏与 Java、联机、插件、尾部装配与启动检查安排。
- 结果只存放在此次初始化的局部状态中。记录每阶段耗时和总体耗时，阶段之间明确连续边界，不重复计算嵌套总量。
- 成功时在现有初始化完成日志处记录一次结果；详细阶段使用 DEBUG，普通结果附带总耗时。中文模板只包含固定阶段名称和毫秒值。
- 失败时不输出成功摘要，保留原有异常传播和逆序资源释放；在原有失败边界增加已耗时及失败阶段上下文，不重复记录同一异常堆栈。
- 不改变服务创建顺序、插件启用方式、共享客户端、配置或返回模型，不引入服务定位器或新的公共计时框架。

这个指标叫“后端初始化耗时”：不包含 Python 导入、打包程序解压、窗口首次绘制或异步更新检测的完成时间。

### 3.3 前端启动计时

- 在 `useAppRuntime.start()` 使用 `performance.now()` 与 `performance.measure()` 记录现有等待阶段：配置预读、事件监听就绪、配置应用、版本读取、前端就绪握手、首次严重错误补查，并记录总体耗时。
- 条目使用固定的 `ecl-startup:` 前缀。重新启动前清理本模块旧条目，控制数量，不清理其他模块的性能条目。
- 指标可由浏览器或 WebView DevTools 的 Performance 条目读取。普通计时不调用 `frontend_log`，不改变现有日志级别或 IPC 类型。
- 不把已启动的异步首页预热算作已完成，不把握手结束解释为真实首帧时间。
- 后端单调时钟与浏览器单调时钟分开报告，不直接相减或相加为“完整冷启动时间”。失败、停止与重启只留下对应阶段的真实结果，不生成虚假的完成记录。

## 6. 验证计划

### 6.1 开发时的定向回归

前端覆盖以下可观察行为，测试时间由 fake timers 推进，不实际等待 30 秒：

- 首次补查发生一次；持续可见时 30 秒前不发生周期补查，达到边界后补查。
- 隐藏后推进多个周期不发起新补查；恢复后立即补查，事件推送在两个状态均可入队。
- 慢查询、频繁隐藏与恢复只保留一个在途请求，不叠加定时器；必要补查不会因请求锁被永久跳过。
- 事件与查询返回同一错误只呈现一次；查询或 ACK 失败后可以恢复，后端错误仍可重新读取。
- 停止后移除监听，旧响应不入队、不确认、不重建调度；再次启动不受旧请求锁影响。
- 展示模式、重复启动不产生真实轮询；计时条目只反映真实执行阶段，不无限累积。

后端使用单调时钟桩和已有资源桩验证正常阶段耗时、成功记录、失败时不误报完成，以及原有顺序和逆序清理。Windows 与 POSIX 条件适用时均覆盖，不要求真实联网登录。

开发用例入口：

```text
主仓库: python -m pytest tests/test_application_context.py tests/test_frontend_api_config.py::test_serious_errors_remain_available_until_frontend_acknowledges_them --tb=short -q
```

## 7. 验收标准与当前状态

- 错误仍通过事件实时送达，补查遗漏能够恢复，ACK 与去重语义保持一致。
- 隐藏期间不发生定时补查，可见周期遵循 30 秒策略，恢复和重启没有并发或资源残留。
- 可以区分启动阶段的实际耗时；不增加每秒日志、敏感数据或高频计时 IPC。
- 通过适用检查后完成本地提交与安全集成，保留其他工作区内容。

当前仅完成调查和方案文档；代码、自动化回归、性能采样与真实桌面验收均未执行。尚无证据支持具体启动加速或资源下降比例。
