# 插件依赖隔离与 `.eclplugin` 安装实施方案（待确认）

## 1. 决策与边界

- 优先保持启动器单文件发行物较小。插件首次需要独立 Python 时，按需下载并缓存由项目发布的专用运行时；同时提供可导入的离线运行时包。所有插件共享同一版本的基础运行时，每个社区插件默认拥有独立 Worker 进程。目标平台、运行时和完整依赖锁完全相同的插件可共用一个虚拟环境；其他插件使用不同环境。
- `.eclplugin` 是可检查的专用 ZIP 包，不是加密文件。它可包含插件代码、锁定的 Python 依赖和离线 wheels。没有 Python 依赖的社区插件也默认在 Worker 中运行。系统内置插件暂留宿主进程，除非后续单独迁移。
- 本期不做 Ed25519 签名或验签，`.eclplugin` 不提供作者身份或来源证明。安装器只检查归档结构、文件哈希与依赖哈希；所有插件包均按“来源未验证”展示明确警告，并经用户确认后允许安装。哈希能检查包内数据是否与清单一致，不能防止他人同时替换文件和清单，也不是插件权限沙箱。签名能力留待后续单独设计和版本升级。
- 现有 `plugin.json.dependencies` 继续表示插件间依赖。新增独立的 `pythonDependencies` 字段，仅描述 Python 包的直接依赖；实际安装以包内完整锁文件为准。
- 原先可选主进程模式只作为用户显式选择的兼容模式：不自动回退，不向宿主安装插件 Python 依赖，并明确提示它不提供依赖隔离。旧的 `docs/plugin-worker-isolation-implementation-plan.md` 是以权限和资源限制为目标的历史草案，不作为本方案的实现依据。

## 2. 当前实现与影响面

| 当前情况 | 需要改变的边界 |
| --- | --- |
| `ECL/plugins/manager/lifecycle.py` 只安装目录，覆盖时先删除旧插件，失败不能恢复旧版 | 统一安装事务、版本化存储、原子切换与回滚 |
| `ECL/plugins/manager/discovery.py` 在宿主进程 `exec_module` | 默认启动每插件 Worker，不把插件的依赖导入宿主解释器 |
| `ECL/plugins/dependencies.py` 仅解析插件间关系 | 保留原语义；Python 依赖走独立锁文件与环境管理器 |
| `ECL/plugins/plugin.py` 直接持有 `framework`，并向认证、联机、启动钩子等注册表传递回调 | SDK/宿主代理，将注册和回调参数转换为显式数据协议 |
| `ECL/api/plugins.py`、`ECL/services/dev_channel.py` 共用 `PluginManager.install`；前端只选择目录 | 预检、确认、进度、取消、错误和包文件入口共用同一安装服务 |
| Windows/Linux 主要使用 Nuitka onefile，macOS 使用 PyInstaller `.app`；发行物未提供普通 Python/pip | 独立运行时资产、按需获取、稳定缓存目录与真实发行物冒烟测试 |
| `ECL/common/runtime.py` 默认把 `ECL_data` 放在可执行文件附近 | 插件代码、环境和运行时应放在启动器数据目录下，且该目录必须跨平台可写；尤其不能写入只读 macOS DMG 或 onefile 临时解压目录 |

## 3. 交付物与文件契约

### 3.1 运行时资产

CI 对现有目标平台分别生成项目控制的 `plugin-runtime` 资产，包含固定补丁版本的 CPython、固定版本的 `uv` 和项目的 Worker SDK。使用独立、可审计的运行时资产清单记录目标平台、Python ABI、版本、大小和 SHA-256；启动器构建时固定对应资产的版本及摘要，不从可变的 `latest` 地址获取可执行文件。

在线首次使用时，后台按固定版本地址下载到部分文件，校验大小和摘要后解包到用户可写、持久的版本化目录。离线导入入口接受 CI 发布的同一资产并执行同样的校验。下载失败、校验失败或磁盘不足不得改变已安装插件状态。下载、解包和安装均有超时、上限、取消与可观察的阶段状态。

运行时资产与插件环境分开维护。所有状态置于 `get_runtime_info().data_path` 下，建议布局为 `plugin_runtimes/<runtime_id>/`、`plugin_envs/<environment_key>/`、`plugin_cache/`、`plugin_packages/<plugin_id>/<package_digest>/`；插件设置和用户数据仍单独保存。`ECL_DATA_PATH` 继续可将开发环境重定向到独立沙箱。默认数据目录在 Windows、Linux、macOS 上必须可写；若当前默认位置不可写，先解决数据目录定位和旧数据迁移，不把环境偷偷放到另一处，也不删除用户现有 `ECL_data`。

更新 CPython 构建或 ABI 时，先保留旧运行时，逐个重建受影响的环境并验证；仍被旧环境引用时不得清理旧运行时。

### 3.2 插件归档 v1

建议固定如下顶层结构，准确字段和版本号在实施时通过测试固化：

```text
example.eclplugin
  plugin.json                 # 插件 ID、版本、入口、API 版本、插件间依赖、Python 直接依赖
  package-manifest.json       # 格式版本、目标平台/ABI、全部载荷文件的路径/大小/SHA-256
  main.py, resources/...     # 插件代码及声明的资源；入口路径沿用当前 plugin.json 约定
  locks/<target>.txt         # 当前目标完整传递依赖，精确版本与 wheel 哈希
  wheels/<target>/*.whl      # 可选的离线 wheel，不包含源码构建包
```

打包工具负责生成确定性文件列表、锁文件与 wheel 哈希。安装器不能仅相信扩展名：先限制压缩包总大小、展开大小、单项大小、文件数和压缩比，再拒绝绝对路径、`..`、符号链接、重复名称及大小写折叠后冲突，要求归档实际载荷文件集合与 manifest 完全一致。载荷文件哈希在解压落地前完成验证；清单及锁文件本身不具有可信作者签名，不能据此声称包未被第三方重新制作。

归档 v1 不定义签名字段或 `package-signature.json`；若出现声称已签名的元数据，按不支持的格式拒绝，避免被误认为已验签。预检与插件详情始终显示“来源未验证”，不展示作者指纹或签名状态。安装同名插件新版本仍需展示版本变化并再次确认。文件与清单不一致、未知格式版本或缺少兼容目标直接拒绝。

### 3.3 依赖锁定

每个支持的目标平台和 Python ABI 使用独立的、包含全部传递依赖的哈希锁定文件；锁文件中只接受精确版本与允许的 wheel 摘要。允许包内只覆盖部分平台，但 UI 必须在安装前明确显示当前平台是否可用。安装器仅安装与实际 Worker 运行时兼容的 wheel，不从源码构建，也不静默改用其他平台或系统 Python。

安装顺序为：检查已验证的包内 wheels 和共享下载缓存；尝试离线安装；若有缺失且用户允许联网，则只下载锁文件允许的 wheel 并逐一校验摘要；最后从已验证的本地 wheel 集合安装。网络失败、无兼容 wheel 或哈希不符时停止，保留原插件。代理、镜像和超时策略与启动器配置保持一致，但镜像不能改变锁定的内容摘要。共享下载缓存仅存放按哈希验证的下载物；可在同一文件系统上使用 `uv` 支持的硬链接或写时复制复用依赖文件，跨文件系统或不支持时退回复制，不以符号链接把已安装环境绑定到可清理的缓存。

## 4. 默认隔离运行与兼容性

社区插件默认经所选虚拟环境的 Python 启动自己的 Worker。每个 Worker 独立拥有 `sys.modules` 和原生扩展进程状态；宿主只保留插件元信息和代理注册项。基础 CPython 可共享，虚拟环境仅在完整依赖锁相同的插件间共享，不能把两个不同锁文件里的依赖合并成一个环境。环境只能在最终的版本化路径创建，不通过移动临时 venv 完成发布，因为虚拟环境中的路径可能是绝对路径。

`environment_key` 根据运行时构建 ID、目标平台/ABI、Worker SDK 版本及当前目标完整锁文件的原始字节摘要生成，不包含插件 ID。空依赖锁也可对应一个共享环境。插件代码、配置、数据和临时文件都不得安装进共享 venv。环境一旦验证并标记可用就不可由安装器原地 `sync`；依赖变化创建新环境，仅切换受影响插件的环境引用。活动版本和可回滚版本都计入引用；重启后从持久状态重建引用关系，只有无引用且无 Worker 使用的环境才可回收。共享环境减少空间占用，但不把具有相同锁的插件当作同一个进程，也不承诺抵御插件主动篡改本地环境文件。

Worker 与宿主使用 Windows 命名管道或 Unix 域套接字上的有界结构化消息；协议包含版本、请求 ID、超时、最大帧大小和明确的关闭流程，不传输任意 Python 对象或使用不可信 pickle。宿主完成插件注册、事件分发、前端资源提供和业务服务调用；Worker 通过稳定的 SDK 请求这些能力。此 IPC 只为兼容性和故障隔离，不宣称能限制插件读取剪贴板、文件或网络。

迁移清单必须逐项覆盖：生命周期、命令、设置、事件、路由与前端 CSS/JS/Vue 资源、实例兼容读取、联机扩展、游戏启动钩子、自定义认证、崩溃分析；同步回调需要有界超时和明确失败策略。现有插件可能直接访问 `framework` 内部对象，不能假定代理完全兼容。默认 Worker 启动失败时不静默切回主进程；用户只能显式选择兼容模式，且不得把托管 Python 依赖装进宿主环境。系统内置插件不进入本期自动迁移范围。

## 5. 安装事务与用户流程

1. 从 `.eclplugin` 或开发用目录执行预检。目录安装仍保留给开发工具，但显示未封装状态；正常发行安装以归档为主。预检返回插件信息、目标兼容性、`unverified_source` 标记、依赖数量与预计下载量，不执行插件代码。
2. 前端展示确认界面。所有包的来源未验证警告、需要联网获取依赖、需要首次下载运行时分别明确提示；继续安装必须显式确认未验证来源。Dev Channel 的无人值守安装也必须传入对应的显式确认参数，不能默认跳过。下载与环境创建用统一进度状态显示，并可取消。
3. 安装服务按插件 ID 和环境键加锁；验证后把代码放入未激活的插件版本目录，并查找同环境键的已验证虚拟环境。没有命中时在最终 `plugin_envs/<environment_key>/` 路径创建新环境；同一环境键的并发安装只创建一次，未完成的目录不能被复用。不可通过复制/重命名已创建的 venv 激活版本。
4. 安装锁定依赖，启动未公开注册项的 Worker 做握手与导入/生命周期验证。成功后原子更新活动版本指针，切换注册项和 Worker，保持原有启用/禁用状态；失败则清理未激活版本并继续使用旧版。插件自身对外部系统产生的副作用不在安装器回滚范围内，预检阶段绝不执行插件代码。
5. 卸载时终止 Worker、撤销宿主注册并更新活动状态；清理历史版本、共享环境和缓存采用引用检查及单独的有界后台任务。卸载一个插件不能删除仍被其他插件或可回滚版本引用的 venv。启动器关闭时必须回收所有 Worker。中断、断电后的下次启动根据活动指针恢复，不加载半成品目录。

前端插件页需同时提供“安装文件”和“安装目录”入口，展示来源未验证/依赖/运行时/安装失败信息；正式 IPC 与 Dev Channel 共用相同的安装服务和错误码。安装、下载、解包、环境创建等阻塞任务不得直接运行在 async 事件循环上。

## 6. 分阶段实施

1. **可行性门槛**：在 Windows x64/ARM64、Linux x64、macOS 当前发布架构以及 Arch 包中，验证专用 CPython、`uv`、纯 Python wheel 和原生扩展 wheel 可运行；证明 onefile/macOS 的稳定可写目录和运行时资产交付。任一正式平台无法通过时先调整发行方案，不宣称隔离功能完成。
2. **协议与制作工具**：定义无签名的归档 v1、目标/锁文件规则和作者打包 CLI；补充独立规范文档和恶意/损坏归档测试。Ed25519 不进入本期交付。
3. **运行时与安装事务**：下载/离线导入、持久缓存、环境创建、在线补齐、版本切换、恢复与卸载；把目录安装纳入相同事务基础设施。
4. **Worker 与 API 迁移**：实现 SDK、IPC、所有现有扩展点代理、关闭与失败处理；逐类迁移测试插件。系统插件继续走现有宿主路径。
5. **UI 与集成**：文件选择、未验证来源确认、进度与错误展示；Dev Channel 与前端契约同步；更新示例与开发文档。
6. **发布验证**：在真实冻结发行物安装相互依赖版本冲突的两个插件、含原生扩展的插件、包内离线 wheel 插件及在线补齐插件，再进行更新失败回滚和重启恢复测试。

以上阶段可分提交交付，但未覆盖全部现有插件扩展点并通过发行物验收前，不能把默认 Worker 隔离标记为完整上线。旧主进程模式的能力边界要在 UI 和文档中如实呈现。

## 7. 测试与完成标准

- 单元/集成：未验证来源必须显式确认、声称签名的 v1 包被拒绝、修改载荷却不更新清单被拒绝、篡改锁或 wheel 与清单不一致被拒绝、路径穿越、重复文件、压缩炸弹、错误 ABI、缺少 wheel、网络中断/取消、重复安装与并发安装。测试须明确证明攻击者同时改写文件及无签名清单时无法建立作者身份或来源保证。
- 隔离与共享：两个插件安装冲突版本的同名库并分别读到自己的版本；锁完全相同的两个插件共用同一 venv 但使用不同 Worker；只有依赖兼容、锁却不同的插件仍使用不同 venv；同环境键并发安装只创建一次；卸载其中一个不删除共享环境。一个插件崩溃、禁用或卸载不影响另一个；原生扩展可导入；宿主 `sys.modules` 不出现插件依赖。
- 回滚：首次安装失败不留下活动插件；更新失败后旧版代码、环境、禁用状态和注册项保持可用；断电残留不参与发现；运行时升级期间旧环境仍可启动。
- 插件契约：当前所有注册表/扩展点的成功、超时、异常、清理与重新启用路径都有覆盖；明确记录无法迁移的旧插件行为。
- 发布矩阵：后端执行 `ruff check ECL tests`、`ruff format --check ECL tests` 和相关 pytest；前端执行 `pnpm check`、`pnpm build`，然后实际启动启动器；各平台发行物验证在线运行时获取、离线运行时包导入、离线/在线 wheel 安装、正常重启和卸载。主仓库与前端子模块依各自规范分别提交，不在未经授权时推送。

## 8. 尚需在实施前确认的产品细节

- “保持单文件较小”意味着全新机器完全断网时，只有 `.eclplugin` 和 wheels 仍不足以启动 Worker；还需预先缓存或另行导入匹配的离线运行时包。本方案提供该入口，但不把运行时塞入主程序。
- 开发用目录插件默认走 Worker；依赖旧 `framework` 内部对象的插件需要显式兼容模式或改用新 SDK。不会在 Worker 失败时偷偷回退到主进程。
- 本方案不新增剪贴板、文件、网络等 OS 权限限制；本期哈希仅检查包内一致性，进程/环境解决依赖冲突，不提供作者身份或恶意插件安全承诺。
