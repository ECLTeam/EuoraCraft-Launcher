# ADR-005：扩展桌面启动参数、排障与无头自动化

- 日期：2026-11-08
- 状态：用户已批准实施，第一批桌面参数完成；继续第二至四批
- 决策者：用户选择全部三个方向；具体契约由本方案提交审阅
- 范围：日常快捷启动、开发排障、脚本自动化，包含真正的无头游戏启动

## 1. 背景与当前实现

用户已选择同时拓展三个方向。本次先完成需求分析与实施方案，不将方向选择视为对尚未展示的具体实施文档的批准。

调研时主仓库位于本地 `main`，主仓库和两个子模块工作区均干净。主仓库记录的 Core 为 `09080a49857c2e9fff271dc1a73d3e710bfcd026`，前端为 `77b027291639d9187dfc16dacec115e742266977`。这些仅为调研基线，实施前重新确认。

当前事实与设计依据：

1. `ECL/cli.py` 已支持桌面快捷启动、游戏设置覆盖、页面打开、插件开发和有限无头任务。游戏参数已有“全局 → 实例 → 本次显式参数”的合并规则，追加 JVM、游戏参数沿用现有语义。
2. `ECL/bootstrap.py` 在业务导入前分流桌面、普通无头任务、插件 Worker 与 guardian。普通无头任务当前仅支持 `runtime-check`，不能启动游戏。
3. `ECL/runtime/contracts.py` 的结果协议为版本 1，任务数据固定为 `probe`；`tasks.py`、`headless.py` 的执行与日志也只面向环境检查。
4. `ECL/api/bridge.py` 在前端就绪后排队执行桌面快捷启动。`ECL/host/single_instance.py` 转发页面和启动请求；转发成功仅表示接收，不能证明游戏已经启动。
5. `AccountManager.get_launch_credentials()` 当前只读取全局选中账户；`switch_account()` 会保存选中状态，不能用“切换后再切回”实现单次启动账户。
6. `ECL/application.py` 创建账户、Java、游戏、插件、后台媒体、启动更新等服务，不能直接作为只读任务的初始化方式。实际账户根还可能位于用户目录下的 `.ECL/accounts`，不同 `--data-dir` 不代表账户存储隔离。
7. 插件临时禁用必须和持久禁用集合区分，且覆盖发现、装载、启用、重载、依赖和开发监听入口。
8. 前端语言来自 `ui.locale`，支持 `zh-CN`、`zh-TW`、`en-US`、`ja-JP`、`ru-RU`、`de-DE`。现有前端 `setLocale()` 会写回设置，不能直接用于临时语言覆盖。
9. `--open-page` 的前端消费方位于 `frontend/src/app/runtime/useAppRuntime.ts`。Java 和插件已有页面；账户管理由游戏页的全屏弹窗承载，不新增账户路由或另建界面。
10. Java 与实例已有只读查询设施，例如 `JavaQueries`、`InstanceQueryCoordinator`、`InstanceReadBoundary`，应复用其领域规则；部分设施仍依赖拥有状态的服务，需提供明确的只读构造边界。

相关现行文档：[命令行说明](guides/launcher-cli.md)、[无头运行说明](guides/headless-runtime.md)、[项目规范](../AGENTS.md)、[前端规范](../frontend/AGENTS.md)。旧方案仅作历史参考，实施位置以当前源代码为准。

## 2. 选项、选择与影响

### 选项一：只扩展日常桌面参数

交付快，便于快捷方式使用，但不满足本次全部范围。

### 选项二：只增加排障与只读脚本任务

自动化边界较小，但不能完成无 UI 游戏启动，也不满足全部范围。

### 选项三：三个方向全部纳入，按依赖分批交付

采用此选项。先完成桌面契约与单次账户，再完成只读业务入口，最后交付无头游戏进程监管；分批提交不删减最终范围。

- 正面：桌面、排障和脚本共享账户选择、实例定位与有效启动设置，避免多套行为。
- 代价：涉及认证、跨进程并发、生命周期、前端启动与内部协议，需要完整检查及真实原生验收。
- 风险：临时覆盖落盘、检查触发写入、账户串用、取消后仍创建游戏、脚本退出后留下无人监管进程。
- 控制：分离持久配置与有效配置；显式账户快照；按任务最小装配；实际进程确认退出；增加覆盖这些行为的回归。

## 3. 桌面参数契约

| 参数                        | 行为                                                            | 适用范围                                |
| --------------------------- | --------------------------------------------------------------- | --------------------------------------- |
| `--account <账户ID>`        | 为本次启动绑定已有账户；ID 不存在或不可用时失败，不改用默认账户 | 桌面 `--launch`，无头启动检查与游戏启动 |
| `--start-minimized`         | 主窗口首次就绪后最小化，不请求前台焦点；保留恢复入口            | 仅新桌面进程                            |
| `--language <代码>`         | 临时覆盖界面语言；代码限现有六语言                              | 仅新桌面进程                            |
| `--disable-plugin <插件ID>` | 可重复，去重；本次进程禁止装载和启用指定插件                    | 桌面进程、无头 `launch` 任务            |
| `--open-page <名称>`        | 在已有名称外增加 `accounts`、`java`、`plugins`                  | 桌面及单实例转发                        |

详细规则：

- `--account` 属于单次启动输入，不属于会话当前账户。未指定时沿用现有默认选择；显式指定时只使用该账户。命令行不接收密码、令牌或账户文件作为凭据。
- 补充 `list-accounts` 无头任务，供脚本取得可用于 `--account` 的真实账户 ID；不创建另一套账户标识。
- 所选账户绑定在启动请求及其领域输入中；凭据刷新、认证提供方复核和进程创建前校验都核对同一账户。不能通过修改 `_current_account_id` 或调用 `switch_account()`实现。
- 有效令牌刷新可按原账户服务契约原子保存凭据，这与改变默认账户不同；失败保留原凭据文件。只读检查不刷新令牌。
- 临时语言独立于持久化 `ui.locale`：读取有效配置时应用覆盖，保存其他 UI 设置时不得把覆盖值带回文件。用户在设置中主动保存语言时保存其明确选择，本次进程仍服从显式参数；前端显示覆盖来源，避免保存后界面无解释地恢复。
- 为保持 `--language` 仅影响启动器，游戏初次语言初始化使用持久界面语言及既有环境配置，不消费本次 CLI 语言覆盖；已有游戏语言保持不变。
- `--start-minimized` 与游戏启动成功后的 `--launcher-visibility` 分别执行；启动失败保持可恢复，失败信息排队保留，不自动抢焦点。主窗口显示和首次 focus 由原生宿主统一协调，避免先置前再最小化。
- `accounts` 导航到游戏页并打开现有账户全屏弹窗；`java` 对应现有 Java 设置页；`plugins` 对应现有插件页。重复请求不得叠加弹窗，初始页面选择应先于相应页面恢复逻辑完成。
- `--open-page` 继续与 `--launch` 互斥。账户、游戏设置等仍须有启动目标，不为无目标输入静默忽略参数。
- 全部会话覆盖都不写回全局、实例或插件持久偏好，不新增旧字段别名与迁移。

### 3.1 插件临时禁用

- 独立保存不可变的会话禁用 ID 集合，由插件管理器统一维护生效规则，不写入持久禁用列表。
- `--disable-plugins` 继续采用现有全部停用语义；指定插件与全部停用同时出现时不会恢复任何插件。新增定向禁用在本次运行期间不可从界面、IPC 或开发热重载重新启用。
- 只读取元数据即可判定目标；已知但停用的插件显示原因。ID 不存在时明确报错，不执行该请求；不得加载 Python 入口来验证 ID。
- 被停用插件的必要依赖方也不得启动，并显示依赖阻断原因；可选依赖沿用现有契约。禁用不改变权限、临时信任、审阅状态或账户提供方绑定。
- 安装同 ID 插件、重载、Worker 重启和开发模式监听均遵守同一会话限制。
- 如果所选账户依赖被停用提供方，启动明确失败，不替换账户、不绕过授权。

### 3.2 已运行桌面进程

| 输入                                                  | 已有同数据目录桌面进程时的处理                                        |
| ----------------------------------------------------- | --------------------------------------------------------------------- |
| `--launch` 及其 `--account`、游戏覆盖                 | 使用既有认证单实例通道转发，队列保留每次请求的账户身份                |
| `--open-page`                                         | 转发既有页面动作，前端就绪前排队，关闭时拒绝                          |
| `--start-minimized`、`--language`、`--disable-plugin` | 进程级输入，拒绝修改已有进程，提示重启；不将请求当普通 focus 成功处理 |
| 既有插件开发等进程级输入                              | 保持现有拒绝规则                                                      |
| 普通无头任务                                          | 独立执行，不唤醒窗口；有写入的无头游戏任务按第 6 节处理冲突           |

同目标不同账户的请求不得被合并；同一请求在排队和执行阶段继续去重。主实例拒绝转发时第二进程不能继续变成共享目录的另一个写入者。

## 4. 无头任务与输入矩阵

保留 `--headless --task <任务>` 结构，所有任务完成后退出。新增任务：

| 任务             | 输入                                               | 结果及副作用                                                                                    |
| ---------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `runtime-check`  | 沿用当前输入                                       | 原有代表性依赖与运行环境检查，不读业务文件                                                      |
| `list-instances` | 可选 `--game-dir`，否则读取配置中的游戏根          | 有界列出实例 ID、名称、游戏版本、加载器、游戏根和实例目录；不创建配置、统计或监听               |
| `list-java`      | 读取已登记 Java 与常规扫描来源                     | 返回已登记及本次识别的 Java，包含路径、版本、架构、来源和状态；不安装、清理、登记或保存探测结果 |
| `list-accounts`  | 读取实际账户存储                                   | 返回账户 ID、展示名、类型和默认选择状态；不联网刷新、不加载认证插件、不输出凭据                 |
| `launch-check`   | `--launch`，可选账户与游戏设置覆盖                 | 检查目标、有效设置、所选 Java、账户本地状态和必要文件；输出设置来源与阻断项                     |
| `check-instance` | `--launch`，可选 `--game-dir`                      | 按本地元数据核对版本继承、Jar、依赖库与资源的缺失/损坏情况；不下载、不自动修复                  |
| `diagnostics`    | 默认仅环境；可选 `--launch` 收集指定实例的有限摘要 | 输出可分享的白名单诊断结果，不包含完整路径、账户 ID/展示名/UUID、凭据、环境变量或原始配置/日志  |
| `launch`         | `--launch`、可选账户和游戏设置；可选插件禁用参数   | 实际准备并启动游戏，持续监管至游戏退出后交付最终结果                                            |

任务专属规则：

1. `--data-dir`、`--result-file`、`--debug`、`--log-level` 沿用；每个任务单独声明允许参数，不能因扩展任务而对所有无头任务放开所有桌面参数。
2. 无头 `--launch` 表示任务的实例目标，动作由 `--task` 决定。`--game-dir` 在列表任务中可以独立使用；在启动、检查任务中沿用版本名与完整实例目录的互斥规则。
3. `--account`、Java/内存/窗口等覆盖供 `launch-check` 和 `launch` 使用；`--server`、`--world` 也在这两个任务校验，实际直达只发生于 `launch`。不适用参数返回用法错误。
4. `--disable-plugin`、`--disable-plugins` 仅供无头 `launch` 的实际插件运行使用；只读检查通过元数据判断提供方状态，不启动插件或运行启动钩子。所有普通无头任务拒绝 `--plugin-dev`、`--dev-channel`、`--frontend-dist`、`--webview-debug-port`、`--open-page` 和 `--start-minimized`。
5. 检查任务不执行游戏、插件钩子、前后命令、下载、更新、语言/全屏文件写入或用户维护任务。不允许“执行真实启动后在创建进程前停下”冒充只读预检。
6. Java 探测允许启动有超时的 Java 信息查询子进程；取消与超时后必须确认探测进程结束。`list-java` 不等于安装或登记 Java。
7. `launch-check` 不联网、不验证在线令牌有效性。结果明确区分 `passed`、`blocked`、`not_checked`；插件动态结果、在线认证、远程资源可达性标记未检查，不能描述为完整启动保证。
8. `check-instance` 仅对本地元数据声明且有可靠大小或摘要的文件作验证。缺少远端索引/元数据时报告检查不完整，不能以未知当通过，不额外遍历用户存档或无关文件。
9. 枚举任务允许有效空列表；文件损坏、读取失败与不支持格式返回明确失败，保留原文件，不伪装为空列表。配置文件缺失使用领域默认值的只读副本，不创建文件。
10. 列表结果供本机脚本使用，允许上述必要路径及账户展示字段；诊断任务是不同的显式白名单投影，不直接打包列表结果。人类日志仍不输出隐私路径或账户信息。
11. 列表输出确定排序。实例使用现有版本 ID 加游戏根定位，不创造不可回用于启动的临时 ID；同名实例保留不同根，并由脚本提供返回的完整实例目录或 `--game-dir`。
12. 检查发现阻断或覆盖不完整时保留结构化发现，返回非零最终退出码；预检状态和程序异常分别表达，不丢失可用证据。

示例（批准并实施后才可用）：

```powershell
python main.py --launch '1.21.1' --account '<已有账户ID>' --memory 6144
python main.py --language en-US --start-minimized
python main.py --disable-plugin '<插件ID>' --open-page plugins
python main.py --open-page accounts
python main.py --headless --task list-instances --game-dir 'D:\我的游戏'
python main.py --headless --task list-java
python main.py --headless --task list-accounts
python main.py --headless --task launch-check --launch '1.21.1' --game-dir 'D:\我的游戏'
python main.py --headless --task check-instance --launch 'D:\我的游戏\versions\1.21.1'
python main.py --headless --task diagnostics --result-file '.\diagnostics-new.json'
python main.py --headless --task launch --launch 'D:\我的游戏\versions\1.21.1' --account '<已有账户ID>'
```

## 5. 结果协议、失败与输出

当前私有协议只支持固定 `probe`。本次升级到结果协议版本 2，以 `data` 承载有明确类型的任务结果，移除旧 `probe` 字段，同步更新所有源码、冻结产物测试与文档，不双格式输出。

所有任务统一结果字段：`protocol_version`、`task`、`success`、`error_code`、`message`、`data`。每个任务结果使用 dataclass 或 Pydantic 模型与显式联合类型，不以 `dict[str, Any]` 作为内部业务模型。

- 环境结果、列表结果、检查发现、诊断摘要和游戏运行结果分别建模；查询和诊断不返回原始服务对象。
- `launch-check` 包括选定目标、有效启动设置及各设置来源、账户可用性摘要、检查状态和阻断项；不得返回凭据、账户原始持久数据或完整启动命令。
- `launch` 包括是否实际创建游戏进程、最终游戏退出码和结束原因；路径与账户信息按最小需要投影，游戏 stdout/stderr 不混入结果 JSON。
- stdout 仅输出一次最终 JSON；人类日志与采样进度写 stderr。指定 `--result-file` 时 stdout 保持安静，继续原子输出、拒绝覆盖已有文件及符号链接；参数错误不生成结果文件。
- 无可用结果通道时，在执行有副作用任务前失败；中途输出失效按实际执行状态报告失败，不把游戏已经结束等同于结果已交付。
- 退出码继续采用 `0` 成功、`1` 执行/检查/游戏/输出失败、`2` 参数错误、`130` 用户取消且实际停止；游戏原始退出码放在 `data`，不直接挤占命令行退出码。
- 预期业务失败复用账户、实例和 Java 的稳定错误码；新增无头冲突、交互缺失等错误在契约中集中定义，并同步文档。异常消息、堆栈和第三方输出经过现有脱敏设施。
- 业务日志由实际执行服务负责；CLI 只补无服务结果的输出失败、入口校验等结果，不能重复记录服务失败。
- `runtime-check` 的不读取业务文件、不导入 UI/业务服务、不创建目录、不通知桌面的行为保持；其结果数据位置按版本 2 更新。

## 6. 无头游戏生命周期与并发

### 6.1 装配与进程归属

- `--headless --task launch` 不导入 Tauri、WebView 或前端 IPC handlers，不依赖 `frontend_ready`。使用独立的业务装配函数，仅创建账户、网络、Java、操作执行器、游戏进程及必要插件服务。
- 从桌面入口和 `GameHandlers.game_launch` 中提取确有重复的“目标解析、有效设置计算、启动输入转换”到游戏领域的普通函数/明确输入模型，实际调用方为桌面 CLI、界面启动、无头预检与无头启动；不新增通用命令框架、服务定位器或空转发类。
- 认证、文件补全、命令构造、实例进程和取消复用现有游戏服务。无头启动允许正常启动所需的网络访问、凭据刷新、文件补全、实例统计及配置中已有的前后命令，其副作用在使用文档明示；不执行桌面启动更新和调试维护任务。
- 无头进程作为本次游戏的监管者，保持运行直到游戏实际退出，之后完成日志、退出回调、Java 使用保护和资源清理，再输出最终结果。不增加默认脱离监管或后台常驻模式。
- 游戏非零退出使任务失败，同时保留实际游戏退出码。游戏窗口显示与启动器无 UI 是两件事；默认仍启动正常 Minecraft 客户端窗口。

### 6.2 账户与插件

- 对已有离线、Microsoft、Authlib/LittleSkin 账户沿用其实际支持契约，允许已有凭据刷新。需要重新登录、设备码或选择角色时明确返回交互需求，不打开浏览器或阻塞等待用户输入。
- 插件账户与启动钩子沿用既有审阅、内容绑定和权限契约。只装配与无头任务相容的运行能力，不自动批准、不恢复上次临时信任，也不把无窗口当作授权。
- 必需插件/认证提供方尚未批准、要求 UI 或窗口能力、或当前无头宿主不能提供其必要能力时，明确阻断；不能静默忽略必需钩子或转成其他账户。可选钩子依现有契约处理并给出必要摘要。
- 插件 Worker 继续走已有 `--headless --role plugin` 与 guardian 分流；普通任务绝不接收任意 Python 脚本、模块名或 Worker 连接参数。

### 6.3 共享状态和冲突

- 只读任务可与桌面并行，使用原子文件快照和有界读取；不能创建发现文件、共享日志轮转、注册表缓存或迁移文件。读取期间数据变更无法形成一致快照时明确失败或要求重试。
- 有副作用的无头启动遇到同数据目录已运行桌面或另一个无头启动时返回 `HEADLESS_RUNTIME_BUSY`，不转发到 UI，也不启动第二个写入者。
- 在桌面和无头业务装配前取得同数据目录的跨进程运行锁：桌面持共享占用，无头有副作用启动持独占占用，使用平台系统锁，归属随进程退出释放；桌面之间是否转发仍由现有单实例设置决定，不把该设置改为永久强制单实例。不能仅凭“发现文件不存在”或 PID 存活检查实现互斥。普通只读探测不持有该锁。
- 不同数据目录可能指向同一实例和账户根：实际实例启动/准备边界增加按规范实例目录归属的跨进程占用保护，防止并发修改同一个实例；锁覆盖实际游戏运行至收尾。
- 账户持久化按真实账户存储根复用/补充短周期跨进程读改写锁，在锁内重新读取并原子提交，防止不同数据目录刷新共享账户时丢失变更；不以长时间网络请求占用账户文件锁。
- 并发保护不通过关闭已有桌面、终止其他游戏、删除用户数据或新建历史扫描流程实现。遇到冲突报告原因，由用户重试。

### 6.4 取消、超时和退出

- Ctrl+C、POSIX SIGTERM 和可用的 Windows 控制台中断统一进入现有取消流程；排队/准备阶段取消后禁止创建游戏进程。
- 创建进程与取消竞争时，取消必须覆盖刚创建的本次游戏，确认实际退出后才返回 `130`；只终止本次任务拥有的进程及受监管子进程。
- 运行阶段取消先请求正常停止，再在有界宽限后终止仍存活的本次进程。Python task 取消、线程超时和等待超时不能冒充底层进程已经停止。
- 网络沿用有界超时，Java 探测和本地扫描有共同预算；实际游戏运行时长不设置任意默认上限。新建线程、探测进程、Worker、监听和订阅均有明确释放归属。
- 关闭顺序为停止接收任务、请求取消、等待实际执行结束、游戏退出收尾、插件退出、服务关闭、释放运行锁；异常路径同样幂等清理。
