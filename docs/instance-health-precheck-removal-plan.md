# 移除实例健康预判及启动限制实施方案

状态：用户已确认开始实施；整套移除、自动检查和 Windows 桌面验收已完成。

## 目标

移除实例扫描阶段新增的健康预判及由其派生的界面和选择限制。实例可以继续通过首页、实例列表、详情页、快捷方式和命令行进入正常启动流程，避免预判主 Jar 或元数据布局错误导致启动入口不可用。

验收重点是用户报告的 `26.4-snapshot-3`：扫描阶段不再生成“缺少主 Jar”提示或因该诊断将实例判为不可启动。测试使用这一版本名称及不同文件布局构造回归，不把它的具体安装内容假定为已知。

## 当前实现与影响

- 主仓库 `b094a2f` 首次引入健康诊断，随后移入 Core 的 `Data/instance_health.py`。
- `InstanceInspection.inspect` 检查 JSON、继承链和主 Jar，`to_health()` 将结果转换为 `health` 与 `canLaunch`。
- 主仓库 `ScanCoordinator._normalize_scanned_version` 返回 `health` 及 `isBroken`，把诊断严重程度转换为前端启动限制。
- 首页 `GameLaunchBar.vue` 根据 `isBroken` 禁用启动按钮，`useInstanceManager.ts` 在提交启动前再次拦截。
- `InstalledInstanceList.vue` 隐藏被标记实例的启动入口；`InstanceDetailOverviewTab.vue` 禁用启动按钮，并显示健康诊断。
- `useResourceInstallTarget.ts` 将 `isBroken` 实例排除出资源安装候选。
- `InstanceInspection` 同时提供加载器组件、继承元数据、Java 要求和模组运行环境，直接删除整个模块会影响这些读取功能。
- `WorkspaceCoordinator.inspect_instance_files` 与启动时文件补全属于现有文件检查/修复流程，与扫描阶段健康预判有独立职责。

## 方案比较与建议

| 方案 | 内容 | 权衡 |
| --- | --- | --- |
| 1：整套移除，建议采用 | 删除健康诊断、协议字段、文案及相关启动/候选限制，保留必需的元数据读取 | 覆盖这套预判引起的全部影响，涉及 Core、主仓库和前端 |
| 2：仅移除主 Jar 判定 | 删除 `_inspect_jar` 与 `missing_jar`，其余诊断及限制继续生效 | 改动较小，其他健康预判仍可能禁止实例启动 |

本文按用户倾向“最好移除”细化方案 1。若用户选择缩小范围，实施前调整本文。

## 具体改动

### 1. Core：将必需功能收敛为只读元数据解析

- 移除 `InstanceDiagnostic`、健康严重程度、主 Jar 检测和 `to_health()`。
- 将 `instance_health.py` 中仍需要的元数据读取、组件识别与 `mod_environment()` 收敛为 `instance_metadata.py` 和职责明确的元数据值对象；具体类名建议为 `InstanceMetadata`。
- 更新 Core 根公开导出与 `Data/__init__.py` 职责清单，删除旧健康接口。直接调整项目内部调用，不增加兼容别名。
- 元数据读取继续校验 JSON 类型、文件尺寸、继承路径边界，并限制遍历层数、处理循环。无法读取的元数据停止本次解析并保留已读取信息，不生成健康状态或启动许可判断。
- 元数据结果仍提供实际加载器组件、Java 要求所需声明和模组环境信息。

### 2. 主仓库：停止产生健康协议和启动状态

- `ECL/services/game/scan.py` 改用元数据读取接口，保留组件归一化、继承 Java 要求及相关回退规则，删除扫描结果中的 `health` 和 `isBroken`。
- `ECL/services/game/resources.py` 的模组环境读取改用新接口，保留现有依赖诊断行为。
- 扫描继续保留具有有效实例标记的目录以及非空但损坏的版本 JSON，方便用户查看或修复；既有的无关目录与空 JSON 排除规则继续生效。
- 将健康测试重组为元数据读取、扫描候选与启动入口回归测试；更新扫描协议的预期字段。
- 正常启动过程中现有的文件下载、补全和实际错误处理继续执行。Java 运行时探测、用户路径及 IPC 输入校验沿用既有规则。

### 3. 前端：清理健康展示与限制

- `ScannedVersion` 类型移除 `health`、`isBroken`，更新展示模式夹具及各相关测试数据。
- 首页删除 `selectedIsBroken` 派生状态和相应按钮禁用条件；保留启动中、未选实例、未选账户等实际条件。
- `useInstanceManager.ts` 删除基于 `isBroken` 的启动前返回分支，使正常请求继续提交到现有启动 API。
- 实例列表的表格和卡片均显示正常启动入口，删除健康诊断描述与阻断徽章。
- 实例详情删除健康诊断区域及基于 `isBroken` 的启动/修复按钮条件；手动“校验文件”入口沿用现有操作。
- 资源安装候选删除基于 `isBroken` 的过滤，保留既有版本、加载器等匹配规则。
- 删除已无调用的 `instanceHealth` 多语言文案，按引用检查实际使用范围。

## 实施顺序

1. 用户审阅本文并明确确认开始实施后，检查三个仓库、相关本地 main 与未提交改动。
2. 建立修复前失败的回归：缺少传统主 Jar 路径的扫描实例仍有启动入口，并能提交正常启动请求；用 `26.4-snapshot-3` 作为其中一个实例标识。
3. 改造 Core 只读元数据接口，同步主仓库扫描、Java 要求和模组环境调用。
4. 清理前端类型、启动限制、诊断展示、候选过滤、文案与测试夹具。
5. 完成 Core、主仓库、前端检查和测试；通过前端 `pnpm check` 后执行 `pnpm build`。
6. 用构建产物实际启动 Windows 启动器，验证扫描结果、各启动入口和正式 IPC 调用；确认请求进入现有启动流程，而不是被旧健康预判阻断。
7. 检查 diff，分别以中文 Conventional Commit 提交 Core、前端和主仓库；主仓库包含两个对应 gitlink 及本文档。
8. 子仓库先同步原始工作区本地 main，再同步主仓库本地 main，保留无关改动。远程推送需本次变更另行明确授权。

## 影响范围与完成边界

本次移除扫描阶段健康预判及其 UI/候选限制，保留支撑加载器、Java 和模组功能的元数据读取。直接删除废弃字段和接口，不增加关闭开关、长期返回“健康”的空实现或旧协议迁移代码。

Windows 验收中应明确区分“成功提交启动请求”“已进入执行流程”和“真实游戏启动成功”。如无法获得用户所报告实例的真实安装文件，只能验证受控回归与正常入口，不能宣称该实际实例已启动成功。

## 实施结果（2026-10-10）

- Core 已移除健康诊断类型、主 Jar 预判及启动许可计算，改为 `InstanceMetadata.read`。仅保留有界继承元数据读取、加载器组件与模组环境解析，删除旧模块和旧公开导出。
- 主仓库扫描不再返回 `health`、`isBroken`，Java 要求与模组环境读取使用新接口。原有扫描候选规则保持有效，空 JSON 和无关目录继续排除；非空损坏 JSON 与只有 Jar 的实例目录继续保留。
- 前端删除首页、实例列表和详情页的健康状态展示及启动限制，删除资源目标中的健康过滤，清理扫描类型、展示模式夹具及六种语言的废弃文案。
- 未添加关闭开关、旧健康接口别名或返回固定健康状态的空实现。手动文件校验、正常启动补全与 Java 恢复功能沿用已有流程。
